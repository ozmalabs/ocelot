# Response-priority residual-continuation v1: diagnostic pilot

Date: 2026-10-06  
Status: diagnostic only; confirmatory panel not run.

## Scope and correction

The first pilot implementation replaced `WorldAdapter.comprehend` with a direct selected-settle call. That skipped host-side conceptualization and monitoring. Its graph divergence is a harness artifact and is excluded. The corrected runner preserves `WorldAdapter.comprehend` and intercepts only `inner.run_rules`; the source lock records selected areas `response_critical` + `global` and that host hooks are preserved.

One corrected paired worker was run per arm on the same seven-turn held-topic sequence. This is a diagnostic pilot, not a confirmatory estimate. Replies and the recorded task-outcome projections matched on all seven turns. The priority arm completed full all-area continuation without a round cap and had no final dirty residual. However, normalized semantic graph fingerprints and graph cardinalities failed parity on every turn. At turn 0 after continuation, priority had 25,027 nodes and global had 25,068. The reference-aware comparison identified missing graph records, including `GapLearningAssessment`, `HumanReview`, `GapRecurrence`, and conversational/message-shape records.

The corrected priority response path took 741 ms summed across the seven turns versus 1,029 ms in the global pilot. Priority then spent 63 ms in continuation versus 54 ms for global. These single-worker, uncounterbalanced wall-time observations are descriptive only; they do not establish a speedup.

## Interpretation and next gate

The selected-area API preserves dirty rules and reports zero residual after continuation, but dirty-bit carry alone does not establish equivalence when host hooks and rules consume transient or event-scoped state. Some work postponed past the response appears not to be reconstructible from the later graph state, even though the reply projection matches. This is a scheduling/order sensitivity finding, not a general failure of the API or a tractability result.

Do not run the three-worker confirmatory panel under the current parity gate. First trace the absent record families to their producing rules and input lifetimes; determine whether events are consumed, overwritten, or become ineligible before continuation. Then choose and preregister one of two valid objectives: (a) preserve event evidence so delayed work can catch up and require full graph parity, or (b) measure response equivalence with explicitly allowed deferred graph residue, plus a separate completeness/retention contract. Repeat the diagnostic, then run the multiworker panel only if the chosen protocol has a falsifiable, meaningful pass criterion.

## Diagnostic amendment: producer and event-state tracing

Source inspection establishes the relevant dependency chain: `register_gap_recurrence_identity` requires a `SelfConcern{status:"noted"}`; `register_recurrent_gap_identity` updates the recurrence count; `assess_recurrent_gap_for_supervised_promotion` requires count ≥2; and `open_human_review_for_recurrent_gap` consumes the resulting assessment. The rule order places `retire_duplicate_gap` at index 383, boot concern production at 386–389, recurrence registration at 1585–1586, and assessment/review at 1589–1590. Host-driven conceptualizer scans also advance request statuses outside rule effects.

The event-trace repeat establishes where eligibility is lost. Before turn 0, both arms have zero `SelfConcern`s. Before continuation, both have 11. Global has 10 retired concerns with recurrence flags set, 11 `GapRecurrence`s at count 11, 11 assessments, and 11 human reviews. Priority has 10 retired concerns with neither recurrence flag, one recurrence at count 1, and no assessments or reviews. Continuation leaves those values unchanged. The `conceptualizer_live` observation is `minted` with generation/transform checks complete in global, but remains `pending` in priority after continuation. Replies still match; graph parity still fails. This is an eligibility loss after a state transition: the later rules require `status="noted"`, and the retired duplicate's `has_self_concern` edge has already been removed. Zero dirty residual does not recover a predicate or edge that no longer exists.

The follow-up native write trace resolves the causal ordering for the turn-zero boot-integrity records. In the global arm, the progressing event sequence is `assess_compromised_boot` → `register_gap_recurrence_identity` → `register_recurrent_gap_identity` → assessment → human review → `retire_duplicate_gap`. In priority, it is `assess_compromised_boot` → `retire_duplicate_gap` → recurrence registration. The latter deletes `agent -has_self_concern-> concern` before the recurrence rules consume the duplicate concerns; later continuation cannot match those retired records. This is consistent with the execution semantics: global closure walks a dirty-rule pass snapshot, while selected settlement re-reads each area's dirty set at its turn and closes the selected area across rounds. Host calls between these fixpoints make the schedules non-equivalent. The failure is now localized to schedule ordering and lost eligibility, not just unexplained graph drift. Do not claim parity or a speed benefit. The next diagnostic should keep `retire_duplicate_gap` with deferred cleanup or otherwise preserve the global consumer-before-retire order, then check whether the six-rule partition still yields complete graph parity. Only after that repeat passes should the multiworker panel proceed.

## Correction after v1.2 API audit

The Python binding converted the canonical selected-area label `global` to a newly interned symbol rather than `Sym::default()`. Consequently, v1's selected arm did not select default-area rules. The recurrence ordering trace for explicitly reassigned named areas remains informative, but the v1 result does not validate complete selected-area execution or its missing-composer interpretation. The binding is fixed and the corrected one-pair diagnostic is reported in [v1.2 results](SUBSTRATE_RESPONSE_PRIORITY_RESIDUAL_CONTINUATION_V1_2_RESULTS_20261006.md).
