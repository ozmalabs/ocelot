## Generation and lineage records

A generation is an immutable record of one operator portfolio state, its parent generation, the active operator digests, curriculum version, training/selection task provenance, cumulative work and memory, proof/adoption/grounding outcomes, approval events and terminal disposition. Each candidate retains its own direct parent operator and candidate digest. Promotion adds a generation edge; it does not rewrite an ancestor. The initial P15 ancestor is the held `commutator` operator plus `commutator_square_v1`, which the user approved under the frozen digest but which remains pending graph promotion. A frozen ancestor arm always runs from a copy of the same starting graph and cannot observe updates from adaptive arms.

An agent-authored generation contains only graph-produced candidate data and declared measurements. Host code may install the frozen starting graph, provide world events and explicit human approval events, invoke bounded native ticks, and collect mechanical outcome records. A human-authored operator edit, changed verifier/criterion, manually edited candidate, missing ancestry edge, or absent approval event invalidates an autonomous-generation claim. Failed, timed-out, rejected, stale, or rolled-back generations remain in the lineage with their receipts and resource use; they are never silently removed or retried without charge.

Approval remains per candidate. The received approval events for `commutator_square_v1` and `commutator_cube_v2` each authorize only the named candidate and exact frozen digest. Every later candidate that reaches `awaiting_human` requires a separate explicit human approval against the criteria digest active for that candidate. No approval is implied by a positive score, a graph-authored proposal, or continuation of the experiment. Each accepted generation preserves the previous active operator as its rollback target. Any proof, adoption, grounding, source-epoch, or action-safety invariant violation suspends that generation and restores the last verified ancestor; rollback itself is recorded and charged.

## Fixed machinery and mutable state

Across all arms, freeze the engine binary/source, evaluator and proof checker, policies and criteria, PMB task generators, primitive access, action boundary, per-generation resource ceilings, train/selection/evaluation allocations, score definitions, and all sealed evaluation identifiers and labels. The curriculum can select only from declared training tasks generated from verified residual progress and cannot read or influence the sealed evaluation. Operator proposals and curriculum state are the only experimental adaptive state. Each arm has isolated mutable graph state and one shared `ThinkingBudget`; concurrency never creates additional budgets.

The three matched arms are:

1. **Unchanged operator:** frozen P14 starting portfolio and fixed, preregistered training schedule; no candidate promotion and no adaptive curriculum.
2. **Adaptive curriculum:** the same frozen P14 portfolio, with graph-authored training-task selection from verified residuals; no operator promotion.
3. **Full system:** graph-authored curriculum and operator proposal/verification/promotion lifecycle, with an explicit human approval event for every promoted candidate.

All arms receive the same generated task instances within each generation and family, primitive/model access, evidence opportunities, wall-clock caps and cumulative native-work ceilings. Each starts from its own copy of the same ancestor. The fixed arm is not reset to a later candidate; generation index denotes the matched evaluation checkpoint, not a hidden change to its operator.

## Split, allocation and registered analysis

The experiment requires at least three sequential operator generations. For each claimed PMB family, each generation and each arm receives at least 200 fresh matched evaluation tasks. Training, selection and evaluation instances are disjoint, and all three splits are disjoint from PMB v1 and every earlier phase. Use the §5 allocation formula with phase 15 (`25,000,000 + family_code*10,000 + control_block*1,000 + draw`); encode `family_code = 10*family_index + generation_index` with generation indices 1–3. Reserve distinct control blocks for training/development, selection, sealed evaluation, and integrity controls; enumerate every concrete seed in the standalone P15 preregistration and mechanically prove no collision. Each family/control has an independent deterministic RNG stream. The sealed evaluation list and outcome labels are kept only by the scorer.

The primary trend estimand is the generation slope in paired task success for the full system versus the unchanged-operator arm, using task-seed-matched binary outcomes and a preregistered logistic model with generation as the ordered predictor. Report per-generation rates, paired differences, Wilson 95% intervals, exact McNemar tests and the fitted slope with a corrected one-sided interval/test. Apply Holm correction across all claimed families at α=.01. A positive trend requires the corrected lower confidence bound for the full-versus-unchanged slope to exceed zero. The adaptive-curriculum arm separates curriculum effects from operator-generation effects. Exact work and task success are reported separately; a score gain at greater work is not an efficiency gain. Use paired 10,000-resample bootstrap intervals for work and latency as required by §5.

Any proof-binding, false-proof, adoption, source/epoch, input-isolation, external-action, or grounding violation is a zero-tolerance failure for that generation and the overall safety gate. A generation cannot compensate for another generation's regression. Unsupported adapters remain `UNSUPPORTED`, absent outcomes remain `NOT_RUN`, and timeouts remain failures/unknowns as specified by the family contract; none become zero or successful completion. No stopped run can be resumed with a replenished budget.

## Resource ceilings and deterministic parallelism

Every arm owns exactly one graph `ThinkingBudget` per generation, shared by all concurrent work in that arm. Freeze its numeric capacity and refill semantics in P15.E2 from the supported budget policy; no per-worker, per-area, or per-request copy is permitted. Hard execution ceilings are 400 outer ticks and 100,000 native rule steps per tick, with a 100,000-node and 64 MiB serialized-graph ceiling per arm/generation. The `ThinkingBudget` ceiling must be no larger than 100,000 declared work units per arm/generation and must be fixed before the draw. Count retrieval, proposal generation, verification, counterexample search, curriculum selection, rechecks, rollback, and primitive actions. Denials and failed operations are recorded; exceeding any ceiling terminates that arm/generation without dropping prior costs.

Parallel workers may execute only independent, predeclared task partitions. They receive reservations from the same shared generation budget before work starts. Receipts and mutations fold in canonical `(generation, family, seed, task, operation)` order using the existing native cycle-plan deterministic fold. If parallel execution cannot guarantee the same graph effects, receipts, denials and total work as serial execution, it is not admissible. Cancellation preserves completed receipts and debits; restart restores the exact generation budget and pending-work identities, preventing duplicate funding.
