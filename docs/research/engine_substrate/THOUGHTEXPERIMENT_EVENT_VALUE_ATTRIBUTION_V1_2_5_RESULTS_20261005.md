# Thoughtexperiment event snapshot payload accounting v1.2.5 results

The three-worker source-locked run preserves graph and closure parity across plain, traced, and exact modes. Ordered replay passes on complete direct, deferred, overlap, byte-control, and direct/deferred-conflict fixtures; report-object truncation again occurs at 16,384 retained objects, and event 33 is marked truncated. Peak worker RSS was 270,220–341,984 KiB, including fixture construction and all three execution modes.

The intended byte-cap gate **fails**. The non-formatting counter measures the cloned outer `Attrs` vector payload, while nested `Value` collections are Arc-backed and shallow-cloned. In the oversized-list control it records 128 bytes and retains the event, although the serialized event snapshot is 218,114 bytes. The 520-object event correctly retains 512 objects and truncates. The 33-event report-object fixture records 16,384 objects, 524,288 payload bytes, and 1,652,753 serialized event bytes. These counts are different quantities and neither gives a total RSS bound. The result shows that accounting cloned container allocation alone is insufficient for enforcing a serialized snapshot limit.

The locked analyzer and corrected analyzer both fail the oversized-value expectation; the original also repeats its known CurPercept target-selection error. Preserve both outputs. The corrected analysis confirms all other applicable structural, replay, parity, object-cap, and conflict checks. This result does not validate bounded serialized capture, edge deletion/attribute routes, or self-directed diagnosis/repair.
