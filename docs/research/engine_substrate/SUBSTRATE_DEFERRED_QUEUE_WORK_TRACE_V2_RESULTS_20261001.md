# Deferred queue operation-work trace v2 results

**Result:** operation-level native work rows reconcile with the existing deferred-family counters in all three measured phases: full closure, scoped-only pending work, and global fallback.

The source-locked panel contains 18 fresh worker processes: writer counts 1/2/4, two replications, and full/scoped-only/scoped-fallback arms. All **229/229** independent checks pass, including source/native stability, fixed-point behavior, explicit pending status, exact full/fallback graph-state parity, zero trace drops, supported operation markers, family-level enqueue/drain reconciliation, and producer RuleIdx attribution.

Each measured full-closure phase records three queue items enqueued and drained, one each for RulePatch, TrackIdentity, and NetCollapse, with three corresponding drain batches. The scoped-only phase records the same three enqueues and no drain, and reports deferred work pending. The fallback phase records no new enqueue and drains those three items in three family-specific batches. Runtime trace units equal the independent family counters in every cell and phase.

One instrumentation change was required: `run_rules_scoped_delta_report` previously lacked a work-operation guard, so its scoped scheduler/effect work had no operation ID and emitted no runtime work rows. V2 adds that trace guard around the existing scoped route. The earlier v1 pilot captured full/fallback events but zero scoped events; it is retained as a failed instrumentation pilot, not combined with v2 measurements.

The small fixture has identical scheduler totals at writer counts 1/2/4: full closure records three scheduler passes and six selected-rule units; fallback records two passes and four selected-rule units. Scoped-only records no scheduler pass/selection metrics in this trace, though its queue events and operation marker are visible. These counters do not imply size-independent scheduler cost in general: the fixture's successful writer/effect work remains fixed while unrelated target population changes. This is instrumentation and bounded workload evidence, not complete CPU accounting, natural queue frequency, or frame-partition safety. The queue audit for `rule_edits` and `fb_samples` remains separate.
