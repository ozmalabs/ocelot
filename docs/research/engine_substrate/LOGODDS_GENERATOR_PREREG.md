## 1. The translate-vs-new-kind decision — registered BEFORE reading further code

**Prediction, made from reading `runners/dsl/src/shape_decode.rs` (main tip)
before writing any code this rung:**

`shape_decode.rs:786-820` (`apply_translate_once`) already implements exactly
the semantics an unbounded, signed, no-wrap evidence counter needs: `v -> v +
offset[j]`, **no wrap** (unlike `modular`), **no origin-normalization**
(unlike `rotation90`/`reflection_*`/`scale2` — translation is ABOUT position,
re-basing to a bounding box would erase the very thing being expressed). The
module's own doc for this generator (`:786-798`) states the exact target use
case: *"a rigidly-translating pattern is the SAME held shape stepping by `k`
along a minted `latent:translate` dimension... any two frames of a constant-
velocity orbit are mutual translates."* An evidence count that steps +1 per
confirming observation is a constant-velocity orbit at velocity 1 along one
axis — structurally the identical shape.

**Registered decision: `translate` genuinely suffices for the IN-FRAME STEP'S
SEMANTICS.** No new Rust generator `kind` will be added. `apply_generator_once`
/`apply_generator_k` (`:836-867`) will not be touched.

**Registered CAVEAT, stated before verifying it, not after (so it can be
checked rather than assumed away):** `apply_generator_once`/`apply_translate_once`
are private functions internal to `shape_decode.rs`, invoked only from inside
`ShapeDecode`/`TransformDecode`/`DimInfer`/`TimeInfer`'s own `eval_*` bodies —
there is no standalone Term a plain graph *Rule* can call to literally
*perform* one generator step as a side effect. This will be confirmed (not
assumed) by grep before the build proceeds. **Prediction: it holds**, and if
it does, the actual RUNTIME MUTATION of the evidence counter (the "+1 on each
confirming observation" event, executed inside `can_native_hebbian_reweight`)
will be done with ordinary, already-existing Term arithmetic (`Plus`/
`IfThenElse`) inside a `set_attr` rule effect — the same idiom
`can_tick`/`codebook_epoch` already use for every other mechanically-bumped
integer counter in this codebase (`can_native_reimplementation.json`'s own
`noted_tick` precedent). The declared `DimensionGenerator{kind:"translate"}`
node is what a **future** `DimInfer`/`TimeInfer` integration could use to
*recognize*, after the fact, that an observed evidence trajectory is a
translate/orbit — recognition and runtime-stepping are different operations,
and only the first needs the generator kind at all. This is registered as the
predicted DIVISION OF LABOUR, to be confirmed against the read source, not
retrofitted into the RESULTS doc after the fact.

## 2. The rendering-function formula — two candidates, registered before picking

**Candidate A — full Griffiths & Tenenbaum causal support.** A Bayesian
log-likelihood-ratio over a full 2×2 contingency table (cause present/absent
× effect present/absent), marginalized over strength parameters. Rejected as
the build target: the graph as built (CAN coactivation) does not populate a
full 2×2 table — there is no "antecedent absent, consequent present/absent"
observation being tracked, only "both committed same-sign" (confirm) vs.
"both committed, opposite-sign" (disconfirm). Importing this formula would
require inventing data the mechanism does not actually observe.

**Candidate B (registered choice) — Laplace-smoothed empirical log-odds from
two accumulated counts:**

```
log_odds = ln( (confirm_count + 1) / (disconfirm_count + 1) )
```

Justification, registered before building: (1) uses exactly the two integers
the mechanism actually accumulates (confirm/disconfirm event counts — no
invented data); (2) the `+1` is standard Laplace/add-one smoothing (a uniform
Beta(1,1) prior), not a borrowed human perceptual constant — it is what keeps
`ln` well-defined at `(0,0)` (→ 0, correctly "no evidence yet, no lean either
way") and prevents a division by zero; this is NOT the ~7-bin-count issue
`CAN_SOLVER_THEORETICAL_LIMITS_RESEARCH.md` §5.3 warns against — it is a
principled statistical constant, not a channel-capacity number, and no bin
count or threshold is introduced anywhere by this formula; (3) it is
monotonic in both counts (more confirm → higher; more disconfirm → lower),
symmetric (equal counts → 0, neutral), and matches Rescorla-Wagner's own
trial-level reading, which `CAUSAL_LINKAGE_DIMENSION_RESEARCH.md` §8.2 named
as the open sub-question this rung resolves by picking the trial-count
reading over the schema-static reading.

**Registered Term composition — zero new Rust:** `Log{arg: Div{a: Plus{confirm,
1}, b: Plus{disconfirm, 1}}}`. `Log`/`Div`/`Plus` all already exist
(`term.rs:499-511`, confirmed by reading before writing this document).

**Registered idiom precedent to mirror:** the render is evaluated live via
`Substrate.evaluate(term, bindings)` (already used by
`tests/test_can_native_reimplementation.py::test_polarization_via_max_steps_
sweep`, `:377-381`) — a pure read, no graph mutation — the same "pure
comparator, kept separate from the canonical stored representation" shape as
`cmp_value_lex` (`value.rs:461`) and as `can_ops.rs::mt_mean_field_marginal`'s
own "pure read, no graph mutation" cross-check in the item-3 live
demonstration. **Registered constraint, checked at build time:** the render
formula must never appear on the right-hand side of a `set_attr` effect
targeting the evidence-count-holding node's own `evidence_confirm`/
`evidence_disconfirm`/`evidence_tick` attrs — those stay integer, in-frame,
mutated only by `Plus(..,1)`.

## 3. Where the in-frame counters live — registered before writing the rule

`can_native_reimplementation.json`'s `causal_influence` edge cannot itself
carry a live-updated attribute: the rule-effect vocabulary
(`rewrite.rs`'s `Effect::SetAttr` family) only targets a bound **node**
variable — there is no `set_edge_attr` effect (confirmed by grep before
writing this document: `grep -rn "set_edge_attr" runners/dsl/src/*.rs`
finds it only as a private `graph.rs` Rust-API method never exposed to rule
effects). The existing `Coactivation` node (already minted by
`can_native_note_coactivation`, already bound in `can_native_hebbian_mint`'s
own match pattern via `a -coactivated_with-> coact -coactivation_of-> b`) is
the correct place: it already reifies "the evidence relationship between a
and b" as a proper node, `SetAttr`-able. Registered plan: extend
`Coactivation` with `evidence_confirm`/`evidence_disconfirm`/`evidence_tick`
(all integers, initialized at `note_coactivation` mint time), bumped by
`hebbian_mint` (first confirming recurrence) and by a new consolidated rule
`can_native_hebbian_reweight` for every later tick.

**Registered starvation-avoidance decision, made BEFORE writing the rule, not
discovered by re-running a failing test:** `CAN_NATIVE_REIMPLEMENTATION_
RESULTS.md` §3 already found and fixed a general `run_rules` cold-path
property — sibling rules competing to update the same kind of node can starve
each other indefinitely, because the cold path commits exactly one
progressing binding per rule per pass and moves on. A separate
`can_native_hebbian_reweight_confirm` / `_disconfirm` rule pair would be
EXACTLY that shape (two siblings racing to update the same `Coactivation`
node). Registered decision: **one rule**, `can_native_hebbian_reweight`,
computing which counter to bump via `IfThenElse`/`Gte`/`Lt` on
`Times([a.state, b.state])`, mirroring `can_native_update_3state`'s own
already-proven fix.

## 4. Live-demonstration scenarios, registered exactly

**(a) In-frame stepping.** Build an isolated 2-Concept network (mirroring
`test_hebbian_mint_on_recurrence_not_on_first_sight`'s own isolation
discipline — `discrete_mode="static"` so item-3's relaxation rules never
interfere). Drive `can_tick` through >=4 mechanically-bumped ticks with a mix
of same-sign (confirm) and opposite-sign (disconfirm) states at each tick.
**Prediction:** `Coactivation.evidence_confirm`/`evidence_disconfirm` are
real Python `int`s (never float) at every tick, strictly non-decreasing,
incrementing by exactly 1 on the tick(s) the corresponding condition held,
unchanged (frozen) on ticks where the condition did not hold.

**(b) Cross-frame log-odds render.** Build two `Coactivation` records: one
heavily confirmed (e.g. `confirm=8, disconfirm=0`), one rarely confirmed
(e.g. `confirm=1, disconfirm=0`). **Prediction:** the render Term, evaluated
live via `Substrate.evaluate`, ranks the heavily-confirmed record's log-odds
strictly higher than the rarely-confirmed one's, and a third record with
`confirm=0, disconfirm=0` renders exactly `0.0`. **Prediction, checked
directly:** after evaluation, `Coactivation.node()["attrs"]` contains no
`log_odds`/rendered key at all — the render never touched graph state.

**(c) Item 4 end-to-end.** Two Concepts, `discrete_mode="static"`, driven
through: tick 0 (first sight, notes only) → tick 1 (recurrence, mints the
edge, `evidence_confirm=1`) → ticks 2-4 (three more same-sign observations,
each on its own `can_tick` bump) → tick 5 (one opposite-sign observation).
**Prediction:** after tick 4, `evidence_confirm==4` (1 at mint + 3
reinforcements), `evidence_disconfirm==0`; after tick 5,
`evidence_disconfirm==1`; the log-odds render at that point is strictly
positive (net confirming) and strictly less than the render would be with
`disconfirm=0`, i.e. the one disconfirming observation measurably moves the
render down. **This is the exact scenario `CAN_NATIVE_REIMPLEMENTATION_
RESULTS.md` §5 left blocked** ("graded reweighting of an already-minted edge
is out of scope... named as blocked, not attempted").
