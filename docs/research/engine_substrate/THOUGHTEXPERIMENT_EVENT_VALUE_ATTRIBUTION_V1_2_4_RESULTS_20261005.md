# Thoughtexperiment event attribution report-object cap v1.2.4 results

## Result

Three source-locked workers pass the report-object boundary pilot. A workload with 33 rules, each writing 512 distinct nodes, reaches a fixed point after 33 progress steps and produces 33 rule events. The first 32 events each retain 512 complete before/after pairs (16,384 total). Event 33 retains no pairs and sets the truncation flag. The traced report estimates 1,915,904 bytes for the retained before/after representations, below the 4 MiB report byte budget. Plain, traced, and exact-snapshot modes reproduce identical final graph states and closure summaries; the full graph contains all 16,896 intended writes, so the final 512 changed nodes are deliberately outside event-value replay because their event was truncated.

The capture and independent analysis confirm that the report object ceiling is reachable and fails closed on the next group. They also confirm an algebraic property of the configured caps: with at most 512 objects per event and 16,384 objects per report, no more than 32 full events can be retained. At 64 KiB/event, that is at most 2 MiB of counted snapshot representation, below the 4 MiB report byte cap. Thus the report byte cap cannot bind before the report object cap under current accounting. This is a derived bound from the current cap counters, not an RSS bound.

The original locked analyzer still reports the known last-writer target-selection false negative; it chose the unrelated PrevPercept identity field. A separately named correction binds the assertion to the actual CurPercept conflict node and passes the remaining checks. The failed output is preserved. Worker maximum RSS ranged from 268,416 to 337,940 KiB, but this is a whole-worker peak covering the large graphs, all three comparison modes, Python snapshots and capture assembly, so it is not attributable to the event journal alone.

## Remaining limits

The run does not isolate journal RSS or formatting temporaries. The `Debug` estimate remains a representation-size proxy, and no encoded-JSON output cap exists. Other mutation routes, repeated writes within a single event, natural-task prevalence, target-blind diagnosis, and repair utility remain open. The report byte cap should be reduced to a reachable bound, or the object limits should be expanded, before it is treated as an independently meaningful guard.
