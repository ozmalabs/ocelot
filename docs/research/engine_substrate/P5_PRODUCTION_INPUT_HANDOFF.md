# P5 Controlled-Run Input and Execution Gate

**Master run:** `P5-MASTER-001`
**Dispatch:** `DISPATCH-063`
**Runsheet:** [`P5_MASTER_RUNSHEET.md`](P5_MASTER_RUNSHEET.md)

**Status:** Track A is the active minimal diagnostic frontier, blocked pending real signed-environment gates. This handoff creates no production artifact, signature, task release, execution evidence, cloud mutation, or runsheet transition.

## Purpose and two-track model

This is the project-control handoff for moving from repository-only review to one narrow self-custodied attested diagnostic. It is not a human-supplied production-input checklist. It defines two separate tracks:

- **Track A — minimal self-custodied attested diagnostic:** mandatory canonical generated inputs, exact candidate image/closure, one real Confidential Space launch and verified attestation, timing before seed, bounded native/OOM/deadline evidence, canonical receipts, and a KMS-signed final result.
- **Track B — optional hardening/release qualification:** optional pre-run lock signing (if Track A elects that mode), optional post-sign GCS persistence, GCS-only least-privilege cleanup, broader operational qualification, and future release work. Track B does not gate Track A.

Track A does **not** require GCS persistence after signing, a pre-run KMS lock signature when the final result binds the exact immutable lock representation/digest, separate GCS-only least-privilege cleanup, controls/contrasts beyond the bounded diagnostic contract, an independent evaluator, exact CPU timing, P5-E1/P5-E2, or P0-A/P0-E1/P0-E2/P1–P4 upstream gates. Those items are not waived for a future release; they are outside DISPATCH-063’s Track A scope.

There are no externally supplied production inputs and no external task provider. The project generator/control plane creates the manifest, split, private truth/store, task set, controls, worker/evaluator contracts, policy, provenance, and lock representation. “Project-generated input” means canonical commitment data, not proof that execution occurred. “Production evidence” means only facts produced and verified at the signed boundary: Confidential Space attestation, KMS signature, FreeTSA timing, authenticated supervisor evidence, canonical receipts, and the final result binding.

### Track A MVP task/control contract

The active MVP selects, rather than inherits, its execution surface:

- **One task:** exactly one canonical generated case identified in the lock by `case_id`, `case_digest`, and ordinal; one `P5R0WorkerTaskV3`; one `cold_reset` native invocation under the locked task budget. The case split is metadata only; no held-out, generalization, or replication claim is made.
- **One control:** exactly one selected `illegal_action` protocol-boundary control, using the same worker/evaluator seam and expected to produce a verified rejection/protocol error. An unexpected legal action fails closed.
- **No implicit catalog:** no other arm, repeated episode, memorization/permutation/semantic/safety/leakage/containment/resource/negative-transfer control, mechanics contrast, aggregate score, or full P5 task matrix is in scope unless explicitly selected, rebound into the immutable lock, and accepted as a changed MVP.
- **Safety evidence remains mandatory:** authenticated lifecycle, bounded native resource behavior, real OOM/deadline handling, process-group cleanup, rollback/impasse, and canonical receipts are required for the selected invocation. These checks are not extra P5 arms or controls.

### Mandatory pre-run input delivery versus optional publication

The exact generated public inputs and private case store must be provisioned to an approved durable boundary before launch, but this pre-launch step is provisioning only: no workload may read, rehydrate, derive, seed, or issue a task from those inputs before verified Confidential Space attestation and capability activation. After attestation, the locked workload must read the exact generated bytes from that attested durable path, verify canonical bytes/digests and access binding, and rehydrate the private store in a fresh process. Delivery, access, digest, or rehydration failure is a Track A stop. A local `var/` fixture, process-local truth, unsigned request, or post-sign object cannot satisfy this prerequisite. If GCS is selected for this **pre-run input delivery**, the post-attestation read is part of the locked workload path and is not the optional publication described below.

After the canonical result has been created, its result seal has been persisted and verified, and the exact verified seal/result digest has received the final KMS signature, GCS may optionally publish the already signed result and required public metadata. This post-sign publication is transport/durability only: it is not the input-delivery gate, is not an authority, and object existence is never evidence or a substitute for signing.

A pre-run lock signature is an optional Track A signing mode, not a hidden prerequisite. If omitted, the final KMS-signed result must bind the exact immutable canonical lock representation/digest and all generated, provisioned, read, rehydrated, selected-contract, candidate, attestation, timing, supervisor, receipt, canonical-result, and verified-seal inputs. If used, it must be a real KMS operation over that exact lock in the approved signed boundary, verified against the bound public authority; a local signature or request does not count, and final-result signing remains mandatory. GCS input provisioning before launch is mandatory when it is the selected durable boundary, but the attested workload may read and rehydrate those inputs only after capability activation. GCS publication after final signing is optional and never evidence merely because an object exists. If the exact final binding is missing or ambiguous, the run fails closed. The Track A completion artifact is the verified KMS-signed final result—not a lock-signing request, local lock, or GCS object.

## Required Track A order

1. **Pre-launch provisioning only.** Run the frozen project generator, select exactly one canonical case, one `cold_reset` task contract, and one `illegal_action` control, and bind the exact generator/version/seed/output, selected-contract, candidate, closure, policy, provenance, and immutable-lock commitments. Provision the exact public/private package to the approved durable boundary and record its canonical delivery/provisioning digests. Before attestation, do not read, rehydrate, derive, seed, issue, or execute from those inputs; provisioning is not execution evidence.
2. **Launch once and verify attestation/capability activation.** Start the exact candidate in Confidential Space and verify the real Google-signed claims bound to the candidate, project/zone, TEE/hardware, Secure Boot/vTPM, WIP/IAM, provisioned-input commitments, and lock. Only after verification may the locked workload activate KMS/GCS/timing/task capabilities.
3. **Read and rehydrate after attestation.** From inside the attested workload, read the exact generated bytes from the approved durable path, verify access policy, canonical bytes, and all digests, and rehydrate the private store in a fresh process. Any mismatch, stale object, access failure, or process-local fallback is a Track A stop. This is the first permitted input read; it is distinct from optional post-sign publication.
4. **Obtain timing before seed/input/task.** Use the pinned FreeTSA/RFC-3161 bridge and durable ledger to obtain and verify the timing record. Only after the verified record is committed may the service derive `timing_record_digest`, `input_seed_digest`, and `input_digest`; no caller timestamp, local clock, caller seed, or pre-timing private task input is authoritative.
5. **Execute the selected bounded native MVP.** Consume only the freshly rehydrated selected task/control envelope through the native worker and authenticated supervisor: one case, `cold_reset`, and one `illegal_action` control. Record lifecycle, worker exit, OOM/deadline behavior, process-group cleanup, and rollback/impasse evidence. Any uncertain failure is an impasse, not a result.
6. **Create and seal the canonical result.** After execution, create the canonical result from the verified evidence and selected disposition. Persist the result seal to the approved durable seal path and independently verify the persisted seal and the exact seal/result digest. No KMS final-result signing may occur before this verification succeeds.
7. **KMS-sign the exact verified seal/result digest.** Assemble the final signing request over the exact immutable lock representation/digest, every generated/provisioned/read/rehydrated input commitment, selected task/control contract, candidate/closure, attestation, timing/input chain, supervisor/resource evidence, canonical receipts, canonical result, verified persisted result seal, and disposition. If the optional pre-run lock-signing mode was selected, verify that it is a real KMS signature over the exact immutable lock; if it was omitted, the final signature must carry that exact lock binding. Obtain and verify the real final KMS signature. A lock signature, request, or unverified seal is never a final result.
8. **Optionally publish after signing.** If chosen, write only the already signed result and permitted public metadata to GCS after final signature verification. This is transport/durability only; object existence cannot upgrade evidence. Track B hardening and P5-E1/E2/release qualification remain separate and are not executed or waived by this sequence.

## Forbidden substitutions and fail-closed rules

- A generated artifact, review manifest, unsigned lock request, local lock, local signer, fixture, test, or normal boot is not a signed execution receipt.
- The selected task/control contract must be explicit in the immutable lock; omitted arms, controls, and contrasts are out of scope and cannot be claimed from the generator’s full catalog.
- Existing Cloud Run/VM readiness is not Confidential Space execution attestation.
- Caller/runner timestamps, durations, timeout flags, CPU times, seeds, booleans, results, or “supervisor” observations cannot authorize or prove execution.
- Timing establishes freshness/order and coarse provider-observed bounds only; it must never be described as exact CPU timing.
- A callback, Python fallback, non-native harness, image pull, privileged mode, host mount, network path, or unverified local process cannot satisfy the native gate.
- Mandatory pre-run input delivery, digest verification, and fresh-process private-store rehydration cannot be replaced by a local fixture or optional post-sign GCS publication.
- The supervisor validator checks a closed shape and commitments; it does not create observations, attest a machine, or promote local evidence.
- A KMS request, local signature, or pre-run lock signature alone is not a final result. The real final KMS signature must cover the exact immutable lock and all selected Track A inputs. If a pre-run lock signature is used, it must be real KMS signing in the approved boundary.
- Missing, stale, malformed, locally authored, or mismatched attestation, timing, closure, supervisor evidence, receipts, final binding, or KMS signature produces a typed redacted impasse.
- OOM, deadline, receipt failure, replay, sequence conflict, authority mismatch, credential expiry, persistence failure, or cleanup uncertainty must terminate/rollback as applicable, append failure evidence, and never produce a trusted result.
- Post-sign result publication is forbidden before final signing. If post-sign publication is selected, it is transport/durability only; approved pre-run input delivery is a separate mandatory boundary when selected. GCS-only least-privilege cleanup remains optional Track B hardening and cannot mask a failed gate.
- Nothing in this handoff creates independent evaluator custody. The project authority, scorer, private truth, receipt chain, and result seal remain self-custodied; Confidential Space and FreeTSA attest workload/timing facts only.
- P5-E1, P5-E2, P0-A, P0-E1, P0-E2, and P1–P4 upstream gates are outside this DISPATCH-063 handoff. No result may imply that they passed.
- No KMS call, GCS upload, VM/deployment change, FreeTSA task timing call, supervisor invocation, task execution, or runsheet mutation may be performed by this review-only handoff.

## Exact remaining Track A prerequisites

1. **MVP authorization and immutable selection:** master-authorize one case (`case_id`/digest/ordinal), one `cold_reset` task, one `illegal_action` control, the resource/deadline profile, and explicit omission of all other arms/controls/contrasts; bind the selection into the lock.
2. **Mandatory input delivery:** review and provision the durable pre-run delivery path for public inputs and private truth, including access policy, exact byte/digest checks, and fresh-process rehydration. This remains required even if no result is published to GCS afterward.
3. **Exact candidate closure:** provide the image digest, native worker, crun/runtime, seccomp, argv, host/resource profile, and evidence/seal/rollback paths, with invocation-boundary recheck.
4. **Real Confidential Space evidence:** complete one approved launch and verify Google-signed image/project/zone/TEE/Secure Boot/vTPM/WIP-IAM/input/lock claims before capabilities activate.
5. **Timing-first evidence:** obtain verified FreeTSA/RFC-3161 timing through the pinned bridge and durable ledger, then derive and preserve `timing_record_digest`, `input_seed_digest`, and `input_digest` before task issue.
6. **Bounded native evidence:** execute the selected task/control through the native worker and authenticated supervisor, with real lifecycle, OOM/deadline, process-group cleanup, rollback/impasse, and canonical receipts.
7. **KMS final result:** verify the receipt chain and real final KMS signature against the bound public authority. If pre-run lock signing is selected, separately verify real KMS signing of the exact lock; if omitted, verify the final signature’s exact immutable-lock/all-input coverage.
8. **Disposition and claims:** emit only the redacted signed diagnostic or typed impasse. Optional post-sign GCS publication may follow A7 but cannot satisfy or upgrade any prerequisite.

## Acceptance rule

The master may accept a **Track A diagnostic** only when the exact project-generated inputs are provisioned before launch, then read from the attested durable path and freshly rehydrated only after verified Confidential Space attestation/capability activation; the immutable lock explicitly selects one task/`cold_reset` arm/`illegal_action` control and omits the rest; candidate closure is bound; timing is verified after rehydration and before seed/input/task derivation; authenticated native/supervisor evidence includes bounded OOM/deadline behavior and cleanup; canonical receipts and the canonical result are verified; the result seal is persisted/read back and verified; and a real KMS-signed final result binds the exact verified seal/result digest, immutable lock representation/digest, and all generated/provisioned/read/rehydrated/selected-contract commitments. A pre-run lock signature is optional: if used it must be real KMS signing of the exact lock; if omitted, the final signature must provide the exact binding. GCS publication and separate GCS-only least-privilege cleanup are not Track A acceptance criteria.

The master may not treat Track A as independent evaluation or release qualification, perfect secrecy, or any broader security claim. Track B remains optional and non-blocking; P5-E1/E2 and all upstream gates require a future master-authorized scope. Until Track A’s exact evidence exists, the strongest output is a self-custodied, redacted readiness/impasse report, not a capability or release result.
