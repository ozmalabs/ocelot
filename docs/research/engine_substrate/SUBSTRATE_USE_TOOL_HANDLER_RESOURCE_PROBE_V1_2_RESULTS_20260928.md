# UseTool handler resource and repeatability probe v1.2 — results

Three independent fresh-process workers pass all seven analyzer gates. The source and resource snapshot is unchanged across capture. All 15 registered handlers are represented; 14 return successfully and repeat identically within each worker and across workers. `text_valence` is the exception: it raises `RuntimeError` after each invocation attempts `nltk.download("opinion_lexicon", quiet=True)`. The two attempts per worker show that a failed first call does not populate the handler cache.

WordNet/OMW ZIP archives and the four selected Wiktionary/ConceptNet slab pairs are present and hashed in the source lock. The WordNet-backed representative cases succeed offline. The fixed lexical-set handlers also succeed. This establishes deterministic repeated outputs for these fixed cases and this resource snapshot, not general semantic correctness, whole-handler purity, or external-version invariance. The SentiWordNet archive is absent; the chosen `derive_opposes(deafening, silence)` case exits through an earlier layer, so this probe does not test its SentiWordNet-dependent fallback.

The earlier v1 pilot is retained as a failed runner capture: subprocesses could not import `domains` because the repository root was absent from child `sys.path`; no handler invocation completed. v1.1 fixed child imports but omitted NLTK archive identities from its lock, so v1.2 is the analyzed capture. The lock refuses overwrite.

The result sharpens the predicate contract: handlers that are read-only with respect to the graph can still perform downloads, throw on missing external data, and be invoked repeatedly. Predicate eligibility must therefore require pinned resources, no acquisition during evaluation, stable failure semantics, and declared invalidation/versioning. This result does not exercise changed-resource invalidation or the full seed boot.
