# Rule-run progress-budget overshoot v1.1 results

All gates pass in three fresh workers for N=1/2/4/8/16/32/64 independent dirty rules. With `max_steps=1`, the first call applies the entire eligible batch: progress steps and native attr-set attempts equal N, and every authored target attribute is present. The report returns `progress_budget_reached`; overshoot is exactly N−1 (0, 1, 3, 7, 15, 31, 63). A second call reaches fixed point with zero progress and no additional attr-set attempts. Integer operation counters replicate across workers.

This confirms that `max_steps` is checked at scheduler-pass boundaries, not as a strict per-rule or per-effect cancellation limit. The implementation runs all rules selected into the dirty batch before checking the outer loop again. Therefore a call with budget one may perform N rule firings in one pass, and it may return after that pass with partially completed higher-level work. Callers needing tighter interruption boundaries must constrain batch size, split stages into separately triggered closures, or add a finer cancellation mechanism. The result does not bound overshoot for arbitrary rules/bindings or wall-clock duration.

The v1 raw capture is exploratory: its analyzer expected a `graph_writes` counter that the scale audit does not export. v1.1 gates on exact attributes and native `rule_effect_attr_set_attempts` instead, with a fresh lock and capture.
