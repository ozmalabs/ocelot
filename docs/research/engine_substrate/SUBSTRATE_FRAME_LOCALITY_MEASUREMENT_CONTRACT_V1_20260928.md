# Frame locality measurement contract v1

Date: 2026-09-28  
Status: operational definition for the next structural gate; not a claim that cheap cuts are learned or common.

## Why a shared contract is needed

The current evidence reports several different structures: rule read/write dependency graphs, ownership projections over a runtime graph, visual neighbor coupling, and factor-graph/treewidth properties. Their edge counts and widths are not interchangeable. A low raw edge cut in the state graph does not establish a small inference separator; a small owned induced width does not establish that effects stay inside that ownership boundary; a scheduler access key is not a learned frame.

## Objects and quantities

Every future frame-locality report must state which graph it measures:

1. **State graph** `G_state=(V,E)`: substrate nodes and typed edges at a named checkpoint. Report node/edge counts and a canonical snapshot hash.
2. **Rule-dependency graph** `G_rule=(R,D)`: a directed dependency from producer rule/effect to consumer rule/match field under a named access-set extractor. Report extraction completeness, global/dynamic keys, vertices/rules, dependencies, and whether values came from static source or runtime trace.
3. **Inference primal graph** `G_inf=(X,F)`: variables connected when they share a factor/constraint. Report factor scopes and domain sizes, then report exact treewidth or a named upper bound. A primal-graph treewidth is not inferred from `G_state` sparsity.
4. **Frame interaction graph** `G_frame=(Π,C)`: declared or learned frames connected by dependencies crossing frame membership. Each frame must include a node/rule/factor ownership map and provenance (`authored`, `protocol projection`, `learned`, or `algorithmically proposed`).

For a particular object, define a partition `Π={F_i}` and report:

- frame size `|F_i|` under the object-specific unit (nodes, rules, or inference variables);
- crossing incidence count `c_i`, counting each distinct dependency/factor incidence once under a stated direction convention;
- distinct external boundary units `b_i` (nodes/rules/variables), separately from incidence count;
- boundary interface `I_i`: the exact state variables/attributes read or written across the boundary, including their domain sizes when finite;
- maximum frame interaction degree and the distribution across frames;
- decomposition width (exact or upper bound) on `G_inf` or another explicitly named graph, with algorithm and proof status;
- partition discovery/maintenance cost, separately from execution cost.

“Small boundary” means a bound on the task-relevant interface `I_i` or separator state, not merely small `c_i`, few neighboring nodes, or low `|F_i|`. If interface domains vary, report `k_i=|I_i|` and the product of interface domain sizes `q_i=∏_x |Dom(x)|`; where domains are continuous/large, record dimension and representation instead of forcing a finite-state claim.

## Correctness and cost comparisons

A partitioned execution is comparable to a monolithic execution only when both use the same input graph, rule/factor snapshot, update semantics, and termination condition. Report exact state/result parity when semantics should be order-independent; otherwise report the declared invariant (for example, both reach an independently checked fixed point while terminal states may differ by basin). Count and time partition construction, boundary messages/reads, rematching, mutation notification, and settlement separately. Include a coupled/high-boundary control and mutation probes that exercise both insertion and deletion/update paths. A notification-omission control is required when the algorithm relies on caller-supplied wakeups.
