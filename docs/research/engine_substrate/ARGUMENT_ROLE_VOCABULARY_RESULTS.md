### 2.3 The mint-time guard, sd-loop shaped

Mirrors two already-established precedents in this exact codebase, not a fourth
invented mechanism: `seeds/blob_edge_correspondence.json`'s
`blob_mint`/`blob_recognize` (recognize/mint duality, the `add_edge`-needs-
match-bound-vars engine constraint reused, not reinvented) and
`seeds/gap_awareness.json`'s `note_*` gap-filing rules (the honest-residual
terminal that files a `SelfConcern` instead of guessing).

Three rules, `seeds/argument_role_vocabulary.json`:

- **`role_recognize_exact`** — a pending `RoleUseCheck` whose owning cue's
  `relation` string is BYTE-IDENTICAL to an already-held OTHER `RelationCue`'s is a
  pure keyword-synonym addition. This is the ONE case the guard is CONFIDENT is
  safe without semantic judgement — identical structure, not merely an identical
  bare token. `add_edge` target is Term-found (`Exists`), not match-bound, so the
  rule sets status only; Python (`check_new_relation_cue_roles`) re-resolves the
  `ArgumentRole` by name and wires the edge AFTER `run_rules()`, executing the
  rule's decision, never making one — the exact `_resolve_blob_edge`/
  `sd_dedup_existing` pattern.
- **`role_mint_fresh_token`** — a pending `RoleUseCheck` whose token names NO
  existing `ArgumentRole` is genuinely new — safe by construction, nothing to
  collide with yet. Mints the `ArgumentRole` and wires it in the SAME rule
  (match-bound, mirrors `blob_mint` exactly).
- **`role_flag_collision`** — the honest residual: an existing token reused under a
  relation tuple that is NOT identical to any held cue's. Files a
  `SelfConcern{kind:'argument_role_collision', content:<token>,
  cue_name:<the new cue>}` and leaves the edge UNWIRED — "flag it, don't silently
  install a second meaning under one name," verbatim from the charter.

`domains/reflective_faculty.py::check_new_relation_cue_roles` (new,
`_load_argument_role_index` alongside it) is mechanical ingest + read-back, mirrors
`record_correspondence` byte-for-byte in shape: write one pending `RoleUseCheck`
per distinct uppercase token, `run_rules()`, read back the verdict, re-wire only
the one case the engine cannot wire from inside a rule. Wired into
`ground_predicate`'s ONE real live cue-minting call site (confirmed by grep — the
only `teach(agent, "RelationCue", ...)` call anywhere in the tree before this rung)
immediately after the `teach()` call, and the per-relation verdicts are returned in
`ground_predicate`'s own output dict as `role_checks` for transparency.

## 3. A real bug found and fixed en route: `ground_predicate`'s own serialization

Building the P4-i "safe, real, zero-friction" demonstration exposed a pre-existing
defect in `ground_predicate`'s own code (`domains/reflective_faculty.py`, line
~1776, untouched by any prior rung): it serialized a minted relation via
`_json.dumps(rel)` with Python's DEFAULT separators (`", "`, with a space), while
`seeds/relation_vocabulary.json`'s own vocabulary rows are compact
(`","`, no space) for at least some cues. This made `role_recognize_exact`'s
byte-identity check fail on `ground_predicate`'s OWN, real, only live minting
path — the exact opposite of the P4-i prediction. Invisible before this rung
because every other real consumer of `RelationCue.relation`
(`_load_relation_cues`, `_relation_cue_index`, `_shared_shape`) re-parses via
`json.loads` and never compares the raw string. **Fixed**: `ground_predicate` now
calls `_json.dumps(rel, separators=(",", ":"))`, matching the vocabulary's
compact convention exactly. No test in the tree pinned the old spaced format
(grep-verified — zero pre-existing tests reference `ground_predicate` at all), so
this is a pure fix, not a behaviour change any existing consumer depended on.

## 4. A second real bug found and fixed en route: inconsistent seed formatting

Chasing the same failure surfaced a SECOND, independent defect: `seeds/
relation_vocabulary.json` itself is internally inconsistent — 27 of its 52
`RelationCue.relation` strings use spaced JSON (`json.dumps` default), 25 use
compact JSON, apparently from being hand-authored/edited at different times by
different tooling. This is invisible to every existing consumer (all re-parse),
but it directly breaks a raw-string-identity guard like `role_recognize_exact`'s
Level-A check for roughly half the vocabulary (e.g. `attention_watch`'s stored
string used spaces; `build_from_prior`'s did not). **Fixed**: every
`RelationCue.relation` string in `seeds/relation_vocabulary.json` was
re-serialized to the SAME compact form (`separators=(",", ":")`), 27 of 52 rows
changed, diff scoped to exactly those lines (verified — no other field, ordering,
or structure touched). Safe by construction: every real consumer parses via
`json.loads` before comparing (grep-verified across `tests/*.py`/`domains/*.py`),
never the raw string, so re-serializing to an equivalent JSON value changes
nothing any existing test or code path observes.

flag-everything-else) held exactly as registered — including that a token the

than silently install it.
