## What the negative analyzer fields mean

Do **not** interpret `all_registered_site_counter_equations_conserve` as a substrate regression. The capture often has no per-rule counter row for observed UIDs; the analyzer fills absent metrics with zero. The aggregate snapshot does record Term variants (for example `term_eval:Attr`) and effect attempts, but cannot be compared directly to a selected UID's trace. Native source also filters ambiguous rule identities before per-rule attribution. In addition, trace events and these cost counters instrument different sites and do not necessarily count the same operation boundary. `pattern_edge = binding_leaves × match_edge_count` assumes every binding leaf visits every match edge, which has not been established. These values are diagnostic mismatches, not conserved accounting equations. A follow-up must preregister equations from source-verified counter semantics, include unattributed work, and distinguish trace-operation counts from attempted-cost counts.

The static-key mismatches are informative coverage gaps. Repeated rows include `pattern_edge` / `edge:is_a` for rules whose declared `rule_access_sets()` omit that key. Source inspection shows `pattern_edge` is emitted for each successful explicit `rule.match_edges` binding, and `derive_access()` is intended to place those edge types in `read_set`. So the observed mismatch is **not yet explained** as an implicit membership read: it points to a discrepancy among trace attribution or symbol resolution and the live rule record. This is a sharper instrumentation/data-integrity issue than the initial hypothesis. It does not by itself show incorrect rule results. A follow-up should capture each rule's exact match-edge triples and raw symbol IDs alongside access sets, then test `derive_access()` freshness and trace attribution before deciding whether to repair derivation or trace mapping.
