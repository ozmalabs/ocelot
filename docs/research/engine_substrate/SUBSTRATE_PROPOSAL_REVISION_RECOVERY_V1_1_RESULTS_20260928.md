# Staged proposal-revision recovery v1.1 results

The corrected, source-locked v1.1 panel passes all gates across three workers, N=2/8/32/64, and cuts after zero, one, two, or all three materialization stages. Each field carries a revision stamp; before the new commit, `resolved_revision` remains at 0 for every cut, so stale/partial values do not advertise themselves as current. The recovery driver reads the stamps and runs exactly the missing max/count/decision stages, then commits revision 1 only after all stamps match. The final state matches the independent score oracle for every cell. Integer counters replicate; there is one active revision node.

The cut behavior is explicit: cut 0 resumes max/count/decision/commit; cut 1 resumes count/decision/commit; cut 2 resumes decision/commit; cut 3 resumes commit only. This demonstrates recovery between completed closure calls in one live graph and a fail-closed commit marker. It does not demonstrate process-death recovery, durable graph serialization, atomicity within one closure/effect list, concurrent writes, or consumer-side enforcement that ignores uncommitted attributes. The empty-string no-selection sentinel is specific to this authored protocol.

The initial v1 raw capture is retained as exploratory because its analyzer failed while comparing worker mappings; no v1 analysis was accepted. v1.1 uses new runner/analyzer/protocol paths and an independent lock. Only v1.1 is confirmatory.
