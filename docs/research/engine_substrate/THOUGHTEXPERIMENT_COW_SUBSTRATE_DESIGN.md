# Thoughtexperiment CoW substrate design

**Status:** partial implementation with measurement. The process-CoW and eager native-copy routes remain controls; `TypedGraph` now offers eager, shared-record-slab, and shared-graph-page paths.

## Purpose

Copy-on-write is an inherently useful substrate capability, not a speed optimization scoped to thoughtexperiments. It provides isolated mutable branches over a shared immutable revision, supports parallel consumers without multiplying the full base state, and establishes a storage-independent lifecycle for speculative work. Isolation, design purity, and future compatibility are first-class benefits even where a workload does not become faster. Keeping storage policy behind the branch interface lets consumers evolve independently of graph layout and permits future backends without changing consumer semantics. Potential consumers include search and planning, simulations, speculative execution, sandboxed tasks, and shared-prefix serving interfaces such as a vLLM-style KV-block adapter. These are workload opportunities, not claims of existing integration. A serving adapter needs separate evidence for block ownership, prefix reuse, mutation isolation, cancellation, and reclamation.

Thoughtexperiment is the first measured consumer, not the definition of the facility. A vLLM-style interface is a concrete compatibility target for shared immutable prefixes and isolated continuation state, alongside solver branches, planning, tool/effect sandboxes, and checkpointed simulations. The analogy is at the interface and ownership level: graph pages and derived indexes do not implement model KV-cache blocks, and no vLLM integration or serving benefit has been measured. The design should allow such consumers without baking any one serving interface into the storage layer.

The API should preserve this capability independently of which storage backend implements it. Linux process-CoW is already measured and useful as a control, but it is platform- and process-lifecycle-dependent. A Rust-native branch API should work in threaded, embedded, and non-Linux callers and make branch ownership explicit.

## Evidence and current limits

The source-locked declaration census covers **25 `TypedGraph` fields and 50 `Substrate` fields**. It is a field-policy checklist, not proof of semantic isolation. A six-candidate native batch passes exact nested residual and primary-isolation gates through 50,771 nodes. Linux fork/scope is 1.91× faster than native copy/scope for branch setup alone at 50,771 nodes, but a full process-CoW batch is slower than the native batch at all measured sizes. The branch-setup gain therefore motivates a native implementation without establishing an end-to-end speedup.

The existing `GraphMutationLog` is for sparse readout. It does not provide sufficient information to roll a branch back: edge before-images store prior existence, not prior attributes; node records do not capture allocator/free-list state or all adjacency/index structures. Reusing this journal for candidate reset would risk observable ID/order differences and stale indexes.

The native representation audit confirms why a wrapper-only change is insufficient. `TypedGraph` stores node and edge slabs plus per-node out/in adjacency lists in `CowPagedVec`. Its eager path deep-copies all four page vectors; the shared-record path shares node/edge pages and copies adjacency; the shared-graph-page path shares all four and now uses a 64-shard persistent map for typed out/in adjacency buckets; remaining graph hash indexes and wider Substrate state still copy eagerly. The source-locked phase profile shows each candidate prediction spends 58–64 ms in three bounded looks; each nested look pays 12–14 ms for branch snapshot and rule setup, while collapse, readout, and trace are much smaller. A source-locked index profile found typed out/in bucket maps account for most eager graph-index clone time at 10k–50k nodes; these two maps now use shard-level CoW. Remaining hash maps and stable append-only interner/term state are still open. Merely putting `Arc` around `TypedGraph` followed by `Arc::make_mut` still clones unshared stores at first write.

### Isolated persistent-vector prototype

An experimental public `CowPagedVec<T>` now implements a fixed-depth persistent radix tree with 64-slot leaves. Fork clones a shared root; mutation clones the radix path and target leaf. Its source-locked probe covers 771/1,771/10,771/50,771 `u64` slots, fanouts 1/2/4/8/32, and 25 measured repeats per cell. All 20 cells preserve exact values, primary isolation, divergent sibling writes, and sharing of untouched leaves. At 50,771 slots and fanout 32, batch fork-plus-one-slot-write is 35.22 μs versus 8.14 ms for `Vec<u64>` clone-plus-write (about 231×); at 771 slots/fanout 32 it is 10.36 μs versus 3.71 μs (about 0.36×). Cow reads cost 5.2–18.4 ns/op in these cells versus 0.5–1.7 ns/op for direct vector indexing, and changed-branch drops also cost more. This demonstrates the expected sparse-branch tradeoff on a primitive, not a graph-level speedup.

The primitive is integrated into `TypedGraph` node and edge slabs; base conversion is excluded from the primitive probe, whose payloads are fixed-size integers and whose measurements omit adjacency/index work and memory accounting. The [source-locked capture](../../../evaluation/reports/cow_paged_vec_probe_v1.json) is one-host microbenchmark evidence with visible timing noise. It supports continuing the experiment for large sparse fanout, while ruling out claims that the primitive is generally faster as a replacement.

### Partial graph integration: slab-only sharing

`TypedGraph` now has explicit `clone_eager()` and `clone_sharing_slabs()` paths. The established `fork_full_copy_experiment` remains an eager node/edge slab and index copy; a second native/Python branch API shares only node and edge pages while eagerly copying adjacency and query indexes plus other `Substrate` state. `imagine()` exposes this as `native_shared_slab_scoped`, with `native_full_copy_scoped` as the matched control. The randomized six-candidate runner requires exact candidate output/residual parity across the two backends and unchanged primary graph/rules.

At 0/1k/10k unrelated nodes, five measured repeats plus two warmups pass both gates. Paired shared/eager batch time ratios are 0.99, 1.19, and 0.94 respectively; the corresponding medians and paired ratios vary widely by block. Candidate snapshot/setup medians improve from 14.98 to 12.21 ms at +1k and 19.65 to 13.86 ms at +10k, but total batch time has no stable advantage in these five-block samples. This is useful evidence that sharing slabs can lower one component while cloned indexes and prediction still dominate total cost. It does not justify an end-to-end speed claim. See the [source-locked comparison](../../../evaluation/reports/thoughtexperiment_cow_shared_slab_comparison_v1.json.gz).

Both arms pass checks for graph counts, type-index query parity, changed-value parity, and unchanged primary state. At 10,771 nodes, clone-plus-write is 1.68 ms versus 1.20 ms. The gap between clone and clone-plus-write shows the expected first-write page-copy cost, though timing variation is visible. Since query indexes are eagerly copied in both arms, this estimates the remaining index cost plus slab savings on one sparse topology; it does not measure full `Substrate` fork cost, memory, or other graph shapes. At 50,771 nodes, eager/shared clone medians are 7.95/2.41 ms (path), 6.45/1.47 ms (star), and 10.65/2.42 ms (grid). With one write they are 8.27/2.46, 7.14/1.65, and 9.41/2.45 ms; with 1% writes they are 8.73/3.31, 7.65/2.27, and 10.38/3.42 ms. ### Sharing adjacency pages

The next graph-level experiment preserves `clone_sharing_slabs()` as the records-only route and adds `clone_sharing_graph_pages()` for shared node/edge records and top-level out/in adjacency pages. Typed out/in bucket maps now use shard-level CoW; other hash query maps remain eager copies. A source-locked release probe compares eager, shared-record, and shared-graph-page branches across the same 12 synthetic cells. All 12 topology/size cells pass exact edge count/query parity; distinct sibling edge insertions remain isolated, and primary state remains unchanged. At 50,771 nodes, clone-only shared-page medians are 0.89–1.58 ms, compared with 7.14–9.62 ms for records-only and 12.80–18.85 ms eager. Clone plus one edge insertion takes 0.87–1.57 ms shared-page, versus 6.84–8.38 ms records-only. With 1% spaced edge insertions, shared-page is 1.63–2.66 ms versus 8.10–9.68 ms records-only. This large step is consistent with avoiding copies of two per-node `SmallVec` arrays while retaining copied hash maps. It is a `TypedGraph` result, not yet a full `Substrate` end-to-end result. See the [graph-page capture](../../../evaluation/reports/typed_graph_cow_graph_pages_probe_v1.json) and [runner](../../../evaluation/substrate_capability/typed_graph_cow_graph_pages_probe_v1.py).

A matching allocator probe shows why the adjacency result is material. At 50,771 nodes, clone-only graph-page branches retain 3.26–4.70 MiB, records-only branches 6.68–7.87 MiB, and eager branches 9.07–11.06 MiB. One edge insertion raises graph-page retention to 3.47–5.10 MiB; 1% spaced inserts raise it to 4.77–6.12 MiB. All 12 cells pass return-to-baseline-after-drop and sibling-isolation gates. These are logical heap payload bytes; the hash maps are still copied, and RSS/PSS and full Substrate state are not measured. See the [graph-page allocation capture](../../../evaluation/reports/typed_graph_cow_graph_pages_memory_probe_v1.json) and [runner](../../../evaluation/substrate_capability/typed_graph_cow_graph_pages_memory_probe_v1.py).

The first fixed-revision six-candidate Substrate comparison includes the graph-page route and passes exact nested residual/outcome parity across eager, records-only, and graph-page backends at baseline/+1k/+10k (three measured repeats plus one warmup). Graph-page batch medians are 879/1,258/981 ms, versus records-only 856/878/940 ms and eager 884/966/1,081 ms. Timing is noisy and the sample is small; graph-page sharing does not yet show a stable end-to-end advantage, although it approaches records-only at baseline/+10k and beats eager by about 9% at +10k. This is the expected warning against extrapolating clone-only wins through rules, prediction, and other copied state. The [compressed capture](../../../evaluation/reports/thoughtexperiment_shared_graph_pages_batch_v1.json.gz) is 4.3 MB rather than 220.6 MB uncompressed; reproduction should retain compression when archiving the runner output.

Exact candidate outputs, nested residuals, and primary isolation pass across eager, records-only, and graph-page branches. Baseline remains a tie (graph-page batch median 849 ms; paired wins 2/5 versus eager and 3/5 versus records-only). At +10k, graph-page is 866 ms versus 1,009 ms eager and 966 ms records-only; it wins all five paired blocks, with median paired speed ratios 1.27× and 1.16×. At +50k it is 912 ms versus 1,426 ms eager and 2,030 ms records-only, winning all five blocks at 1.65× and 2.15× paired median ratios. This upgrades adjacency sharing from a graph-only gain to an end-to-end gain on this synthetic thoughtexperiment family and host, while natural-task coverage and independent-host replication remain open. ### Allocation accounting

A separate release probe wraps `System` with an atomic counting allocator and measures live requested heap bytes around each single branch operation; branch destruction must return the logical live-byte count to its pre-operation baseline. It repeats the v2 topology/size/write matrix seven times and checks sibling isolation. All 12 cells pass both gates. At 50,771 nodes, an eager clone retains 8.23–10.22 MiB by topology, while a shared-slab clone retains 5.84–7.03 MiB. Thus slabs account for about 2.39–3.19 MiB saved at clone time, while several MiB of non-slab graph fields (including indexes and allocator metadata structures) remain branch-owned. One write adds 3,936 bytes to a shared branch; spaced writes to 1% of nodes add about 1.07–1.08 MiB. With those writes, shared branches retain 6.92–8.11 MiB versus 8.29–10.28 MiB eager. These are allocator-requested payload bytes, not RSS/PSS, resident pages, allocator fragmentation, or full-Substrate memory. This quantifies the next target: sharing query-index storage and other non-slab graph state. See the [allocation capture](../../../evaluation/reports/typed_graph_cow_memory_probe_v1.json) and [runner](../../../evaluation/substrate_capability/typed_graph_cow_memory_probe_v1.py).

### Shared typed-adjacency indexes: current selective CoW stage

The path/star/grid index profile identified `out_by_type` and `in_by_type` as the main remaining graph-copy cost. These maps now use a 64-shard persistent map: a fork shares its root; the first mutation copies the shard-pointer array and only the affected shard. Eager and shared-slab controls explicitly deep-copy both maps. The shared-graph-page route shares them, while `by_type`, edge attributes, high-degree target lookup maps, edge-type maps, attribute bitmaps, and the wider `Substrate` still use their prior copy policies.

The source-locked index profile uses 25 repeats at 771/10,771/50,771 nodes on path and star graphs, with a 128-value declared attribute index and four edge types. At 50,771 path nodes, eager map materialization takes 2.92 ms for `out_by_type` and 2.32 ms for `in_by_type`; a shared root fork takes 0.05/0.04 μs. Its 100k-query 50/50 hit/miss stream measures 5.2/4.4 ns per lookup, against 3.4/3.7 ns for a flat `FxHashMap`. Star lookups are 2.0/3.0 ns against 2.0/1.9 ns. This leaves a small and topology-dependent read cost; the first hash-based shard selector was 5–8× slower and was replaced by direct NodeID/edge-type shard selection before these final measurements.

The refreshed graph-page fork/write probe passes all 12 topology/size cells. At 50,771 nodes, clone medians are 39/83/53 μs for path/star/grid with graph-page sharing, versus 14.17/11.21/15.78 ms eager. One-edge writes take 53/70/94 μs; writes to 1% of edges take 1.42/0.71/1.83 ms. The allocator probe reports clone-only branch retention of 0.39/0.95/0.58 MiB versus 10.08/9.08/11.07 MiB eager, and 1%-write retention of 3.72/2.74/4.10 MiB. All branches return to the measured live-allocation baseline after drop. The refreshed 81-row mutation gate also passes eager parity, derived-query checks, nested/sibling isolation, and delete/reuse behavior across three sizes, three topologies, and three operation orders. The [index profile](../../../evaluation/reports/typed_graph_cow_index_clone_profile_v1.json), [fork/write capture](../../../evaluation/reports/typed_graph_cow_graph_pages_probe_v1.json), [allocation capture](../../../evaluation/reports/typed_graph_cow_graph_pages_memory_probe_v1.json), and [mutation capture](../../../evaluation/reports/typed_graph_cow_mutation_semantics_v3.json) retain raw rows and source locks.

The live six-candidate Thoughtexperiment batch now exercises this representation. At baseline and +1k, paired timing is noisy and does not favor shared pages; at +10k it wins all five blocks with a 1.16× median ratio. A separate +50k run wins all five blocks at 1.81× (1.10 s eager versus 0.63 s shared pages). One of six candidates is useful in every backend, so measured useful-candidate count is unchanged. Reusable snapshot capture/fork composes with the same residual contract but shows no consistent additional speed over direct shared-page branches. ## Proposed contract

Treat a snapshot as an immutable, versioned semantic base. A branch holds a reference to that base plus local writes, deletions, allocator state, and derived-index changes. Reads resolve branch-local change first, then the base. A branch result is tagged with the base revision and includes its residual, outcome, and provenance. Dropping a branch releases its private state. Adoption is a separate operation that checks the base revision and explicit policy; branch state is never merged implicitly.

Illustrative consumer-neutral interface (names are provisional):

```rust
let base = substrate.snapshot()?;
let mut branch = base.fork();
branch.apply(candidate)?;
let result = branch.run(probe)?;
let receipt = result.into_receipt(base.revision());
// Optional and separately gated:
substrate.apply_delta(receipt, expected_revision, adoption_policy)?;
```

The public interface should not expose storage layout. The Rust and Python application APIs now follow this boundary: `Substrate.snapshot()` selects the default implementation internally, `SubstrateSnapshot` exposes identity/revision/fork, and backend selection is confined to private measurement hooks. Controlled benchmark runners use those hooks to compare implementations. The contract should support several branches from one base, branches from a branch when explicitly requested, cancellation/drop, deterministic results, bounded resource budgets, and exportable receipts. A future backend can switch from page CoW to persistent maps without changing application callers.

CoW is a first-class capability even when a caller values isolation, lifecycle control, or backend portability more than speed. Therefore the contract is validated separately from any one workload's performance. The initial consumer is the thoughtexperiment harness; subsequent compatibility gates should exercise at least one solver/planner consumer and one read-only shared-base consumer. A vLLM-style shared-prefix interface is a useful future compatibility target, but it requires a separate adapter and workload evidence: this graph snapshot API does not represent model KV-cache blocks, and compatibility must not be inferred from naming or shared-state semantics alone. The storage layer must remain independent of that adapter.

The current `fork_*_experiment` methods are prototype/evaluation entry points, not the final public contract. Promote the stable snapshot/branch lifecycle to consumer-neutral names only after full semantic isolation, cancellation, deterministic receipt, revision-conflict, and resource-budget behavior are specified. Keep eager copy as the semantic oracle and retain backend-selectable measurement so storage can change without consumer changes.

## State and storage policy

Use the current [source-locked state inventory](../../../evaluation/reports/thoughtexperiment_state_inventory_v1.json) as the exhaustive field list and refresh it whenever either Rust struct changes.

| State | Branch policy |
|---|---|
| `TypedGraph` node/edge records and edge attributes | Immutable shared base plus sparse changed-record overlay and deletion tombstones; preserve stable IDs. |
| Graph adjacency and query indexes | Persistent or page-shared base indexes plus branch-local bucket deltas. Do not rebuild or scan the full index on each read. |
| Node/edge allocators and freelists | Branch-local state with deterministic allocation order; merging must detect collisions/revision drift. |
| Interner and `TermArena` | Stable shared ID namespace with branch-local append segments. A branch must never allocate an ID that aliases a different base/peer value. |
| Rules, concepts, checker | Share immutable revisions; candidate edits use branch-local replacements/appends and preserve stable rule slots/UIDs. |
| Rule dependencies, dirty bits, cursors, evaluation/shape caches | Branch-local or revision-keyed derived state; invalidate/rebuild only affected entries. Never share mutable cache contents across diverging branches. |
| Epochs, graph revisions, references to semantic roots | Branch-local revisions rooted at the base revision; receipts identify both. |
| Counters, traces, telemetry, diagnostics | Branch-local and optional. They cannot affect semantic outcomes. |
| Pending effect queues and framebuffer handles | Empty/refused at snapshot, or represented by explicit sandboxed capabilities. No external effect may escape a branch. |

The graph representation should use independently shareable storage units (for example, immutable arena pages) rather than `Arc<TypedGraph>` followed by `Arc::make_mut` on the whole object. Whole-object `Arc::make_mut` merely postpones the full clone until first write; it does not provide sparse CoW for branches that mutate. Branch overlays must cover both content and the indexes the runtime uses to find it. The consumer-facing snapshot/fork/receipt contract is the compatibility boundary: consumers should not depend on whether a backend uses page CoW, process CoW, or persistent maps.

## Implementation sequence and gates

1. **Freeze the contract and state map.** Reconcile the live 25/50 field census, name each field's policy, and document effect eligibility. Gate: every field is classified; unsupported/external fields fail closed.
2. **Prototype storage primitives in isolation.** Add a small paged arena with shared immutable base pages, branch-local changed pages, and tombstones. Gate: exact insert/update/delete/read parity, stable IDs, branch-of-branch behavior, sibling isolation, and bounded page copying under sparse writes.
3. **Integrate graph reads and writes.** Route `TypedGraph` lookups, iterators, persistence, matching, and effects through the overlay. Keep base indexes shared and update only local buckets. Gate: all supported graph APIs match eager-copy results after each mutation sequence, including edge attributes, node deletion cascades, high-degree indexes, edge scope, and attribute indexes.
4. **Integrate the complete substrate snapshot.** Apply the policies above to the 50 `Substrate` fields. Gate: exact rule execution, nested forward-look residuals, candidate order, rule IDs/UIDs, and complete semantic graph/rule exports match eager-copy controls; primary and sibling branches remain unchanged.
5. **Measure workloads and fanout.** Compare eager native copy, process-CoW, and Rust CoW on the same seeded fixtures. Cross graph sizes 771, 1,771, 10,771, 50,771 and larger; branch fanout 1/2/4/8/32; read-heavy, sparse-write, dense-write, delete-heavy, and nested-look workloads. Report branch creation, first-write, reads, closure, residual, drop, adoption, CPU, peak RSS/PSS/private dirty, bytes copied, page/overlay allocations, and useful outcomes per fixed time/memory budget. Gate: exact parity; no primary/sibling mutation; sparse-write allocation proportional to touched pages/records rather than base graph size; no material regression in read-heavy latency; measured end-to-end wins on the workloads that benefit.
6. **Exercise future consumers.** Reuse one immutable snapshot through at least two independent interfaces (for example, solver alternatives and thoughtexperiment candidates), plus one read-only shared-base consumer. Gate: one branch family cannot affect another, branch lifecycle/reclamation is bounded, revision conflicts are explicit, deterministic receipts identify the base, and backend choice is invisible to the consumer contract. Treat vLLM-style shared-prefix serving as a later adapter gate with its own representative workload; do not count the analogy as integration evidence.

### Shared-prefix consumer compatibility gate

The next compatibility probe should model the ownership shape of shared-prefix serving without importing a serving engine or presenting graph pages as KV blocks. Define a small consumer-neutral `PrefixStore` contract over an immutable base handle: publish a completed prefix, fork a request continuation, read shared prefix state, write request-local continuation state, cancel a request, and release its references. The fake payload can be deterministic fixed-size blocks; the substrate snapshot is only the lifecycle/isolation backend. Keep block identity and prefix lookup in the adapter so a later implementation could map the same contract to an actual KV allocator.

The minimum semantic matrix is: two requests share one prefix; each appends divergent continuation blocks; one request is cancelled while the other continues; a third request forks after the cancellation; all reads remain correct; no request-local write is visible to siblings or the published prefix; and dropping the final handle releases branch-owned allocations. Also exercise stale base/revision rejection and repeated create/cancel/drop cycles. Compare every visible result against an eager-copy reference. Run both the default snapshot API and an eager control through a private test hook, with the consumer itself unaware of backend choice.

Record fork/publish/read/write/cancel/drop latency, live and peak retained bytes, shared versus branch-owned block counts, and reclamation after each lifecycle event. The pass criteria are exact oracle parity, prefix and sibling isolation, deterministic ownership receipts, no leaked references after cancellation/drop, and bounded memory as repeated request cycles complete. Performance is reported descriptively; this gate does not require a speedup. Passing it establishes that the snapshot lifecycle can support a shared-prefix-shaped interface. It does not establish compatibility with vLLM, model KV-block layout, scheduler behavior, continuous batching, token throughput, or serving memory efficiency. Those claims require a later adapter against a representative model/runtime and workload.

The sequential synthetic adapter probe completes 30 fresh workers (three background sizes × two backends × five repeats). #### Connected topology and write-density sweep

The follow-up crosses path/star/grid topologies, 10k/50k nodes, 1%/10% edited nodes, fanout 4/16, and shared/eager branches in 144 waves. Each touched node gets a 128-byte payload update and a branch-local edge to the branch's unique new node. Exact write validation, branch-ID parity, cancellation/survivor isolation, and zero mutation-adjusted post-drop bytes pass all cells. Shared snapshots use 1.73×–3.12× less all-live allocator payload and win median full-wave time in 24/24 cells. However, at 50k/fanout16/10% writes, CoW's mutation increment is 85.9–110.8 MiB against 6.9–19.3 MiB eager, although total live bytes remain lower for CoW. This identifies first-write amplification as a real density-dependent cost; it cannot be hidden by fork-only savings. Topology changes both totals and write costs. Evidence is three repeats, one host, one deterministic evenly spaced target layout. The next placement/degree gate is reported below. See [results](COW_CONCURRENT_MUTATION_SCALE_V1_RESULTS_20261001.md), [preregistration](COW_CONCURRENT_MUTATION_SCALE_V1_PREREG_20261001.md), [raw capture](../../../evaluation/reports/cow_concurrent_mutation_scale_v1.json), and [analysis](../../../evaluation/reports/cow_concurrent_mutation_scale_v1_analysis.json).

The subsequent degree/placement panel adds a regular-four profile and selects targets by clustered IDs, evenly spread IDs, low out-degree, or high out-degree. All 384 rows pass exact semantic, sibling, revision, and allocator-reclamation controls; shared snapshots reduce total allocator payload in 64/64 cells. On the regular-four topology, where all nodes have out-degree four, clustered 10% writes use 62.0 MiB mutation-plus-fork live allocation versus 128.7 MiB for spread writes. This isolates page placement from degree. On a 50k star, 10% spread writes including the hub cost 101.2 MiB versus 34.5 MiB for a central contiguous cluster of leaves; the high-degree-selected set, laid out contiguously by ID, costs 38.5 MiB. Grid low-degree targets also cost more than high-degree targets (73.5 versus 53.4 MiB), despite the low-degree set's smaller out-degree sum. Thus the target-degree multiset alone is not enough: placement and how writes intersect shared pages/indexes jointly determine first-write cost. The study is one host with three repeats and fixed payload size. Next randomize degree distributions and target-set topology, then replay task-generated receipts. See [results](COW_CONCURRENT_DEGREE_PLACEMENT_V1_RESULTS_20261001.md), [preregistration](COW_CONCURRENT_DEGREE_PLACEMENT_V1_PREREG_20261001.md), [raw capture](../../../evaluation/reports/cow_concurrent_degree_placement_v1.json), and [analysis](../../../evaluation/reports/cow_concurrent_degree_placement_v1_analysis.json).

The current 10× marginal candidate-cost goal remains a separate stretch performance gate. CoW capability work can succeed on isolation, compatibility, and memory-amplification evidence even when a particular inference path is dominated by rule execution or result transfer; performance claims must still be stated per workload.

### Reusable snapshot interface: first lifecycle measurement

The initial lifecycle probe used backend-selecting `Substrate.snapshot(backend)` for controlled comparisons. The application-facing Rust and Python APIs have since moved to `Substrate.snapshot()` and hide backend identity; controlled measurements use a private backend-selection hook. A snapshot carries an opaque identity and the source graph/rule revision; callers can create multiple independent mutable consumers and a later read-only consumer from the same base. The release-build [lifecycle probe](../../../evaluation/substrate_capability/thoughtexperiment_snapshot_fork_contract_v1.py) checks those semantics for eager copy, shared slabs, and shared graph pages, and records capture/fork timings separately. At 10,000 path nodes with five repeats, all 12 backend × fanout cells (fanouts 1/4/16/32) pass branch, primary, and read-only isolation. Median shared-graph-page fork is about 0.25–0.27 ms through fanout 16; the fanout-32 median is 0.74 ms and visibly noisier. Eager-copy fork medians are about 2.0–4.1 ms, while shared-slab medians are about 1.2–1.4 ms. These are API lifecycle timings, not candidate-evaluation speedups: other `Substrate` fields and most graph hash indexes are still eagerly copied, and that first probe omitted inference, residual readout, memory accounting, cancellation/drop bounds, concurrent consumers, adoption, and revision-conflict policy. The [capture](../../../evaluation/reports/thoughtexperiment_snapshot_fork_contract_v1.json) establishes the first reusable consumer contract, not the full thoughtexperiment harness or any serving adapter.

### Concurrent branch execution

`ExperimentSnapshot` satisfies `Send + Sync` and can be shared among Rust threads. A source-captured probe performs simultaneous branch forks and one branch-local node insertion, with primary, sibling, and later-fork isolation checks. On 771-node bases, concurrency loses at every tested fanout. At 10,771 nodes it loses at fanout 1, then wins 5/5 paired blocks at fanouts 4 and 16 (median 2.77× at fanout 16). At 50,771 nodes it wins 5/5 at fanouts 4 and 16; fanout 16 is 4.28× versus serial. This validates concurrent immutable snapshot use and a crossover for the measured setup mutation, not parallel rule inference, writes to one shared live substrate, or end-to-end search throughput. See the [results](COW_SNAPSHOT_CONCURRENT_FORK_V1_RESULTS_20261001.md), [capture](../../../evaluation/reports/cow_snapshot_concurrent_fork_v1.json), and [Rust probe](../../../evaluation/substrate_capability/fixtures/cow_snapshot_threads/src/main.rs).

The first harness integration adds `native_reusable_snapshot` to fixed-revision six-candidate batches. One base snapshot is captured after the baseline prediction, checked against the batch revision, then forked for each candidate; focus scope, rule patch, prediction, and sparse residual readout stay on the branch. In two measured blocks plus one warmup at 0 and 1,000 unrelated nodes, this mode exactly matches `native_shared_graph_pages_scoped` on all six candidate outcomes, nested residuals, and primary-state checks. It shows no speed gain: batch medians are 686.7 vs 639.3 ms at baseline and 608.2 vs 587.5 ms at +1k (reusable/direct shared pages). The reusable capture itself costs about 0.3–0.4 ms, while per-candidate setup remains dominant. Only the designated candidate converges in either mode, so useful outcomes are equal. The capture is one synthetic task family, one host, and two measured repeats; treat the small latency difference as directional only. The result points to the remaining whole-Substrate and index copies as the next performance surface, while the reusable snapshot is already valuable as an isolation/compatibility boundary. See the compressed [matched batch capture](../../../evaluation/reports/thoughtexperiment_reusable_snapshot_batch_v1.json.gz) and the [runner](../../../evaluation/substrate_capability/thoughtexperiment_fixed_revision_six_candidate_batch_v1.py).

CoW is a general substrate capability, not a Thoughtexperiment optimization. Immutable bases and isolated branches provide safe concurrent or speculative work, a stable lifecycle contract across storage backends, and a clean boundary for future consumers. Those benefits stand even when a workload shows no speedup; performance is one measured property, alongside isolation, lifecycle correctness, composability, and backend compatibility. Keeping the consumer contract independent of graph-page representation is also a design-purity constraint: clients should request snapshots, forks, cancellation, and residual/commit behavior without depending on how storage shares memory. The same contract can support future interfaces such as vLLM-style shared-prefix or KV-block serving, but graph snapshots do not represent model KV blocks. A serving adapter remains a separate compatibility target, requiring its own measurements of prefix ownership/reuse, concurrent readers and writers, cancellation, scheduler integration, and bounded reclamation.

### Parallel native rule closure: larger mutable branches

The [parallel closure probe](COW_SNAPSHOT_PARALLEL_RULE_CLOSURE_V1_RESULTS_20261001.md) extends the concurrent-fork result to 45 fresh-process runs of native rule execution. Every semantic and isolation gate passes. Independent branch concurrency reduces median wall time at fanouts 4/16 for both CoW and eager branches; fanout 1 often loses to thread overhead. CoW medians are modestly faster than eager across this synthetic ring workload, but live PSS is mixed and is higher for CoW at 50,771 nodes for all tested fanouts. Dense branch-local edge creation can consume the sharing benefit. This adds concurrent rule execution as a consumer result while identifying write density and touched-index locality as controls for the next scale study. The tested AddEdge rule is not `batch_safe` under the engine's read/write analysis, so this is branch-level concurrency, not within-rule batching.

The result strengthens the general-purpose case for CoW as isolation and lifecycle infrastructure. A vLLM-style serving interface remains a future compatibility target: graph snapshots are not KV blocks, and no serving adapter, request batch scheduler, cancellation, or reclamation contract is implemented. Those should be independently designed consumers of the abstract snapshot lifecycle rather than special cases in graph storage.
