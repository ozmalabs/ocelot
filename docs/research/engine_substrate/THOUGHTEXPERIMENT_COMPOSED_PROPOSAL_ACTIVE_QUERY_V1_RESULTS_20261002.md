# Thoughtexperiment composed proposal active query v1 — results

**Gate result: pass for integrating prompted composition with bounded active querying on the control-kind fixture.** Four workers each used the normal `ground_concern` general-structural route to select `classify_kind_family` and `flip_comparison`. Every graph proposal matched an independently enumerated host candidate by digest. Before any labels were attached, each worker froze query selections from pools of 100 names at 0%, 50%, 90%, and 99% neutral rates. Across all 16 pools, the query selector found a one-bit disagreement between the faulted target and composed proposal. The post-freeze task oracle retained only the composed proposal in every case. All source/native hashes were stable.

Each composed proposal passed both established held-out names in a fresh branch with a valid receipt and preserved primary state; all four fault baselines failed. Random single-probe discrimination was 4/4 at 0% neutral, 3/4 at 50%, and 0/4 at 90% and 99%. Mean query-stage wall time rose from 10.62 ms at 0% neutral to 208.66 ms at 99%. The query stage includes native rule execution for each hypothesis/input pair; the rising cost reflects this authored workload's many nonmatching cases and does not isolate the entropy selector or establish a general complexity rate.

This connects two previously separate measured components: prompted structural composition and finite active query selection, with the candidate rules' predictions obtained from isolated native graph branches. Python still defines the fault, cue, input pool, family labels/oracle, proposal materialization, and scoring. It is one authored target and a constructed name distribution, so it does not demonstrate autonomous diagnosis, broad transfer, or self-improvement. Next transfer the same staged protocol to a newly authored rule family and capture full composition, query, closure, and held-out costs; recurrence remains a likely test of whether a domain-specific operator is required.
