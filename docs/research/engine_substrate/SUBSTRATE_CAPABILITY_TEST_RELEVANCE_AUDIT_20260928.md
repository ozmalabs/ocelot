# Capability inventory linked-test relevance audit

## Method

The audit reads the generated capability map and parses linked Python test references with Python AST. It compares call names against source-linked callable leaves, records the enclosing function, counts syntactic `assert` statements in that function, and follows same-file local helper calls from `test_*` functions. It also inventories `#[cfg(test)]` blocks and `#[test]` function names in each linked Rust source file, and notes whether a linked callable identifier appears in the source after the test-module marker. The current refreshed inventory contains 65 linked Python test references across 26 capability rows (61 unique test files), all parseable. Both language checks are lexical structural leads: they do not determine whether a branch executes, whether assertions concern the matched call, whether an independent oracle is used, whether the production implementation is reached, or whether evidence remains fresh. Rust identifier occurrence anywhere in a test-module tail is especially weak evidence of relevance.

## Findings

The current Python AST crosswalk finds 17/26 rows with candidate callable-name calls, 15 with at least one match in an assert-bearing test function, two with candidate matches only outside test functions, five generic-name-only rows, and four with no linked Python test call matching a source-linked callable name. Generic leaves now explicitly include `tick`, `process_audio`, and `run_pipeline`, because test calls with those names can reach different APIs than the mapped Rust symbols. The crosswalk finds 186 lexical call sites reachable from test functions, including 173 in assert-bearing test functions; these counts are syntactic and may include repeated matches across rows. Rust source-local test inventory finds 77 row-to-source links to files with `#[cfg(test)]` blocks and linked-symbol name occurrence in at least one Rust test tail for 16/26 rows. In the seven newly mapped families, the Python crosswalk has a specific candidate match only for codec/transcoding. Feedback control (`tick`), auditory (`process_audio`), and neural/pipeline (`run_pipeline`) are weak generic-name-only matches; cognitive runtime, motor synthesis, and admissibility have no callable-name match. Rust test-tail symbol mentions occur for cognitive runtime, feedback control, auditory (APC only), codec/transcoding, and graph neural execution; they do not occur for motor synthesis or admissibility. Local tests exist in some modules even when no mapped callable name appears, so neither a no-match nor a name mention decides actual test relevance.

The unmatched planning/action row remains a gap signal: linked Python files validate proposal/runtime-closure protocol artifacts and do not call source-linked bounded planner functions. Source review located five relevant inline Rust unit tests in `p2_bounded.rs` and `p2_native.rs`; those were run under exact-name filters in the separate [v1.4 capture](SUBSTRATE_PLANNING_NATIVE_UNIT_AUDIT_V1_4_RESULTS_20260928.md). The generic-only Terms/value evaluation and memory rows are weak evidence too. Direct and helper-reachable call counts and Rust test-tail mentions remain static leads; this analysis does not establish assertion relevance, oracle independence, test execution, production-path coverage, or freshness.
