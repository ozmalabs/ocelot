# Signed provider evidence at code-write adoption v1.1 — results

The follow-up source/native/seed-locked panel passes all seven independent analysis checks across 12 fresh full-seed workers. It repeats the four v1 adoption cases after hardening the verifier against empty probe sets and adds an explicit zero-probe control to every process.

All 48 authentication negative controls fail closed: post-signature label tampering, reuse of a signed label under another request ID, a signature from an unregistered provider, and a validly rehashed request with zero probes and empty evidence. In the last case, the legacy core adjudicator returns an internally consistent accepted receipt for the empty request; the authenticated verifier now returns `ok=false` with `request has no probes`, and authenticated teaching refuses it.

The other outcome classes reproduce v1: unsigned forged labels are refused before adoption in 3/3; honest signed square labels expose the wrong identity candidate and refuse it in 3/3; correct square candidates adopt with exact 4/4 held-outs in 3/3; trusted-key signatures over false values authenticate and still cause false adoption in 3/3. This isolates four properties: request/evidence integrity, provider-key possession, semantic residual detection, and trusted-provider correctness. Authentication handles the first two only.

The keyring is still passed explicitly by the integration caller and the HMAC key is a fixture key. The legacy receipt-only teach route remains callable. This v1.1 result closes the zero-probe verifier defect within the opt-in wrapper; it does not establish deployment-grade trust or provider correctness. Median full-seed boot was 11.82 s.
