# General-rule structural proposal transfer to control-kind v1 — results

**Gate result: pass for the bounded cued classifier probe.** Four source-locked workers captured orders before held-out scoring. Every prompted graph proposal selected `classify_kind_family`, selected `flip_comparison`, preserved the target during composition, and matched the host reference candidate by semantic digest. The empty-residual arm abstained in all four workers. Source hashes remained stable, and the score artifact binds to the frozen orders.

The proposal passes both held-out control-kind examples with a verified isolated-branch receipt and unchanged primary state in 4/4 workers. The source rule passes both examples and the faulted rule fails in 4/4. The full host reference candidate set was scored (24 worker/candidate outcomes total), with both useful and failing candidates present; all host candidate receipts and primary-preservation checks pass. Independent analysis passes all ten checks.

The new opt-in general-rule path extends graph-resident target selection beyond `writes_chosen_action` rules. It exposes non-frozen rule summaries, then uses the existing graph Term Argmax for target and applicable operator selection. Python still extracts applicability and materializes the selected rule JSON; the held-out oracle and cue are also supplied by the harness. Median measured graph-composer call was 23.74 ms and host candidate enumeration was 0.645 ms, but these are different scope timings: the former includes provenance exposure, graph selection, applicability, and materialization, while the latter is only the host generator call. No speed comparison is claimed. This is repeated measurement on one authored classifier and two held-out names, not independent task-family replication or open-ended self-improvement.

Next, route the opt-in composer through the ordinary thoughtexperiment proposal path instead of direct API invocation; separately time provenance extraction, graph decision, Python applicability, materialization, branch creation, scoring, and receipt verification. Then preregister shape-axis and recurrence as distinct non-action rule-family transfers, with fresh held-out task instances and no host-candidate fallback.
