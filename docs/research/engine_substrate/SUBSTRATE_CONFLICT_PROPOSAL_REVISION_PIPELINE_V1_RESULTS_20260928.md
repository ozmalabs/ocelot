# Explicit revision pipeline for proposal resolution v1 results

All correctness and reproducibility gates pass across three workers, N=2/8/32/64, and five graph states: initial unique maximum, addition of a higher proposal, creation of a tie, removal of the tied proposal, and lowering the higher proposal's score. Each state is reached through an explicit revision node and three ordered fixed-point closures: compute maximum, compute the count of proposals at that maximum, then write ambiguity and selected label. The captured target state matches the independent Python score oracle at every revision. The explicit event successfully wakes resolution after score mutation, which the previous one-closure probe failed to do.

At N=64, total measured Term evaluations per revision are 789, 1,602, 1,437, 3,204, and 4,005 across the five transitions. The stages keep the calculations ordered and correct, but old revision nodes remain in the graph; later closures re-evaluate historical stage bindings, so counted work grows with revision history as well as proposal count. This makes the event protocol a correctness construction, not yet a scalable lifecycle implementation. A follow-up should compare bounded event retention or compacted revision state and include event creation/deletion costs.

This result requires the caller to signal every relevant change and run all three stages in order. It does not establish automatic invalidation, recovery from interruption between stages, concurrent mutation safety, a general truth-maintenance mechanism, or an asymptotic complexity class.
