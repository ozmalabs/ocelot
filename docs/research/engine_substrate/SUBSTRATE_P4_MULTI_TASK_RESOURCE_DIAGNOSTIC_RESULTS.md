# Repeated P4 acquisition resource diagnostic results

**Run state:** locked discovery diagnostic on the already inspected contrast-string fixture; not confirmatory generalization or scaling evidence.

The runner processed all 18 fixture tasks in order, creating a fresh substrate for each and using the standard P4 request route with four revealed examples. Eleven tasks returned `accepted`; seven returned `gapped` with `enumerate_failed`. Of the accepted tasks, five matched all four revealed and three held-out rows through the IR evaluation helper. Six accepted tasks did not pass all seven rows, including all six first tasks in the replace-first/reverse-split strata. Acceptance therefore cannot be treated as a correctness result in this sample.

TermArena logical length had **zero net delta on all 18 acquisitions**. Graph node count grew by 103–119 per acquisition (1,959 total), reflecting retained route state in each newly booted substrate as measured by this harness. Current process RSS deltas from the post-boot, pre-route snapshot ranged from 0 to 12,760 KiB; the process-wide high-water mark was 155,476 KiB. That RSS is cumulative and allocator-sensitive, not a per-substrate allocation measure. Median route wall time was 141.1 ms across all tasks; accepted tasks had a 52.7 ms median, while gapped tasks had a 678.4 ms median. These descriptive medians reflect the fixed fixture order and its route outcomes, not expected task costs.

This broadens the one-task cleanup result to a real multi-task P4 route: no logical TermArena growth was observed, while graph state and RSS changed during repeated fresh-substrate acquisitions. It does not establish process-memory reclamation, isolated task costs, a representative task distribution, or complexity scaling. The seven-row helper evaluation is a harness score for accepted IRs, not a blinded generalization result.
