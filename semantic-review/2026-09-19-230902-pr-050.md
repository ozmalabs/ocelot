# Separate GCS-only IAM boundary for operation 4

DISPATCH-050 adds a repository-only IAM provisioning definition for operation 4. It separates the GCS capability from the observed KMS-capable account, scopes a custom create/get role to the exact run prefix, removes the broad and stale bucket grants, and binds the reviewed image-digest principal only to `roles/iam.serviceAccountTokenCreator` on the new account. The runner requires default approval and expected-prestate artifacts, versioned IAM preconditions, ordered injected apply, poststate verification, rollback, a receipt, and a single no-retry attempt; no cloud operation or credential creation is enabled. **Watch for:** **confirmed** the new account is still paired with the old bucket/prefix in the Cloud Run template; **confirmed** poststate validation does not preserve the existing account’s KMS role or IAM policy; **confirmed** the runtime still constructs GCS and KMS capabilities from the same token and must remain blocked until the separate KMS path is reviewed. The historical source packet remains `sha256:a8c313f6e5b775b4ba48a8e8ff4cc5e2561c560930c4e89ec2e9666fb509c447`; the current GCS capability definition is `sha256:705c5323a8bf8f300547d2051cf128825b03e0415c334dd452cd4e9db0280ee2`; and the DISPATCH-050 definition is `sha256:817ce6cff5f25487ba131a2d587fbcd489a52245e3a8173aa6320862ed49ce25`. **Verdict**: NEEDS_CHANGES

## High-level view

The IAM definition now describes a distinct `p5-r0-gcs-only` account, a custom role containing only object create/get, an exact operation-4 prefix condition, removal of `roles/storage.objectAdmin` and the stale `v3/` WIF grant, and no direct bucket access for the WIF principal. Its blocked status, default artifact paths, etag/fingerprint preconditions, receipt, rollback order, and no-retry ledger keep this repository work separate from an apply.

**Confirmed** account wiring is not end-to-end: Cloud Run selects the new identity but still configures `p5-r0-private-PROJECT_ID` and `v3`, while the reviewed grant is for `p5-evaluator-ocelot-proof-141633828616` and the exact operation-4 prefix. The added attestation subject prefix also expands to `REGION-a`, while the reviewed WIF condition is fixed to `us-east1-b`.

**Confirmed** the existing KMS authority is represented in the prestate and removal plan but not protected by poststate validation. A poststate with the old account’s KMS project role removed or its account IAM policy changed is accepted, so a faulty executor could damage the authority path while still producing a verified receipt.

**Confirmed** runtime activation remains blocked: `CapabilityFactory.build()` impersonates the configured account and constructs both a GCS client and a KMS signer. The new account is deliberately GCS-only, so this shared factory cannot be treated as an operation-4 runtime until the KMS capability is split and separately reviewed; `iam-policy.md` documents the boundary, but the deployment template does not enforce it.

<summary>Details</summary>

### GCS-only identity does not match the Cloud Run storage namespace

**Confirmed** the current definition grants `serviceAccount:p5-r0-gcs-only@ocelot-proof.iam.gserviceaccount.com` only the custom create/get role under `projects/_/buckets/p5-evaluator-ocelot-proof-141633828616/objects/p5-r0/operation-4/rs069r18r13-op4-04a98e3e/`. The deliberate Cloud Run change selects that account, but `P5R0_BUCKET` remains `p5-r0-private-PROJECT_ID` and `P5R0_PREFIX` remains `v3`. The runtime `GCSStore` therefore targets a bucket and namespace for which this account has no reviewed grant. Bind the runtime bucket and prefix to the operation-4 definition, or keep this deployment path explicitly disabled.

**Confirmed** the added `P5R0_ATTESTATION_SUBJECT_PREFIX` and `P5R0_EXPECTED_ZONE` template values use `REGION-a`, while the reviewed provider condition requires subjects under `.../zones/us-east1-b/instances/`. Resolve the template to the exact reviewed zone before any WIF binding is applied; otherwise the runtime and provider accept different attestation boundaries.

### Existing KMS authority is not preserved by poststate verification

**Confirmed** `_validate_state()` normalizes `existing_account` and `existing_account_policy`, but `validate_poststate()` constrains only the new target account, target policy, bucket grants, and custom role. It does not require the existing account to retain `roles/cloudkms.signerVerifier`, retain its no-key-material state, or retain the prestate account-policy bindings. A local mutation probe removed the existing KMS role and separately cleared the existing account policy; both altered states still passed `validate_poststate()`.

The apply is meant to remove only the old account’s bucket `roles/storage.objectAdmin` binding while leaving that account as the KMS authority. Require exact preservation of the old account’s project roles, key-material flag, and account-policy bindings, with their observed versions in the receipt, and add tamper tests for each drift.

### Shared capability construction remains an activation blocker

**Confirmed** `CapabilityFactory.build()` uses the configured capability account to mint one effective token, then calls both `_storage_client()` and `_kms_client()` and constructs `KMSEd25519Signer`. The signer reads the configured KMS public key during construction, so a GCS-only account with no KMS role cannot activate this path even when its GCS IAM is correct. This does not justify granting KMS to the GCS-only account.

Keep the IAM definition, Cloud Run activation, and operation-4 child approval blocked until a separate reviewed KMS token/client path exists. The first safe apply boundary remains fresh read-only IAM prestate, exact child approval, a reviewed injected executor, and signed-environment credential readiness, with no runtime activation claim.

### Test coverage

**Confirmed gap:** the 14 targeted tests use a fake executor and do not test a concrete IAM adapter, the Cloud Run bucket/prefix and zone bindings, preservation of the existing KMS account policy, or the shared-factory activation gate. The repository-only checks pass—targeted tests, definition validation, `py_compile`, and `git diff --check`—with no cloud apply, credential creation, GCS upload, or applied-state claim.
