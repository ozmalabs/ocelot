# Signed-credential and rollback hardening for APPROVAL-023/DISPATCH-082

This hardening adds verifier-bound credential/evidence, child-approval, packet/source, expiry, and attempt checks around the fixed IAM apply executor. It also makes the allowlisted command map immutable, validates the referenced source artifacts, emits rollback V2 receipts with freshly observed versions, and keeps the CLI and downstream flags blocked by default. The focused offline suite passes and no cloud, IAM, GCS, or credential operation was performed. Watch for: **confirmed** — the fixed `gcloud` runner strips the environment but never transports the supplied signed credential, so the authenticated apply path cannot execute; **confirmed** — mutation bookkeeping can classify an effectful command followed by a read/transport failure as “no mutation” and skip rollback; **confirmed** — verifier provenance is still process-local metadata/callback plumbing rather than an independently enforceable cryptographic boundary; **confirmed** — downstream blocking is represented as fields, with no mandatory consumer gate found.

**Verdict**: NEEDS_CHANGES

## High-level view

The earlier REVIEW-081 command-boundary gaps are addressed locally: the allowlist is immutable, optional reads require an explicit `NOT_FOUND` marker, target-policy versions are checked, and source artifacts are revalidated against fixed digests. The remaining execution topology is inconsistent: `SubprocessGcloudRunner` requires credential metadata while passing only a minimal non-authenticated environment, and the fixed backend advertises `direct_gcloud=True` while the executor rejects that backend class.

Packet, prestate, attempt, evidence digest, authority, child approval, and expiry fields are now compared before ledger reservation, and rollback receipts record a new restored-state digest and observed resource versions rather than claiming restoration of the old versions. The approval signature and credential “ownership,” however, are enforced by in-process registries and a caller-supplied callback shape; the code does not establish a concrete verifier-owned cryptographic implementation at this boundary.

The executor keeps `later_operations_enabled:false` in the packet, ledger, receipts, and return values, and the CLI remains read-only. That is a fail-closed result for this entrypoint, but it is not an enforceable downstream gate because no consumer of this runner’s verified receipt or ledger was found.

1. **Credential transport and backend reachability** — The fixed `gcloud` runner validates credential metadata but passes no token or credential handle to the subprocess, while the executor rejects the direct-gcloud backend; implement one concrete reviewed adapter with explicit non-ambient credential transport and test the actual subprocess environment.
2. **Verifier-owned provenance** — Credential objects are plain metadata dataclasses and approval/signature verification relies on process-local registration plus a callback supplied to a private factory; require a real verifier-owned cryptographic signer/verifier and bind the accepted backend to that implementation.
3. **Unknown mutation outcome skips rollback** — A successful remote mutation followed by a failed post-command read can leave `mutation_count` unchanged, so the executor records no mutation and performs no rollback; mark each effectful attempt unknown before dispatch and reobserve or enter manual review on any uncertain outcome.
4. **Downstream gate is declarative** — `later_operations_enabled:false` is emitted but no mandatory downstream consumer verifies a terminal verified receipt/ledger; add a gate that rejects every later operation until the IAM receipt is independently verified.

### Authenticated execution through the fixed command boundary

The fixed runner requires an `InjectedSignedEnvironmentCredential`, checks its source, expiry, and no-ADC/no-key flags, and then invokes the absolute SDK path with shell disabled and `stdin=DEVNULL`. The actual subprocess environment is only `PATH`, `LANG`, and `LC_ALL`; the credential is not converted into an access-token argument, an explicit credential file descriptor, or any other non-ambient transport. Since `FixedCommandIAMBackend` is marked `direct_gcloud=True` and `ReviewedFixedCommandExecutor` requires `direct_gcloud=False`, the module has no concrete authenticated production path that can both satisfy the executor and perform the fixed commands. This is **confirmed** by the runner and backend checks; provide the explicit credential injection/adapter contract before any apply is eligible.

### Signed credential and child approval provenance

The child approval now has useful exact bindings: packet artifact digest, fixed attempt, normalized prestate digest, credential evidence digest, authority digest, signer identity, issued/expiry window, and an approval digest are all checked before the ledger is reserved. Source definition, capability, prestate, and live-observation files are also reopened and checked against the packet’s fixed digests, which closes the REVIEW-081 self-digested packet gap.

The remaining provenance is not independently enforceable at this boundary. `InjectedSignedEnvironmentCredential` is a freely constructible frozen dataclass with no seal or registration, `VerifiedCredentialReadinessEvidence` and `VerifiedIAMChildApproval` rely on process-local object identity registries, and `VerifiedIAMApprovalSignatureVerifier` ultimately executes a callback supplied to `_issue_verified_signature_verifier`. The executor also accepts any object with the expected backend attributes and `validate_credential_binding` method rather than requiring a concrete verifier-owned adapter. These are **confirmed** implementation properties; replace them with a real verifier-owned cryptographic object/factory and strict adapter identity before treating the approval or credential as signed provenance.

### Rollback receipts versus uncertain mutation outcomes

The V2 rollback receipt records a newly observed restored-state digest, per-resource digests, and current versions, while semantic comparison deliberately ignores version fields so it does not claim that old IAM versions were recovered. The resource guards reject known version/state drift before the reviewed rollback writes.

The mutation boundary still has an unsafe uncertainty hole. `FixedCommandIAMBackend._mutate` increments `mutation_count` only after the cloud command and a follow-up `_current()` read succeed. The executor updates `mutation_started` only after each backend method returns. If the cloud command succeeds but the follow-up read fails, or a backend raises after a remote mutation, the exception reaches the failure branch with `mutation_started=False`; the ledger then reports no mutation and skips rollback. **Confirmed**: effectful calls need an attempt marker set before dispatch, with uncertain outcomes forcing re-observation/manual review rather than silently treating the resource as untouched.

### Downstream blocking and test boundary

The packet loader rejects enabled downstream operations, and the executor’s ledger events, success/failure results, receipts, and CLI output all carry `later_operations_enabled:false`; the blocked CLI smoke test also confirms no ledger is created. No downstream module imports this executor or validates its terminal ledger head/receipt before proceeding, so the protection is currently declarative. **Confirmed** as a repository-scope observation: add a mandatory predecessor check for the later operation rather than relying on callers to honor a boolean.

The focused suite passes `24` tests, including immutable allowlist and explicit not-found handling, target-policy version drift, source/packet digest checks, verifier prerequisite rejection, child-approval binding, fresh rollback receipt fields, manual-review rollback, one-attempt rejection, and blocked CLI behavior. Compilation and the read-only `validate` command also pass; the latter reports `applied_state:false`, no cloud operations, and `later_operations_enabled:false`. Not tested are a real subprocess environment capture proving credential transport, a real cryptographic signer/verifier, a mutation-success/read-failure rollback case, and a negative downstream-gate integration test.
