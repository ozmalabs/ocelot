# Evaluator-attested native graph exports at the P1 boundary

The P1 launcher now admits a graph export only after an authority signature binds its digest to the run, control plane, agent build, input snapshot, capture sequence, and capture time. The public client transmits only an opaque proposal identity; the evaluator process resolves it from the verified export, projects the V2 request, and binds the exact canonical bytes before the broker can accept it. In the default P0-A configuration the same exported action reaches a signed `method_not_enabled` denial, while the explicitly enabled local fixture accepts only the attested `steps=1` export and rejects both caller-created V2 traffic and `steps=2` request substitution. **Watch for: confirmed — one reachable launch rejection, a receipt log whose manifest hash does not match the verified manifest, raises before writing either a receipt or a launch-attestation record.**

**Verdict**: NEEDS_CHANGES

## High-level view

The acceptance path is constrained to evaluator-attested canonical export data. Export tampering, omitted or forged attestations, and malformed export bytes stop before a client exists and produce signed terminal launch receipts; the local fixture has a distinct authority signer, but the repository correctly documents that this does not provide evaluator custody against a same-user adversary.

The retained process endpoint accepts only proposal IDs. Malformed messages, including raw V2 request bytes, receive signed denials; replay remains durable across broker restart, and the evaluation tick bypasses legacy host-dispatch construction entirely. The remaining accounting asymmetry occurs before export validation: a valid manifest plus a mismatched receipt log rejects with no durable boundary record.

## Attested export is the only enabled-fixture source

The enabled-fixture regression proves the key P1 property: the export contains `steps=1`, a caller recomputes a matching-looking V2 request for `steps=2`, and both the ordinary client API and deliberately accessed pipe reject that request. The evaluator resolves only the exported proposal ID, projects the request itself, and the broker compares the entire canonical request against a capability that cannot be supplied through the retained endpoint (`evaluation/p0a/entrypoint.py`, `evaluation/p0a/provenance.py`, `evaluation/p0a/broker.py`).

Missing, unknown-key, and digest-tampered attestations plus malformed export bytes terminate before an action client is yielded and write a signed `invalid_native_graph_export` impasse (`evaluation/p0a/entrypoint.py`; `tests/evaluation/test_graph_proposal_routing.py`; `tests/evaluation/test_p0a_startup.py`). This is protocol-level attestation, not real evaluator custody: the distinct local authority private key remains available to the same-user test harness. The limitation is explicitly recorded in `docs/security/P0A_LOCAL_HARNESS_DESIGN.md` and `docs/security/P0A_ROADMAP_EVIDENCE.md`.

## Retained endpoint and legacy boundary stay outside effect dispatch

The regression sends tuple-wrapped and bare canonical V2 bytes directly through the hidden client connection and receives a signed `raw_v2_evaluation_ipc_message` denial with no simulator effect (`evaluation/p0a/entrypoint.py`; `tests/evaluation/test_graph_proposal_routing.py`). Default P0-A denies the valid exported catalogue action before any grant is requested, and proposal/request/grant replay remains reserved in the signed receipt chain across restart.

The evaluation tick test replaces direct host-handler construction and dispatch with failures, then confirms the evaluation branch completes without either call. The route inventory test also invokes each registered host path directly under the active evaluation guard and confirms it fails before an effect (`tests/evaluation/test_graph_proposal_routing.py`; `tests/evaluation/test_legacy_io_blocking.py`). This is an inventory-scoped local guard, not hostile-agent containment, as the security documentation states.

## Receipt-log binding rejects outside the recorded launch path

`evaluation_mode` verifies the manifest, then compares `receipt_log.manifest_hash` to `verified.manifest_hash` and raises `ProtocolError("receipt log manifest mismatch")` directly (`evaluation/p0a/entrypoint.py`). That branch precedes the `_record_launch_failure` block used for invalid exports.

A standalone invocation with an otherwise valid signed manifest, valid export/attestation, and a deliberately mismatched receipt-log hash produced `ProtocolError receipt log manifest mismatch receipts= 0`. This is **confirmed**, not a failure to protect the effect path—the broker never starts—but it violates the requested condition that each reachable rejection has a receipt or launch-attestation record. The fix needs a verifier-owned failure record that does not rely on a log whose manifest binding has just failed; appending to the supplied mismatched log would defeat the binding being checked.

## Exercised coverage and remaining assertion

`python3 -m pytest -q tests/evaluation` passed: **30 passed**. The suite covers attestation absence/forgery/tampering, malformed startup export, raw V2 client-pipe traffic, enabled-method request substitution, default-deny behavior, replay across restart, direct registered host-handler denial, and tick-level legacy-handler exclusion. **Not tested:** a real evaluator-controlled signer/process/OS identity; this is outside the local fixture's claimed authority and documented as such.
