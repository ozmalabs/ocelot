# Rootless Podman acceptance gate repaired

The evaluator-owned Podman acceptance gate now stages a finite, Python-3.13-compatible Ed25519 runtime instead of depending on optional distribution metadata from the Python 3.12 test runner. It builds and imports that closure through both image interpreter paths before any hostile worker starts, then runs workers in a rootless, no-network, read-only profile that is checked from live Podman inspection. The three provisioned scenarios cover a denied opaque proposal, a forged authority frame, and evaluator-initiated stop of a worker descendant. The independent Python 3.12 execution collected all three cases and passed in 27.61 seconds. Watch for: no blocking concern remains.  
**Verdict**: APPROVED

## High-level view

The staging boundary is explicit: only the P0A import closure, the finite cryptography/Ed25519 manifest, `_rust.abi3.so`, and the required CPython-3.13 CFFI backend cross into a fresh build context. The gate chooses a local Python 3.13 runtime for those ABI-specific files while allowing the test suite itself to run under Python 3.12, then proves imports through both `/usr/local/bin/python3` and `/usr/local/bin/python3.13` in the derived image.

Each case runs under the same inspected hardened Podman profile: rootless user mapping, private namespaces, no network, read-only root, a sole writable tmpfs, dropped capabilities, no-new-privileges, seccomp, and resource limits. The hostile route produces a signed default-deny receipt for the sealed proposal; a raw forged authority frame instead yields a signed terminal protocol-violation record with zero receipts/effects.

Lifecycle control remains evaluator-owned. The stop scenario finds the live worker and child with `podman top`, invokes `podman stop --time 2` externally, and records a stopped container with PID 0 and no remaining container processes. Cleanup first inventories only the launcher's exact nonce-qualified container/tag, removes those artifacts, and leaves the cached base image plus unrelated Podman workloads outside its scope.

### Python 3.12 test execution with a finite image-compatible import closure

The repaired launcher no longer uses `importlib.metadata` file lists as its staging authority. It selects a local Python 3.13 cryptography installation whose ABI matches the pinned `python:3.13-slim` image, copies the finite Ed25519 closure plus the explicitly named ABI3 Rust and CPython-313 CFFI extensions, and rejects paths outside that manifest. Before a worker can run, the derived image imports the complete P0A and cryptography closure with both available image interpreter paths; each final-case evidence record reports return code 0 and all 12 expected module paths for both interpreters.

Independent validation reran `P0_RUN_OS_ISOLATION_TESTS=1 P0_OS_ISOLATION_PROVISIONED=1 /usr/bin/python3.12 -m pytest -q -vv --basetemp=/tmp/p0a-independent-verification tests/evaluation/test_os_isolation_integration.py`. Python 3.12.3 collected and passed the hostile, forged-frame, and external-stop cases in 27.61 seconds, so the staging repair is exercised rather than inferred from the retained artifacts.

### Hardened profile constrains each live worker

Every retained and independently regenerated case records a passed local/rootless/non-remote preflight, a local-only build with `--pull=never` and `--network=none`, and live inspect data for the worker. The inspect evidence confirms `65534:65534` with the exact `0:1:65536` mappings, read-only root, private PID/IPC/UTS/cgroup namespaces, network mode `none`, no privilege or added capabilities, no-new-privileges plus the explicit seccomp policy, 64 PIDs, 256 MiB memory/swap, 0.5 CPU, and `/workspace` as the sole writable tmpfs. The command contains no checkout, control directory, socket, bind, volume, privileged flag, host namespace, or inherited host environment.

### Hostile probe receives a denial receipt without host access

The hostile case's retained report sees only descriptors 0–2. Its attempted reads, directory listings, and writes against evaluator-created checkout, home, control, receipt, terminal, and result sentinels all fail; attempts to access loopback/external targets and both Podman socket paths do not succeed. Its sealed proposal ID is returned in phase `denied`, and the retained `ActionReceiptV2` is signed, binds the proposal digest, and records `method_not_enabled`; the evaluator-side sentinel snapshot is unchanged.

### Forged authority frame terminates before effects

The forged-frame case retains an `EvaluationRuntimeFailureV1` terminal record signed by `receipt-log-writer`, with reason `sandbox_protocol_violation`, error `agent protocol authority field`, and no prior valid receipt. Its evidence records `accepted_effects: 0`, while the case assertion verifies the receipt sequence remains zero. This keeps malformed authority input on the terminal failure path rather than converting it into an action or ordinary receipt.

### Evaluator stop reaches the descendant scope

The stop case first records both the worker init process and its `time.sleep(300)` child from `podman top`, alongside the live container cgroup. The evaluator then runs `podman stop --time 2`; Podman escalates to SIGKILL after the hostile process does not exit on SIGTERM. Post-stop inspection records `Running: false`, `Pid: 0`, exit code 137, and `StoppedByUser: true`; the post-stop process list is empty (Podman 4.9's expected stopped-container `top` rejection is retained as evidence).

### Exact-name cleanup reclaims only P0A task artifacts

All three final-case evidence files show a prefix-confirmed cleanup inventory containing one exact `p0a-<nonce>` container and one exact `localhost/p0a-acceptance:<nonce>` tag, followed by successful stop, remove, and image-remove commands and zero matching artifacts afterward. The pre-repair scoped inventory separately records 24 task-tagged images and four stopped `p0a-` containers; the present Podman inventory contains no P0A tag or container, demonstrating that the task artifacts were reclaimed. The cached `python:3.13-slim` base image remains, as do the unrelated stopped workloads and the running `jellyfin-uxperf-test` container, consistent with the exact-name/tag cleanup boundary. The integration tests wrap preflight/build/import/run work in `finally` cleanup, and the launcher performs the same scoped inventory before removal when a start path fails.
