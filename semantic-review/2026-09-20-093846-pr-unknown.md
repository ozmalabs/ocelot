# Rerunnable Confidential Space/WIF/KMS credential bootstrap

The change adds a small, read-only credential bootstrap around the existing `ConfidentialSpaceAdapter`. The adapter obtains the launcher token through the shared bounded Unix-socket protocol, verifies the JWT nonce, issuer, audience, time window, image, project, zone, TEE, AMD SEV, Secure Boot, debug, workload, and smoke claims, exchanges it with the exact WIF provider, and derives a short-lived impersonated IAM token without exposing token bytes. The new process validates the reviewed KMS authority binding and capability observation, keeps requests and approvals in pending/non-applied states, and emits a sealed redacted receipt rather than signing, uploading, or mutating cloud state. **Watch for:** **confirmed** the final receipt is not re-bound to the adapter's actual STS source, configured service account, or capability binding; **confirmed** the child-approval request digest omits the capability account and destination identity; **confirmed** the credential-only factory check happens after activation, allowing an ordinary capability factory—and, for a non-GCS-only target, a KMS public-key read—to run before rejection; **confirmed** the new bootstrap has no production caller and its happy-path tests do not exercise the real launcher adapter path.

**Verdict**: NEEDS_CHANGES

## High-level view

The attestation gate is the strongest part of the path: it uses the shared launcher framing adapter and rejects mismatched nonce, time, identity, hardware, posture, workload, and smoke claims before STS. The resulting startup evidence is bounded and redacted, and the credential factory limits the derived token to the source and attestation lifetimes.

The process does not apply IAM or write protected artifacts, but **confirmed** its final receipt boundary trusts a registered capability receipt without checking that its source digest, account, and capability-binding digest match this activation. **Confirmed** the request/approval digest also leaves the account and destination outside the approved operation identity, so a valid approval can be reused with a different configured capability target.

The implementation remains a library-only review boundary: **confirmed** `bootstrap_credentials` has no runtime or container entrypoint caller, while the tested production entrypoint still activates the normal evaluator service. The tests prove the synthetic adapter seams and redaction, but **confirmed** they do not prove that this process invokes the shared launcher socket and verifier as a single end-to-end credential flow.

<summary>Details</summary>

### Capability receipt is not re-bound to the live STS activation

**confirmed** — `bootstrap_credentials` validates that `adapter` is the exact adapter type, activates it, checks that a receipt exists and that its expiries do not exceed the attestation (`services/p5_r0_evaluator/deploy/signed_environment_credentials.py:385-393`), but it never compares `capability_receipt.source_token_digest` with `activation.federated_token_digest`, `capability_receipt.service_account` with `adapter.config.capability_service_account`, or `capability_receipt.capability_binding_digest` with the receipt factory's binding digest. The factory's private `_receipt` slot is still an ordinary mutable attribute, and valid verifier-registered receipts can be produced for arbitrary source/binding/account combinations through the existing short-lived-capability validator. Replacing that slot after activation therefore allows the bootstrap to emit a receipt whose credential provenance does not describe the launcher/STS token or capability target used by this run, while all current checks pass.

The final boundary should require all three equalities, and the test suite should inject registered receipts with a mismatched source digest, account, and binding digest and assert that no bootstrap receipt is emitted. The later `build_verified_credential_readiness_evidence` path performs a source-digest comparison, but that does not repair the weaker standalone bootstrap receipt.

### Approval identity omits the capability account and destination

**confirmed** — `_expected_claims` and `build_execution_request` commit provider, audience, image, project, zone, TEE/posture, workload/smoke, KMS version, and authority-binding digest (`services/p5_r0_evaluator/deploy/signed_environment_credentials.py:62-76,135-153`), but they do not commit `capability_service_account`, the WIF principal, bucket, prefix, or run/destination identity. `validate_execution_request` therefore accepts an old request and child approval after those target fields change, because the rebuilt request remains byte-for-byte equal; the later capability-binding check validates the current binding, not what the approval authorized.

Add the exact target account/resource, WIF principal, bucket, prefix, and capability-binding digest to the closed request schema and bind them into the approval digest. Add a regression test that changes each target field after approval and proves validation stops before launcher activation.

### Credential-only guard runs after ordinary capability activation

**confirmed** — the process checks `isinstance(factory, CredentialOnlyCapabilityFactory)` only after `activate_after_external_preflight` has called `adapter.activate_attested_service` (`signed_environment_credentials.py:385-388`). A caller can supply the ordinary `CapabilityFactory`; activation then creates GCS and KMS clients and constructs `KMSEd25519Signer`, whose constructor performs a KMS `get_public_key` read, before the process rejects the factory. This violates the module's credential-only boundary and can contact a protected KMS endpoint even though the requested operation is only credential derivation.

Require the exact credential-only factory before any adapter activation, and add a test with a normal factory whose KMS client records calls; the call count must remain zero when bootstrap rejects the adapter.

### Bootstrap receipt is not wired to the runtime or readiness consumer

**confirmed** — `bootstrap_credentials`, `CredentialBootstrapReceipt`, and `CredentialExecutionRequest` have no callers outside `services/p5_r0_evaluator/tests/test_signed_environment_credentials.py`; the container entrypoint still constructs and serves `ConfidentialSpaceAdapter` directly (`services/p5_r0_evaluator/confidential_space_app.py:67-74,145-170`). The receipt therefore cannot currently be the process's operational output or the input to the verifier-owned R18R13 readiness path; it is a tested library seam rather than a rerunnable deployed process.

Wire one explicit, non-HTTP invocation that supplies the reviewed request/approval/binding artifacts and emits only the receipt, or document and test the external caller contract. The integration test must assert that a real `LauncherTokenSource`/shared launcher protocol path feeds the receipt and that the receipt is consumed by the intended readiness transition without promoting any proposal to applied state.

### End-to-end launcher evidence coverage is synthetic

**confirmed** — the bootstrap happy path uses `FakeSource`, `FakeVerifier`, and a fake STS (`services/p5_r0_evaluator/tests/test_signed_environment_credentials.py:107-118`), while the launcher-protocol tests are separate and no changed test invokes `LauncherTokenSource` or `launcher_protocol.fetch_token` through `bootstrap_credentials`. The adapter unit tests cover individual claim mismatches and the probe covers framing, but they do not establish that this credential process consumes a real launcher response, verifies the nonce against that response, exchanges that exact token, and preserves only redacted evidence in one flow.

Add an adapter-level integration fixture with a fake Unix socket speaking the shared launcher protocol and a verifier that returns the decoded claims, then assert the request contains the configured audience and unique nonce, the STS subject is the launcher token, all fixed claims are enforced, and no raw token appears in the receipt or emitted output. Keep the test entirely local; it need not call Google.
