# Cloud evaluator security and P5 V3 integration review

The deployed `p5-v3-evaluator` is protected by Cloud Run IAM plus a Google OIDC subject allowlist, rejects malformed and replayed requests, uses Cloud KMS for remote signing, and keeps held-out truth behind a private GCS adapter. The code does not accept or export private key material, and its worker projection excludes the evaluator’s private fields. **Watch for:** **confirmed** production timing is uncertified; **confirmed** `roles/storage.objectAdmin` is broader than necessary; **confirmed** authority metadata, signing, and privacy were not exercised on a real run because the corresponding endpoints/bundle are absent. **Verdict**: NEEDS_CHANGES

## High-level view

The supplied deployment evidence supports a fail-closed Cloud Run boundary: unauthenticated access is denied, final ingress is private, and application OIDC restricts callers to the runner subject. A completed authenticated run was not possible because the private bucket had no committed objects.

Authority metadata is fixed at startup and KMS refuses a public-key mismatch, but there is no `/v1/authority`, `/healthz`, or standalone `/v1/tasks/sign` route. Stability and signing therefore cannot be independently smoke-tested through the deployed API.

Canonical schemas, principal-bound runs, idempotency, sequence checks, task digests, and generation-checked state provide useful replay resistance. The private-truth projection is protected by code-level separation, but production privacy remains untested without a populated bundle.

The wrapper intentionally ends in local-readiness impasse: it omits controls/contrasts, has no restart rehydration, and cannot attest native containment or rollback closure. It is not ready to integrate with P5 V3.

### Cloud Run IAM and application OIDC boundary

The supplied evidence reports HTTP 403 for unauthenticated access, no service-level public binding, and final ingress `internal-and-cloud-load-balancing`. `GoogleOIDCVerifier` also checks the configured audience and runner-subject allowlist. **Confirmed limitation:** these platform/IAM commands could not be re-run because `gcloud` is not installed in this checkout; the live conclusions rely on the supplied smoke/deployment record.

### KMS authority and private-bucket permissions

`KMSEd25519Signer` obtains the KMS public key at startup, compares it with configured authority metadata, and sends only a SHA-256 digest to `asymmetric_sign`. No private-key import, environment variable, export operation, or response field carries private key material. **Confirmed limitation:** the empty bundle and absent `/v1/tasks/sign` meant no live KMS signing request was exercised; the no-export conclusion is implementation-verified, not production-response-verified.

The supplied IAM evidence gives the service account `roles/cloudkms.signerVerifier` on the specific key, which matches the signing need. **Confirmed concern:** the retained `roles/storage.objectAdmin` bucket grant is wider than the adapter’s `get`, create-only upload, and generation-checked replacement operations; delete and other administration are not needed. Least privilege is therefore not met as reported, despite the bucket being private and having no public grant.

### Replay rejection and fail-closed state transitions

Canonical parsing and closed endpoint schemas reject malformed requests; run state binds the principal and commitments, and subsequent calls enforce idempotency, one outstanding task, sequence, and task digest. A changed replayed result returns 409, a nonexistent run returns 404, and missing committed objects return 422. The focused service suite passes 4 tests covering canonical rejection, result signature verification, duplicate-result idempotency, changed-reply replay rejection, missing identity, and the injected timing seam.

**Confirmed gap:** the supplied smoke results cover only negative paths—invalid input, replay-shaped nonexistent run, and missing objects—so they do not prove a successful real-bundle run or deployed KMS/GCS write path.

### Authority metadata and endpoint contract

The configured authority is copied at startup; locks are checked against the exact authority object, authority digest, transport-attestation digest, and Ed25519 lock signature. **Confirmed gap:** `/v1/authority` is absent, so authority stability is only indirectly observable in run responses, and no run reached that response path. **Confirmed gap:** `/healthz` and `/v1/tasks/sign` are also absent, removing the reported readiness and standalone-signing smoke contracts.

### Held-out truth boundary

The GCS adapter keeps the private store server-side, and the V3 task builder derives worker observations and legal actions without copying truth, target actions, secret seeds, split labels, or private family fields into the envelope. **Confirmed limitation:** the bucket remained empty, so no deployed request produced a task from real held-out truth. A populated-bundle smoke must inspect every start/task/result/error response and stored evidence artifact before accepting the privacy property operationally. Truth/store digests are commitments rather than the underlying truth, but their permitted exposure still needs confirmation against the P5 V3 threat model.

### Timing attestation and the third-party seed proposal

**Confirmed:** timing is not certified by this deployment. `create_service()` passes no attestor, so `timing_certified` is false and the final seal records the missing independent timing ledger. The injectable interface records only `task_issued` and `result_received`; it does not observe the worker’s actual process start/end or CPU boundary.

A third-party seed service could certify freshness and ordering by generating unpredictable seeds, durably sequencing events, trusted-timestamping them, signing run/task/payload bindings, and committing start/end event IDs into the task/result/receipt chain. **Confirmed limitation:** that would certify the provider-observed interval, including transport and provider scheduling—not exact worker CPU time or containment. Exact execution timing requires observation or control of the worker boundary; a runner-submitted seed or timestamp is only an assertion.

**Confirmed concern:** `validate_attestation()` requires only a nonempty signature and does not verify the signature, trusted authority, global sequence continuity, seed turnover, or timestamp semantics. A third-party integration must implement those checks and fail closed on missing, invalid, stale, or contradictory events.

### P5 V3 integration boundary

**Confirmed:** the service README and implementation limit this wrapper to local readiness. `_schedule()` emits primary arms without controls or mechanics contrasts; finalization creates a `P5R0ResultSealV3HTTP` with `native_verified: false`, `disposition: impasse`, and no-release claim language. The existing local seal verifier needs an adapter for this GCS-backed HTTP seal, and the process-local engine has no restart rehydration implementation. This is an authenticated no-go/impasse wrapper and security smoke target, not a P5 V3 integration-ready evaluator.
