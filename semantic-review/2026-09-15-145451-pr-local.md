# Opaque graph-proposal evaluation ingress

The change introduces an evaluator-owned process that resolves an opaque graph proposal ID from a sealed native export and projects the canonical candidate to `ActionRequestV2`. The process boundary prevents the public client from submitting a V2 body, binding, grant, or callback; the projection binds its canonical bytes to the export evidence, so a `steps=1` proposal is not structurally rebindable to `steps=2`. The P0 manifest’s empty enablement set remains the first authorization check, and the proposal pump bypasses the legacy host-handler and voice paths. **Watch for: confirmed — every valid public-client submission raises `TypeError` while decoding the endpoint reply, so callers cannot receive the denial/acceptance reply or its observed receipt.**

**Verdict**: NEEDS_CHANGES

## High-level view

The public side of the evaluation boundary accepts only a string proposal identity, while the evaluator process owns the provenance verifier, projector, and broker. A raw V2 request cannot cross that protocol, and the canonical request binding includes the exact projected bytes, which prevents a caller-supplied `steps=2` request from replacing the exported `steps=1` candidate.

P0 default denial, graph replay reservation from signed receipts, and the daemon’s evaluation-only proposal pump are present in the privileged path. They are not reachable through the supported client because the wire reply contains a serialization field that the client passes to a constructor which does not accept it.

**Confirmed:** the suite also contains an unconditionally failing ambiguity test: its duplicate proposal IDs are rejected while building the sealed export, before the projector can return the asserted ambiguity denial.

## Public proposal submissions fail at the process boundary

**Confirmed.** `_projector_endpoint` serializes its reply with `reply.as_dict()`, which includes `schema: "BrokerReplyV1"` (`evaluation/p0a/entrypoint.py:72`). `EvaluationActionClient.submit_graph_proposal` then constructs `BrokerReply(**reply_data)` without removing that field (`evaluation/p0a/entrypoint.py:98`), but `BrokerReply` has no `schema` constructor parameter. Consequently every valid public proposal ID raises `TypeError` after the evaluator has already projected the proposal and appended a receipt. This blocks both expected P0 `method_not_enabled` replies and enabled-fixture acceptance replies, and prevents `observed_outcome` from receiving the receipt mirror.

The connection accepts only a string ID, `submit_exported_proposal` resolves evaluator-owned evidence, and the binding compares the complete canonical projected request bytes. The regression test for an exported `steps=1` candidate therefore reaches its final valid submission only to fail at this reply decode; it does not currently prove the expected `steps=1` receipt through the public API.

## Duplicate native-evidence fixture cannot exercise ambiguity

**Confirmed.** `test_stale_or_ambiguous_native_provenance_is_denied` creates an export containing the same proposal twice and expects `GraphProposalProjector.submit` to return `ambiguous_graph_provenance` (`tests/evaluation/test_graph_proposal_routing.py:121-123`). `NativeGraphProvenanceVerifier._validate_export` rejects the duplicate `proposal_id` during construction (`evaluation/p0a/provenance.py:98-103`), so the test raises `ProtocolError` before creating a projector. This leaves the evaluation suite red and documents a behavior that the implementation cannot reach.
