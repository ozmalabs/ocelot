### Authority/KMS binding can drift from the reviewed key

**Confirmed.** `services/p5_r0_evaluator/deploy/rs069r18r11_operation_3.py:167-188` delegates to the generic `validate_candidate_binding`, then only fixes the transport, project ID/number, and KMS project prefix. It never requires the reviewed values from `authority_binding_proposal.py`: `REVIEW_AUTHORITY_ID`, `REVIEW_KEY_ID`, `REVIEW_PUBLIC_KEY_DIGEST`, and `REVIEW_KMS_KEY_VERSION` (`services/p5_r0_evaluator/deploy/authority_binding_proposal.py:24-28`). Consequently, any self-consistent Ed25519 public key, arbitrary authority/key identifiers, and any syntactically valid KMS version under `projects/ocelot-proof/` can produce `binding_verified` and be recorded in the operation-3 ledger.

The focused test constructs exactly such a non-canonical packet: it generates a fresh key at `test_rs069r18r11_operation_3.py:32-42` and uses `projects/ocelot-proof/locations/us-east1/...` at line 86, whereas the canonical proposal fixes the public-key digest and the `locations/global` KMS version. The passing test therefore demonstrates the gap rather than protecting the reviewed binding. Bind the operation-3 artifact to the canonical proposal commitments (including the exact public-key digest and key version), and add negative tests for changed authority ID, key ID, public key/digest, and KMS version.

The exact unsigned request and R18R10 dependency checks are covered by the focused suite, and the exercised execution path reports no cloud operations, no signature, no production promotion, and no downstream enablement. `python3 -m pytest -q services/p5_r0_evaluator/tests/test_rs069r18r11_operation_3.py` passes 5 tests; no cloud command was run.
