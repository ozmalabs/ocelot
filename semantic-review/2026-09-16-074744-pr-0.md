# P4-R0 local no-go readiness boundary

The change adds a bounded Rust planning state machine plus a local evaluator, signed lock/receipts, staging checks, and a rootless/offline Podman policy. The coordinator deliberately cannot produce trusted execution evidence: without an attested digest-bound native worker it emits signed impasse/no-go receipts and restores the original graph, preserving the stated local-only scope. The native planner uses `future_manifold::feasible_selection` before it emits its intervention request, and the evaluator remains the intended grant and action authority. **Watch for:** **confirmed** — a state-machine action outcome is accepted without any receipt or proposal binding; **confirmed** — evaluator grants accept arbitrary action kinds and resource reservations above every locked limit; **confirmed** — the staging closure helper is never applied to the Podman inputs, so a future enabled execution path would not bind mounted artifacts to the lock.  
**Verdict**: NEEDS_CHANGES

## High-level view

The Rust side is a native, graph-only causal planning path: it selects a feasible candidate through the existing manifold API, records belief-to-proposal nodes, asks for one intervention, then replans before proposing an action. The progression is bounded by a fixed limits structure, and unsupported manifold inputs become impasses rather than effect requests. The action-outcome transition, however, trusts a caller-supplied enum and does not require even a syntactically valid receipt, so the claimed sealed evaluator boundary is not present at that final step.

The evaluator contains the right separation of roles in outline: it creates envelopes, issues a one-use token, owns simulator calls, and can restore the graph. Its validator leaves `kind` unrestricted and treats every non-negative reservation as valid, while `grant` never compares those fields to the lock's limits or tracks cumulative use. The one-shot property therefore prevents replay of a specific token but does not control what a valid proposal is allowed to request.

The current coordinator preserves local-only scope by always returning `no_go` after containment preflight, writing impasse/result/rollback receipts rather than an execution trace. The Podman policy expresses useful restrictions, but the lock and `P4PodmanSpec` are not joined through `validate_closure`; the specified worker, agent, and input mounts have no digest check against the preregistration artifacts. This is harmless while the forced no-go remains in place, but it is a blocking trust-boundary gap before the containment path can be enabled.

<summary>Details</summary>

## The action result is not sealed to the action it completes

The planner emits the action proposal in phase 2, then phase 3 completes whenever `status` is `SealedActionOutcome`. That branch does not require `parent_receipt`, validate a digest, compare it to the action proposal, retain the proposal identity, or reject a repeated/non-monotonic `logical_time`. Phase 1 and phase 2 only require a string with the `sha256:` prefix and a fixed length; unlike the Python protocol’s `is_digest`, they do not even require hexadecimal characters.

This is **confirmed** to break evaluator-owned outcome separation. Any caller with access to `advance_p4_r0` can move an action proposal directly to `Complete` with a fabricated `SealedActionOutcome` and `None` receipt. The existing negative test proves only that an action outcome at phase 2 is rejected; it does not cover the phase-3 missing-receipt path. Persist the intervention/action proposal digests and expected evaluator receipt hash in immutable causal evidence, have the evaluator validate and supply the matching signed outcome, and test missing, malformed, unrelated, replayed, and out-of-order receipts.

## One-use grants still authorize unlimited arbitrary work

`validate_proposal` requires a closed object shape and non-negative integer reservation fields, but it imposes no allowlist on `kind` and no upper bounds. `P4R0Evaluator.grant` validates only that shape, derives a token from proposal digest and time, and adds it to a set; it does not receive the lock limits, accumulate prior reservations, or check that the proposal’s parent receipt is an evaluator-issued receipt. A valid proposal with `kind="arbitrary-unrestricted-kind"` and `{actions: 999, risk: 999, transactions: 999}` receives a token, as confirmed by direct execution.

This is **confirmed** to leave the advertised action, risk, and transaction controls as metadata rather than enforcement. The token is consumed after one successful `act`, which prevents reuse of that particular grant, but a caller can request as many separately valid grants as it can construct. Make the evaluator own a ledger keyed by run and lock, reject unsupported kinds and parent lineage, compare each request plus the accumulated reservation to the locked ceilings, and derive outcome receipts from that ledger.

## Podman preflight does not bind the staged execution inputs

`staging.validate_closure` can reject symlinks and digest mismatches, but no P4 caller invokes it. `preregister_local` hashes the Rust source export, Containerfile, seccomp file, fixture bundle, and preregistration document; it cannot hash an unavailable worker. `P4PodmanSpec.validate` later checks that its worker, agent, input, and seccomp paths are below a staging root and checks only the seccomp digest. It does not compare the worker, agent, or input contents to the signed lock.

This is **confirmed** as an activation blocker for the otherwise restricted Podman path: after the intentional `native stdio protocol not yet attested` exception is removed, a caller can supply a different staged worker/agent/input tree while retaining the same valid lock and image digest. Extend the lock with the complete closure digests, verify them immediately before preflight, and make the launcher consume only the verified paths. Until then, retaining the existing impasse/no-go behavior is required.

## Local-only failure behavior is correctly non-promotional, but not execution evidence

`run_local` forces an impasse after containment preflight, writes signed impasse and no-go receipts, restores the graph exactly, and returns `classification="local_readiness_only"` with adoption and promotion authority both false. That result must not be treated as a fixture run or release evidence.

Not tested: no end-to-end native worker protocol exists to exercise the full proposal → grant → action → evaluator outcome chain. Add it only after the provenance, grant limits, and staged-closure bindings above are enforced; until then, tests should continue to assert no action call and exact rollback on every containment failure.
