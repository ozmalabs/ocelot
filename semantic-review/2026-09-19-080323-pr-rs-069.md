# RS-069 reviewed desired-state plan for signed-environment execution

RS-069 adds a blocked, review-only JSON plan for binding a candidate image, correcting WIP claims, binding self-custodied KMS authority, ingesting a diagnostic bundle, configuring Cloud Run/Confidential Space, preparing a supervisor run request, and cleaning up or rolling back. The plan keeps production values unresolved, records diagnostic inventory digests, requires approval at every operation, and contains no direct cloud mutation commands. The local validator confirms the seven-operation order, digest commitments, no-op/drift wording, self-custody boundary, and empty command lists, but it does not turn those prose contracts into a machine-applicable IaC state. The proposed state should remain blocked and non-mutating while the plan gains typed resource/object state and explicit activation and approval evidence bindings.

Watch for: **confirmed** the plan is not yet rerunnable IaC state: resource addresses, desired attributes, ownership, remote fingerprints, and state-lock semantics are absent, so an apply workflow would have to reinterpret prose. **Confirmed** approval gates are free-text markers rather than operation-scoped, digest-bound approval records. **Confirmed** bundle ingestion does not enumerate or validate the eleven object records, and **confirmed** Confidential Space activation is only a configuration/attestation prerequisite, not a represented state transition.

**Verdict**: NEEDS_CHANGES

## High-level view

The dependency chain is sensible and preserves the intended trust boundary: image identity precedes WIP claims, authority/KMS binding precedes bundle ingestion, and runtime configuration precedes run preparation and cleanup. The **confirmed** state-model gap is that the JSON is a review checklist with stable-looking idempotency keys, not a provider-backed desired state; matching and drift behavior are asserted in prose and are not tied to resource identities or observed state fingerprints.

The plan deliberately retains null and `REQUIRED_INPUT:` values for production image, project, provider, authority, KMS, bucket, attestation, supervisor, and rollback inputs. That is the right blocked posture, but the **confirmed** approval-model gap is that no typed approval artifact is bound to each operation and exact input digest, leaving the gate dependent on an external interpretation.

The bundle operation names create-only and generation-checked behavior, while the Confidential Space operation names immutable runtime commitments and exact attestation claims. The **confirmed** coverage gap is that neither operation supplies the concrete object/resource records or an activation evidence record needed to make those constraints rerunnable and auditable; supervisor/task work is correctly kept as preparation only, with task release absent.

<summary>Details</summary>

### Desired state versus a prose rerun contract

The operation chain is a useful review ordering, and the empty `commands` arrays plus `review_only_no_execution` boundaries keep this pass from becoming a shell-history replay. The **confirmed** gap is that `desired_state_operation`, `preconditions`, `expected_postconditions`, `rollback_conditions`, and `rerunnable` are all strings or lists of strings. The validator only requires those fields to be present and checks that the rerun text contains “no-op” and “fail closed”; it does not validate a resource address, provider type, desired attribute set, remote observation, state lock, ownership label, or import/update/delete policy.

As a result, a later approved workflow cannot mechanically answer what object it owns or how to compare the current state with the desired state. “No-op when provider desired state fingerprint matches,” “no-op when rendered desired state and revision fingerprint match,” and “restore the last approved revision/state” describe outcomes without supplying the fingerprints, revision identifiers, or state records that make those outcomes reproducible. Replace the prose-only operation payload with canonical typed desired-state records, retaining the current human-readable rationale alongside them.

### Approval and fingerprint barriers

The blocked status, `master_approval: false`, `confidential_space_approval: false`, unresolved production inputs, and explicit no-mutation boundary correctly prevent this plan from claiming execution. The **confirmed** enforcement gap is that the validator checks only that each `approval_gate` string contains `APPROVAL_REQUIRED:` and that the global booleans remain false. It does not bind an approval to an operation, the exact input/digest set, the approving authority, an expiry, or the transition it authorizes.

That creates a **likely** path for an external apply adapter to treat a generic approval as sufficient for a changed provider, image, bucket, or run request unless it implements rules that are not present in RS-069. Each mutation-capable transition should carry an approval record whose scope includes the operation ID, canonical plan digest, relevant immutable digests, approver, and expiration; the validator should reject an apply state whose record does not match those values.

### Create-only bundle ingestion needs object-level state

The ingestion operation correctly keeps the bucket, prefix, run ID, and generation state unresolved and explicitly protects the private case store. Its stated contract is create-only or exact-generation-match, with ownership-checked cleanup and no local upload. The **confirmed** concrete-state gap is that the plan has only aggregate artifact-index/manifest/private-store/task/control/lock digests, while the source index contains eleven separate artifact records with paths, file digests, and public/private flags. The validator checks aggregate fields against the index but never iterates the artifact records, verifies their files, or validates the planned destination/visibility/generation for each object.

That makes the “exactly the generated artifact index entries” postcondition dependent on an unstated renderer. Add an object map (or a canonical derived-state digest with a validator that fully checks its source) containing every suffix, content digest, file digest, visibility, ownership marker, and create-only/generation precondition. The private-truth object also needs an explicit private IAM/CMEK/retention state rather than only the prose assertion that it remains private.

### Confidential Space configuration is not activation

The runtime operation has the right security-oriented constraints in its desired text: immutable image and closure commitments, internal ingress, single-instance behavior, locked startup, exact claims, and no credential/KMS/GCS/task calls from local validation. The **confirmed** gap is that its postcondition is still only a local render, and its stop condition says startup must prove the attestation claims; no activation transition records a successful attestation or its evidence digest.

Operation 6 accepts `signed_environment_approval` as a required unresolved input and correctly refuses to invoke a supervisor or task. The **confirmed** consequence is that the activation result sits outside the RS-069 state model. Add an explicit activation step, disabled in this review-only pass, with a typed verified-attestation record binding the candidate image digest, canonical provider, STS audience, project/zone, subject prefix, claim-path map, nonce/time validity, and capability grants. Only that record should satisfy the run-preparation dependency; a generic approval string must not.

### Supervisor, task release, and rollback boundaries

The run-preparation operation preserves the no-execution boundary: task release authorization is explicitly absent, the self-custodied diagnostic claim is retained, and timeout/invalid-receipt/rollback-impasse outcomes are fail-closed. The cleanup operation likewise requires ownership, generation, prior state, and retention inputs and refuses unknown ownership. The **confirmed** remaining gap is that these outcomes depend on the missing typed state model: there are no concrete run resource addresses, supervisor state/receipt records, task-set binding in the run request state, or prior revision fingerprints to which cleanup can attach.

The proposed state for this pass is therefore still `blocked_pending_master_approval`, `ready: false`, with all unknown production values preserved, no cloud operations, no task execution, and no independent evaluator claim. Before changing that state to applyable, add the typed IaC/resource records, object-level bundle state, operation-scoped approvals, and verified Confidential Space activation record; then retain the existing fail-closed cleanup and task-release gates.

### Validation coverage

The CLI and six targeted tests pass. **Confirmed not tested:** rejection of a plan whose rerunnable prose names the wrong resource or omits ownership/state semantics; rejection of an approval not bound to a changed operation digest; per-object bundle path/digest/visibility/generation validation; or requiring a verified activation record before run preparation. Add regression tests for those cases with the typed state model.
