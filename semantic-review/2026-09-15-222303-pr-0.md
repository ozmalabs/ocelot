# Release-lock receipts retain non-authoritative caller evidence

P2 now distinguishes an unverified submitted envelope from the lock-sealed input and establishes the authoritative input digest only after `validate_lock()` succeeds. Malformed, untrusted, and tampered locks leave every lock-bound receipt digest null while retaining only `submitted_input_evidence_hash`; post-validation denials retain the lock manifest’s sealed-input digest. **Watch for: [confirmed]** receipt-chain reload is broken for both primary and fallback terminal records: schema validation constructs a set containing mutable sets and raises `TypeError` before signature or chain verification, so an existing receipt cannot be restart-verified or safely appended after. **Verdict**: NEEDS_CHANGES

## High-level view

The lock is the authority boundary: `score()` does not assign either the validated lock or its sealed-input digest until the trusted-key, content-hash, and signature checks return. Caller input is kept as separately named hash evidence, preventing invalid-lock terminal records from claiming it is the released input.

After validation, the runner binds `input_digest` from the lock before receipt-key, artifact-closure, worker, and envelope checks. That same bound digest flows through ordinary terminal receipts and receipt-persistence fallback records, preserving the distinction between locked input and submission evidence.

Receipt persistence still has a blocking restart defect. The initial append can create a signed seal, but every subsequent reload of a non-empty primary or failure log crashes while checking its allowed field schema; the signed chain is therefore not recoverable or append-safe.

## Caller input remains evidence until the release lock is trusted

`P2Runner.score()` starts with `lock` and `input_digest` unset and computes a safe evidence hash of the submitted envelope. The only assignment that gives either value authority is the successful return from `validate_lock()`, which verifies the trusted signer, canonical content hash, complete manifest, and signature. All failures before that point enter `_finish()` with a null lock and digest, causing `_receipt_payload()` to emit `lock_status: "unverified"`, null `lock_digest`, `input_digest`, `worker_image_digest`, and `evaluator_binary_digest`, plus `submitted_input_evidence_hash`.

The focused malformed-lock, wrong-trust-key, and tampered-lock tests passed and assert that shape.

## The locked sealed-input digest survives every post-validation denial

Immediately after a verified lock returns, `score()` copies `lock["artifacts"]["sealed_input"]` into `input_digest`, before evaluator-key checks, receipt-key checks, closure validation, worker preflight, or caller-envelope comparison. `_locked_envelope()` returns that same manifest value only after the staged file is measured against it and the submitted envelope is byte-identical to the sealed artifact. Thus artifact substitution, a different valid caller envelope, and worker/evaluator failures retain the lock-bound digest rather than substituting caller evidence.

The artifact-substitution and separately-signed-envelope coverage passed, including assertions that the receipt digest equals the lock’s `sealed_input` artifact while `submitted_input_evidence_hash` remains distinct.

## Primary and fallback terminal seals cannot be reloaded

**[confirmed]** `ReceiptLog._reload()` checks whether the parsed record’s fields match an allowed schema with this shape:

```python
set(body) not in {receipt_fields, receipt_fields | _OPTIONAL_DIGEST_FIELDS, ...}
```

Each candidate is a mutable `set`; creating the outer set raises `TypeError: unhashable type: 'set'`. `ReceiptFailureLog._reload()` repeats the same pattern for fallback seals. As a result, the first append may write, hash, sign, fsync, and seal a terminal record, but a restarted log cannot validate its signature or chain. A later score likewise cannot reload the primary receipt chain before append; the focused suite observed a second score degrade from `replay_denied` to `receipt_persistence_failed`.

Use an ordered container of set alternatives, such as `(... )`, or construct each candidate as a `frozenset`. This restores durable continuation of both terminal-record types.
