# Pre-attested P1 proposal mediation in the test-only Podman probe

P1 replaces the worker’s opaque proposal-ID submission with a bounded, complete `GraphActionProposalV1` sent over the stdio protocol. Before any V2 request exists, evaluator-side code verifies the signed native-export attestation and requires exact equality with the matching canonical export record; the trusted projector then seals the V2 request. Verified graph outcomes carry the native export and attestation digests in a signed `ActionReceiptV3`, while forged, mismatched, and replayed candidates receive chained denials without effects. The Podman path remains an evaluator-side, test-only acceptance probe and does not change Bubblewrap production launching. Watch for: **confirmed** this approval is limited to same-user, rootless-Podman mediation of a pre-attested fixture export; it is not evidence of evaluator custody, dynamic native-graph execution, or autonomous planning.

**Verdict**: APPROVED

## High-level view

The worker has one proposal ingress: `submit_native_graph_proposal` carries a complete candidate and rejects unknown frame types and authority-bearing fields. The host protocol does not turn a worker-selected identifier into a proposal; it passes the candidate to the evaluator-owned projector, whose equality check selects only data already present in the attested export.

The evaluator validates the export’s signature and run/build/control/input bindings before starting the worker. A successful equality match becomes a sealed V2 request binding, and the receipt writer records both export and attestation digests as V3 provenance. The tested default-deny outcome preserves this provenance without granting an effect capability.

The hardened Podman launcher is separately provisioned test code, with no production fallback or control socket mount. Its documentation consistently limits the result to a same-user local profile and explicitly requires a future evaluator-owned capture/replay service for any dynamic-native claim.

## Complete candidate ingress replaces opaque proposal selection

`EvaluationAgentProtocolV1` permits `submit_native_graph_proposal` only when the frame contains a `proposal` object, correlation ID, run binding, and session nonce. The legacy `submit_graph_proposal` message type is rejected, and the source and active security documentation consistently reserve “opaque” for the staged entrypoint binding rather than for graph proposal submission. **Confirmed:** no active worker submission route or description still authorizes an opaque proposal-ID lookup.

The host server accepts only that complete-candidate frame and documents that it will never translate a worker-selected opaque identifier. The worker client, the graph adapter, and the Podman hostile contract all pass the candidate itself, keeping request construction and grant access on the evaluator side.

## Attested equality gates V2 projection and V3 provenance

Prelaunch attestation verification binds the canonical native export to the verified run, agent build, control plane, and input snapshot before a worker is created. The provenance verifier then admits a candidate only when the complete dictionary exactly equals the uniquely matching export record; an altered but self-consistent candidate is denied as forged rather than projected. **Confirmed:** the V2 request binding is created from the evaluator-owned matched record, not from worker bytes.

The sealed binding carries the export and attestation digests into the broker’s graph receipt fields. `ReceiptLog` selects `ActionReceiptV3` only when native export provenance is present and validates that V3 records carry both provenance fields. The Podman integration assertions distinguish verified V3 denials from V2 denials for forged or mismatched candidates, preventing an unverified submission from being represented as attested provenance.

## Podman evidence is deliberately narrow and security limitations remain explicit

The acceptance launcher stages a finite runtime into a fresh context, uses a rootless non-remote engine with a cached image, disables pulls and build networking, and rejects mounts, control sockets, elevated capabilities, host namespaces, and inspection mismatches. It is invoked only from provisioned tests and does not modify the Bubblewrap-only production path. **Confirmed:** the code and both security documents state that same-user rootless Podman is not independent evaluator custody.

The documentation also states that the export attestation is a local protocol fixture and that the probe does not execute a dynamic native graph substrate or establish autonomous planning. A dynamic-native claim is required to fail closed until an evaluator-owned post-launch capture/replay service and distinct authority are deployed. This prevents the pre-attested test fixture from being described as stronger custody evidence than it supplies.
