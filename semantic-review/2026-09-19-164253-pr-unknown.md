# Fail-closed RS-069R18 operation-2 WIP mapping handler

These files add a narrowly scoped operation-2 handler that validates the blocked R17 request, canonicalizes the WIP provider prestate, applies one fixed gcloud update, verifies the poststate, and records a hash-chained ledger. The remaining authorization inputs are passed into the handler as ordinary mappings and strings, so their internal digests do not establish who produced or verified them. **Watch for:** **confirmed** — caller-constructed claim evidence and master approval can be treated as resolved without real attestation or authorization; **confirmed** — an unexpected exception after mutation can bypass the rollback block.

**Verdict**: NEEDS_CHANGES

## High-level view

The mutation path is a describe → exact prestate comparison → fixed update → describe sequence. Rollback reuses the fixed update command and compares configuration rather than the changed provider fingerprint, but the post-update cleanup boundary is limited to the handler’s custom blocked exception.

**Confirmed authorization gap:** the claim and approval records are caller-supplied, with “verified” and “approved” represented by literals, booleans, and self-computed hashes. The blocked request’s unresolved attestation inputs are therefore not independently resolved.

**Confirmed execution gap:** a ledger or other unexpected runtime failure can escape after the cloud update, leaving no rollback attempt or terminal ledger record. The tests cover pure helpers but not these authorization or post-mutation paths.

<summary>Issues (4)</summary>

1. **Real attestation is not verified** — The claim record is caller-constructed and only self-consistent; require a trusted cryptographic/token verification result, bind its evidence digest to the request and approval, and keep operation 2 blocked until that evidence exists.
2. **Master approval is self-authorizing** — `review_state`, approval flags, and the approval-record digest are all caller inputs; require a trusted, signed master-review record bound to the exact request and input digests rather than accepting recomputed fields.
3. **Rollback does not cover unexpected post-mutation failures** — Exceptions such as ledger I/O failures can escape the narrow catch after mutation; catch and classify all post-update failures, attempt the etag-guarded rollback, and record the terminal failure.
4. **Authorization and rollback paths lack adversarial execution coverage** — Tests accept a synthetic claim record and do not exercise unsigned approval rejection or unexpected post-update failure; add pure verification tests and mocked runner tests without invoking cloud mutation.

<summary>Details</summary>

### Claim-record digests do not establish real Confidential Space attestation

**Confirmed:** `_validate_claim_record` enforces a closed object, fixed schema/source strings, equality between supplied evidence and its digest, and exact candidate/project/zone/security values. Those checks prove only self-consistency. There is no signature, token verification, verifier identity, certificate chain, freshness/nonce validation, or trusted attestation artifact; the positive test constructs the entire “verified” record locally and is accepted.

**Confirmed:** `validate_request` requires the packet’s `attested_project_zone_and_image` and `zone_digest` inputs to remain `None`, while `validate_operation_2_bindings` accepts a separate `attested_claim_record` and substitutes its hash into approval bindings. A caller can therefore fill the unresolved boundary with declarations that satisfy local digest checks. The handler must consume trusted verifier output or signed evidence, bind its digest to the exact request/candidate/scope, and reject until real attestation is available.

### Master-review state is caller-supplied rather than authenticated

**Confirmed:** the gate accepts the literal `review_state == "master_reviewed"`, four caller-supplied booleans, a fixed approval ID, and a closed `approval_record`. Its `approval_record_digest` is recomputed from that same record, so it detects edits but provides no provenance or authorization. No signature, trusted review source, reviewer identity, or key binding is checked; a caller can manufacture `approved_single_operation_pending_apply` while the request still says `master_decision: pending`.

The approval record needs to be a trusted, signed master decision whose verified signature covers the request scope, operation/order, candidate image, provider, attestation evidence, template, mapping/condition, and later-operation disablement. Until then, the current R17 packet must remain blocked even when function arguments claim that review occurred.

### Post-update failures can escape without rollback

**Confirmed:** `mutation_started` is set before the update, but the surrounding handler catches only `RS069Operation2Blocked`. `_run_json` translates only selected runner failures; a post-update ledger write can raise an ordinary filesystem exception, as can another unexpected runner/runtime failure. The update may have succeeded, yet execution can exit before rollback, the failure ledger event, and the stopped event.

The post-mutation boundary must treat every failure as rollback-eligible, preserve the original failure in redacted form, and record whether rollback was verified or requires manual review. Tests should inject failures at post-update describe, poststate validation, ledger write, and rollback verification without invoking a real command.

### Tests cover binding helpers, not the authorization or execution boundary

**Confirmed:** the tests cover drift cases, changed-fingerprint rollback, hash chaining/redaction, closed stdin, fixed describe arguments, and disabled later operations, but they do not assert rejection of unsigned/caller-constructed attestation or approval. The attestation test instead accepts a manually assembled record, and no test exercises `execute_operation_2`, post-update exception handling, or terminal ledger outcomes. These omissions leave the two authorization blockers and rollback gap undetected.
