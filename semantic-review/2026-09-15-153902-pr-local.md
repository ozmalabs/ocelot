# Evaluation-mode I/O containment and terminal-evidence hardening

The local P0/P1 harness adds graph-attested action projection, a broker-only fixture effect path, receipt-chain validation, and signed launch/runtime terminal records. Raw client and IPC inputs cannot create an `ActionRequestV2`; the evaluator process resolves only an opaque proposal identity against an externally attested export. The red-team pass found two blocking gaps in the claimed evaluation-mode containment and failure-evidence guarantees. Watch for: **confirmed** direct OS reads can bypass the I/O guard, and **confirmed** a runtime failure can be attributed only to an earlier run when control-plane storage is reused. **Verdict**: NEEDS_CHANGES

## High-level view

The graph path gates the fixture effect behind a manifest, an evaluator-attested native export, a projection binding, and a signed grant. Valid enabled-fixture proposals are accepted only through that chain; raw V2 IPC, malformed IPC, and self-authored or tampered exports stop before dispatch.

The I/O containment layer is an in-process patch/audit mechanism, not a comprehensive interception boundary. **Confirmed:** it leaves ordinary OS metadata/directory reads and memory mappings of retained descriptors available during evaluation, so host data can reach evaluated code without a receipt or broker decision.

Runtime append failures transition the broker to impasse and normally publish independent signed evidence. **Confirmed:** that evidence is a single fixed file per supplied control-plane root rather than per run, so a prior record suppresses terminal evidence for a later run using the same root.

## Unintercepted OS reads and inherited descriptor mappings — confirmed

`intercept_legacy_process_io` patches a selected set of `os` and `Path` methods, while its audit hook maps only `open` and selected mutators to `deny_direct_io`. It does not patch or audit-deny `os.listdir` or `os.stat`; inside a live `evaluation_mode` context, the red-team probe listed the temporary run directory and read the source file size successfully. Those reads bypass both the reporter and the broker, so no denial receipt or terminal evidence describes them.

A retained file descriptor is likewise not an effective containment boundary. The active guard blocks `os.read`, but it does not intercept `mmap.mmap`; descriptors opened before activation successfully mapped and read `secret`, then mapped and changed it to `Xecret`, while the guard was active. This is a direct unreceipted host read-and-write channel. The documented local-custody limitation correctly says the mechanism is not an OS boundary, but the requested evaluation-mode property that no direct host I/O reaches an effect is not met. The existing direct-I/O test covers `open`, selected `Path` calls, `os.open`, `os.read`, and mutators, but not these successful read/write paths.

## Terminal runtime evidence can be retained from another run — confirmed

`RuntimeFailureRecord.record` returns any existing `runtime-failure.json` before constructing a new record, and `evaluation_mode` rejects that existing record only when its `run_id` and manifest hash match the candidate run. A later run sharing the control-plane root therefore starts despite an older record; if receipt-head publication then fails, the broker reaches impasse but `_record_runtime_failure` receives the older record instead of publishing evidence for the current run.

The red-team probe first wrote a signed record for `prior-run`, then launched an enabled-fixture run with the same runtime-record root and forced `ReceiptLog._replace` to fail. The client received `impasse`, while the sole signed terminal record still named `prior-run`, not the active run. This is a post-authority failure with neither an appendable receipt nor a terminal runtime record bound to the run that failed. The append-failure regression covers the empty-record case, but does not cover reuse of a control-plane root across distinct runs.

## Attested graph projection contains the enabled fixture path

The valid enabled-fixture proposal test completes only after the evaluator endpoint resolves its identity from the attested export, derives the canonical V2 request, and verifies the sealed binding before the broker invokes the deterministic simulator. The adversarial regressions also cover raw V2 IPC, malformed endpoint messages, export attestation tampering, receipt append failure, receipt-chain tampering, and supervisor stop. These checks do not mitigate the two issues above because both occur outside the canonical proposal path: one before broker authority and the other when the broker cannot durably acknowledge a failure.
