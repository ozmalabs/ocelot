# Signed evaluator outcome handoff into native P4 readiness

The local P4 runner stages a receipt-backed action, serializes an evaluator-signed outcome, and invokes a Rust worker that advances native state only through `advance_signed_evaluator_outcome`. The completion capability remains private, and the native state machine requires the signed outcome to match its action reservation, proposal, run, snapshot, sequence, and receipt digest. The valid Python-to-Rust transport completes, while forged signatures, altered bindings, wrong key IDs, and replayed outcomes are rejected in the exercised cases. **Watch for: confirmed — the Rust worker accepts its evaluator public key, key ID, authority ID, and lock digest from the untrusted request itself, so a caller can provide a fresh key and a matching signed outcome and obtain `complete`; the claimed lock-bound authority is not authoritative at the native boundary. confirmed — `run_local` also accepts an arbitrary launcher, and the passing integration test uses one to execute the staged worker directly rather than enforcing the Podman policy.**

**Verdict**: NEEDS_CHANGES

## High-level view

Python validates the local lock, produces a canonical signed outcome after the grant/action chain, and the Rust state machine refuses an unverified outcome. The opaque native capability and state-bound reservation checks only help after the worker has selected a trusted verifier identity.

**confirmed** — that identity is currently selected by the request being verified. A self-consistent attacker-controlled request can install its own Ed25519 public key, lock digest, and signed outcome, satisfying both signature and native graph bindings without referring to the preregistered lock.

**confirmed** — the Podman policy is fail-closed when used: it requires rootless Podman, a locally present digest-pinned image, and an offline locked-down command. The generic launcher parameter bypasses that route and can still receive `execution: complete`; locally, the required image is absent, so the genuine Podman route remains an impasse rather than demonstrated readiness.

## Canonical evaluator transport reaches the opaque native completion gate

`run_local` creates the action proposal only after emitting the release and replan receipts, asks the evaluator to grant and act, and serializes only `verified_native_outcome`. The worker reconstructs the bounded native trace to its action phase, then routes each outcome through `advance_signed_evaluator_outcome`, not the bare state-machine entry point. In Rust, the verifier requires canonical JSON and an Ed25519 signature before the crate-private adapter can mint `VerifiedActionOutcome`; native completion additionally checks the persisted proposal and reservation digests, run ID, snapshot, sequence, and outcome receipt parent.

The exercised transport is not only an in-library fixture. `evaluation/p4/tests/test_native_runtime_integration.py` builds and starts `p4_native_readiness_worker`, sends the evaluator’s real canonical output, and observes the native `complete` reply. It also exercises forged signatures, a validly signed altered reservation, a wrong key ID, and a repeated transport; the targeted Python suite passed 16 tests, and the Rust readiness and capability-boundary tests passed.

## The worker lets the transport choose its own verifier **confirmed**

`p4_native_readiness_worker.rs` deserializes `authority_id`, `key_id`, `authority_public_key`, and `lock_digest` from `Request` and immediately constructs `P4TrustedEvaluatorAuthority` from those values. The signed transport is required to repeat those same values, but the worker neither receives the signed local lock nor derives any of them from a preinstalled trusted source. This makes the equality checks self-referential rather than lock-bound.

The gap is exploitable in the worker as written. A fresh Ed25519 key paired with arbitrary valid digest strings for the request and a matching signed outcome returns `{"schema":"P4NativeReadinessReplyV1","status":"complete"}` with exit code 0. The graph binding checks still pass because the same request supplies its proposal, reservation, snapshot, and receipt digests while the worker stages a synthetic graph around them. **confirmed** — native completion is therefore authenticated only to an authority selected by the caller, not to the lock’s evaluator authority.

The repair needs an immutable trust anchor inside the actual execution boundary: mount a lock artifact authenticated by its existing lock signature, include it in the verified closure, derive the evaluator tuple from that parsed artifact, and compare the request fields against it before processing the outcome.

## The direct-worker test bypasses the Podman containment contract **confirmed**

`run_local` validates closure digests and asks its supplied `launcher` to preflight, but it does not require the supplied objects to be `P4PodmanLauncher` and `P4PodmanSpec`. The integration test supplies a local `LocalWorkerLauncher` whose `argv` returns the staged host binary directly; that path produces `execution: complete` without the rootless container, offline image, read-only filesystem, network isolation, or resource flags encoded by `P4PodmanLauncher`.

The direct-worker route still returns `local_readiness_only`, `no_go`, `adopted: false`, `promotion_authority: false`, and an exact rollback digest. It does not establish Podman-contained readiness. **confirmed** — Podman is rootless on this host, but the required `sha256:aaaa…` image is not locally inspectable; the genuine Podman preflight fails closed and `run_local` records an impasse. No image pull was attempted.
