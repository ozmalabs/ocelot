# Terminal evidence gap for P0-A startup denials

The receipt-log/manifest-mismatch repair now writes and independently verifies a signed `EvaluationLaunchFailureV1` record before rejecting, without appending an action receipt to the misbound chain. The focused startup probe confirms no context body runs, no `EvaluationActionClient` is yielded, and the record binds the verified and observed manifest hashes under the configured signing key. Evaluator-attested export admission, malformed retained-endpoint IPC denials, request-rebinding resistance, and the exclusion of legacy host dispatch remain covered by the adversarial tests. **Watch for: confirmed — `evaluation_mode` still has reachable startup rejections before and after the repaired mismatch branch that raise without either an action receipt or a signed launch-failure record.**

**Verdict**: NEEDS_CHANGES

## High-level view

The repaired mismatch branch treats the action receipt chain as unusable evidence and publishes a separate, independently verifiable control-plane record instead.

Admission still depends on an authority-attested native export before graph provenance is constructed. The retained pipe accepts opaque proposal identities only; raw V2-shaped or malformed traffic is denied through the broker, and evaluation routing does not construct the legacy host handlers.

The terminal-evidence policy is not yet uniform across launcher startup. Manifest verification and several policy/process-boundary checks occur outside either failure-record mechanism, so those rejected launches leave no durable evidence despite being reachable through `evaluation_mode`.

## Receipt-log mismatch now has independently verifiable terminal evidence

After manifest verification, `evaluation_mode` compares the supplied receipt log’s manifest hash with the verified manifest. On disagreement it creates `LaunchFailureRecord` on the control-plane path, signs a canonical `EvaluationLaunchFailureV1` document, atomically publishes it, and only then raises `ProtocolError` (`evaluation/p0a/entrypoint.py`, `evaluation/p0a/launch_failure.py`). The record carries the run ID, both manifest hashes, reason, timestamp, signer key ID, and signature; `read()` rejects a noncanonical, structurally invalid, or incorrectly signed record.

The dedicated mismatch probe passes: a valid manifest and export/attestation paired with a deliberately different receipt-log hash raise before the context body, leave the action log empty, and recover the signed terminal record through a freshly instantiated reader (`tests/evaluation/test_p0a_startup.py`). Writing an action receipt into the manifest-misbound chain would not be evidence for the verified run.

## Export custody, malformed IPC, and direct host dispatch remain constrained

A native export still needs `NativeGraphExportAttestationV1` verification against an authority key before the provenance resolver and broker are constructed. Missing, unknown-key, and digest-tampered attestations are converted into a signed `invalid_native_graph_export` impasse, including when a local fixture would otherwise enable the deterministic method (`evaluation/p0a/entrypoint.py`, `evaluation/p0a/provenance.py`, `tests/evaluation/test_graph_proposal_routing.py`).

The public client exposes only `submit_graph_proposal` and `observed_outcome`. Its process endpoint classifies malformed input and raw V2 bytes, routes the denial through the broker first, and returns an observed outcome backed by a signed receipt. The regression exercises both tuple-wrapped and bare raw V2 traffic, while the direct-I/O and tick tests show evaluation routing neither dispatches the registered host paths nor constructs/calls the legacy host-handler path (`tests/evaluation/test_graph_proposal_routing.py`, `tests/evaluation/test_legacy_io_blocking.py`).

## Startup evidence remains incomplete beyond the repaired mismatch branch

`evaluation_mode` invokes `manifest_verifier.verify()` before it can select or write either terminal-evidence path. Any malformed, expired, unauthorized, digest-mismatched, duplicate-run, or disallowed-method manifest therefore raises directly with no receipt or launch-failure record. After a manifest has verified and receipt binding has passed, the explicit `fixture_registry` policy rejection, supervisor run-ID mismatch, unavailable `fork` process context, and an endpoint start failure likewise raise without calling `_record_launch_failure` or `LaunchFailureRecord` (`evaluation/p0a/entrypoint.py`, `evaluation/p0a/manifest.py`). This is **confirmed** from the reachable control flow, not an inference from missing tests.

Those paths remain fail-closed with respect to action execution, but they do not meet the stated requirement that every reachable rejection leave receipt or signed launch-attestation evidence. A single launcher-level terminal-record strategy needs to cover pre-broker validation and process setup, with a schema that can safely describe failures before a manifest is verified; receipts should remain reserved for failures against a verified, correctly bound receipt chain.

## Exercised coverage

The four boundary regressions pass: mismatch terminal-record/no-client, attestation enforcement, raw-V2 retained-endpoint denial, and legacy host-handler exclusion. `python3 -m pytest -q tests/evaluation` also passes with **31 passed**, and the focused startup/routing/direct-I/O group passes with **17 passed**. **Not tested (confirmed):** a universal signed terminal record for manifest and later pre-broker startup failures, because the implementation does not currently create one.
