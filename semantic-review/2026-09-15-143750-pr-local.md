# Broker-routed graph action proposals

P1 adds a graph-proposal ingress to the evaluation launcher: graph attributes are canonically serialized, projected to a fixed V2 request shape, and sent to an entrypoint-owned `ActionBroker`. The launcher now builds that broker under a verified, empty-enablement P0 manifest, so the only catalogued simulator action is denied before any fixture handler can run; the daemon’s evaluation branch also avoids constructing the legacy host-handler registry and skips voice I/O. Denials and accepted V2 actions are intended to be signed receipts bound to a proposal ID, proposal digest, causal parent, request ID, nonce, grant, and sequence. Replay state is rebuilt from the verified receipt chain, while malformed input, method/grant substitution, and writer failure are denied or terminally impassed. Watch for: **confirmed** graph-source provenance is not actually verified by the entrypoint, and **confirmed** evaluated code can reach the broker’s direct ingress through the public client object, producing a V2 request without the graph receipt binding.  
**Verdict**: NEEDS_CHANGES

## High-level view

The normal route is narrow: untrusted proposal bytes select only `GraphCounterAdvanceV1`, the projector—not the graph—maps that kind to `simulator.counter.advance.v1`, and P0 evaluation mode owns a broker whose manifest enables no methods and whose registry is empty. A normal proposal therefore produces a signed V2 denial receipt rather than an effect, and the daemon switches away from the legacy host dispatcher when supplied an evaluation client.

The receipt chain validates writer signatures and persists V2 replay reservations, preserving the P0 controls that earlier work required. The projection nevertheless treats source provenance as an assertion whenever `evaluation_mode` constructs it, so a matching snapshot digest is enough to make arbitrary source digests appear in a signed graph receipt.

`EvaluationActionClient` exposes its `_broker` field to the same evaluated Python process. That process can call `submit_action` directly with a self-built V2 request and omit `graph_receipt_fields`; the current P0 default-deny configuration prevents an effect, but the graph-only ingress and provenance-bound-receipt invariant are bypassable rather than enforced.

## Provenance fields are self-asserted in the entrypoint route

**Confirmed.** `evaluation/p0a/entrypoint.py` constructs `GraphProposalProjector(broker)` without a `provenance_verifier`. In `evaluation/p0a/graph_proposals.py`, `_provenance_result` then accepts every structurally valid `source` tuple whose `graph_snapshot_digest` equals the manifest snapshot: it returns `None` when the verifier is absent. The other source fields—`origin_rule_digest` and `source_content_digest`—need only be strings beginning with `sha256:`; neither is resolved against graph state.

Consequently, an arbitrary graph-originated byte payload can choose invented source digests, retain the public snapshot digest, compute its own proposal digest, and receive an `ActionReceiptV2` whose signed `graph_proposal_digest` binds that self-asserted candidate. This does not grant authority in the current P0 run: the catalogued simulator method is rejected as `method_not_enabled`, no grant resolver is provided, and the broker registry is empty. It does defeat the stated provenance meaning of the receipt and would carry forward as an audit/trust error if enablement or grant issuance is introduced. The ambiguity test supplies a verifier directly to the projector, but it does not exercise the entrypoint that production evaluation uses.

## The evaluated client exposes a raw broker path

**Confirmed.** `EvaluationActionClient` in `evaluation/p0a/entrypoint.py` has a publicly readable `_broker: ActionBroker` field; Python naming convention does not prevent evaluated code from executing `run.action_client._broker.submit_action(...)`. `ActionBroker.submit_action` in `evaluation/p0a/broker.py` accepts both V1 and V2 wire requests directly, and V2 validation checks only the request’s self-contained `graph_provenance`. It does not require `graph_receipt_fields`, compare them to that provenance, or require that the projector called it.

A direct V2 submission therefore emits an ordinary V1 receipt when no `graph_receipt_fields` argument is supplied, even though its request schema says V2. It can also supply arbitrary receipt fields because that keyword argument is public. P0 still fails closed because `evaluation_mode` verifies an empty `enabled_methods` manifest and creates the broker with no fixture registry, so neither direct route reaches a legacy handler or simulator effect. The boundary is nevertheless not graph-proposal-only and does not guarantee the required graph-provenance binding for every V2 request. Keep the raw broker private to the launcher/projector, use an opaque client without it, and have the broker enforce projector-only V2 metadata.
