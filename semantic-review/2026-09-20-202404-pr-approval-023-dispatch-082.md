# Fixed-command IAM provisioning for APPROVAL-023/DISPATCH-082

This change adds a one-shot IAM/GCS executor for the separate GCS-only service account, custom role, exact conditional bucket grant, stale/broad grant removal, and Workload Identity token-creator binding. The implementation uses the absolute `/home/matt/google-cloud-sdk/bin/gcloud` path, a shell-free subprocess boundary, a captured raw/normalized prestate, exact poststate checks, and a hash-chained ledger with rollback/manual-review closure. The checked-in packet is scoped to `provision_gcs_only_iam_boundary` and keeps downstream operations disabled; the focused offline suite passes without cloud calls. Watch for: **confirmed** — exit code 1 is treated as “resource absent” for optional reads, so target-account or custom-role permission failures can be mistaken for a safe create-if-absent prestate; **confirmed** — the exported allowlist is mutable and can be extended to arbitrary gcloud argv; **confirmed** — an existing target account's policy version is not compared to the approved etag/fingerprint before mutation; **likely** — rollback can overwrite concurrent IAM changes and normal IAM version changes make the claimed exact-prestate rollback verification fail.

**Verdict**: NEEDS_CHANGES

## High-level view

The command boundary is narrow in its normal code path: every backend operation selects a literal argv and the subprocess disables shell and stdin, while the tests verify the absolute executable and reject an unknown command. **Confirmed**, that boundary is not closed at runtime because `ALLOWLIST` exposes the mutable dictionary used for authorization, and optional describe failures are not fail-closed.

The prestate loader verifies the sealed raw artifact, raw state digest, and normalized digest before any cloud read, and the poststate validator enforces the exact reviewed bucket grant and target token-creator binding. **Confirmed**, the existing-target path weakens that contract by checking only an empty binding list, not the approved target policy etag/fingerprint.

The executor reserves a ledger path with `O_EXCL`, performs the reviewed operations once, emits a success receipt, and disables downstream work. **Confirmed**, its rollback calls policy-binding helpers without comparing the current remote versions or a known post-mutation state first; **confirmed**, the packet self-validates its digest and identifiers without independently authenticating the parent approval or resolving the referenced source artifacts.

1. **Optional IAM reads fail open** — **confirmed**: `_run(..., optional=True)` maps every exit code 1 to `None`, so permission denied or another failed describe can look like `NOT_FOUND` and permit account/role creation. Accept only a positively identified `NOT_FOUND` response and fail closed for all other errors.

3. **Target policy version is not bound** — **confirmed**: `update_target_account_policy` requires an empty binding list but ignores the expected etag/fingerprint when the target account already exists. Compare the complete current policy, including its sole version field, with the approved prestate before adding the token-creator binding.
4. **Rollback is not concurrency-safe** — **confirmed**: bucket rollback checks only the bucket name and then issues unconditional remove/add commands; **likely**, concurrent changes can be overwritten and normal IAM etag changes make exact prestate digest verification fail. Re-observe and compare a versioned expected post-mutation state before restoring, use version-aware set-policy operations, and treat any drift as manual review without further writes.
5. **Child packet provenance is self-authenticated** — **confirmed**: `_load_packet` checks a digest recomputed from the supplied JSON and literal parent/dispatch/source strings, but does not verify an approval signature or load the referenced definition/live-observation artifacts. Require an independently authorized child approval, bind its signature/expiry to the exact packet and operation, and verify each source digest from its canonical path.

### Fixed gcloud boundary and optional resource discovery

`SubprocessGcloudRunner` does enforce the requested shell-free mechanics: it requires the absolute executable, rejects argv not equal to an allowlisted tuple, strips the credential-file override variables, uses `DEVNULL` stdin, and passes `shell=False` (`reviewed_iam_backend.py:170-196`). The authorization set is nevertheless mutable: `_ALLOWLIST` is a normal dictionary (`:137-161`) and `ALLOWLIST` exports that same object (`:503-504`). **Confirmed**, a caller can add a new tuple to `boundary.ALLOWLIST` and then pass it to `run`, bypassing the claimed closed command set. The fix is structural, not another test: keep an immutable tuple/frozenset of approved argv and make `allowlisted_argv` return copies without exposing the authorization object.

The more direct fail-open path is `_run` (`:216-221`). It returns `None` for every optional operation with return code 1. `describe_prestate` uses this mode for the target service account and custom role (`:275-286`), where the expected approved state is absent. **Confirmed**, a permission-denied, expired-authentication, or other exit-1 response can therefore be normalized as “absent”; the executor can proceed to `account_create` or `role_create` instead of stopping before mutation. Parse and require an explicit `NOT_FOUND` classification, or use a command/result contract that distinguishes not-found from all other failures.

### Raw/normalized prestate and target token-creator binding

The expected artifact path verifies the artifact digest, the raw `state_digest`, and the normalized digest before execution (`reviewed_iam_backend.py:358-369`); the shared normalizer requires exactly one non-empty etag or fingerprint for each present policy/role. The fixed backend also compares the complete bucket policy before its bucket mutation (`:300-312`), and `_exact_poststate` plus the shared validator require the exact private bucket and target policy poststate (`:371-385`).

The target-account update does not preserve the same versioned precondition. `update_target_account_policy` only checks that the current target policy exists and has no bindings (`:314-319`). **Confirmed**, for an already-existing target account, a policy whose bindings remain empty but whose etag/fingerprint changed is accepted; the subsequent add then writes against a state different from the approved prestate. Compare `current["target_account_policy"]` with `self._expected["target_account_policy"]` when the expected account exists, while retaining the post-create empty-policy check for the create-if-absent path.

### Ledger closure and rollback behavior

Rollback does not have an equivalent concurrency guard. `restore_target_account_policy` acts on whatever current policy contains the reviewed binding, while `restore_bucket_policy` checks only the bucket name before removing/adding bindings (`:323-340`); `restore_custom_role` updates or deletes without checking the current role version. **Confirmed**, if another actor changes an unrelated binding or role between the failed mutation and rollback, these helpers can write over that change. **Likely**, the final `validate_prestate` includes IAM etags/fingerprints, while each successful IAM policy/role write normally produces a new version, so a semantic restoration can still be reported as `rollback_failed_manual_review`. Rollback should first capture and compare a known versioned post-mutation state, then use a version-aware restore; if that state has drifted, stop and record manual review without issuing restore writes. The deliberate “never delete a created service account” behavior remains appropriate, but its unresolved account must be represented explicitly in the failure receipt.

### APPROVAL-023/DISPATCH-082 packet provenance

The packet carries the requested parent approval, dispatch, operation, attempt, source digest, and disabled-downstream fields (`approval-023-dispatch-082-iam-child-packet-v1.json:2-34`), and the loader enforces those literal values (`reviewed_iam_backend.py:99-124`). **Confirmed**, it does not authenticate them: anyone able to provide a packet path can construct the same fields, recompute `artifact_digest`, and satisfy the loader. **Confirmed**, it does not open the IAM definition, GCS definition, or live-observation artifact to verify that the supplied source digests still identify those exact files. The backend constants keep its actual cloud target narrow, but that does not make the child approval authoritative. Bind application to an independently authorized child artifact/signature and verify the source files and parent approval rather than treating self-computed JSON as approval provenance.

### Test boundary

`python3 -m pytest -q services/p5_r0_evaluator/tests/test_reviewed_iam_backend.py` passes with 12 tests. Those tests are useful for pure digest, sequencing, receipt, rollback-status, and retry behavior, but they use a fake runner/backend. **Confirmed**, they do not test the failure classifications or remote-version races above. No cloud mutation was executed during this review.
