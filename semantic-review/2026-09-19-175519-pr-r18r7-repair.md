### Update output is not state evidence

`_run_status` captures update process output only as an implementation detail and makes the decision solely from the exit code, so empty or non-JSON successful update output is accepted while nonzero exit status is blocked. The update result is never passed to a state parser. **confirmed**

The only JSON parsing of command stdout is in `_run_json`, which is used at describe call sites. The post-mutation verification path calls a fresh describe before `validate_poststate`; it does not infer state from the update response. **confirmed**

### Fresh describes close poststate and rollback verification

After the fixed update, the handler obtains a new describe response, canonicalizes it, and requires exact approved mapping/condition and digest relationships before emitting `operation_verified`. A mismatch enters the failed-closed path instead of being accepted as a successful update. **confirmed**

Rollback uses the same fixed update runner with the current observed etag availability, then performs another describe and requires the restored configuration digest to equal the expected prestate configuration digest. A changed volatile fingerprint is tolerated only when the canonical configuration is restored; rollback failure remains `rollback_failed_manual_review`. **confirmed**

### Bounded errors preserve manual review and no-retry

Failure records contain the exception type plus a stable phase classification, while rollback records contain only a stable rollback-substep classification and a redacted marker. Raw command output and detailed exception text are not written to terminal ledger events; ledger-write uncertainty produces a recovery marker and a manual-review result. **confirmed**

The R18R7 artifact sets `mutation_not_proven`, `desired_poststate_not_observed`, `rollback_not_verified`, `no_retry`, and `downstream_disabled` to true. Those claims are appropriately conservative for the prior failed attempt and do not authorize a retry. **confirmed**
