# Self-custodied attested Track A runner

The change adds a protocol-only `TrackARunner` for the narrow self-custodied Track A diagnostic: provision the generated package, activate attested capabilities, rehydrate inputs, obtain timing-derived input, execute one `cold_reset` task plus one `illegal_action` control, verify receipts, persist/read back a result seal, and request a KMS signature. The six adapter-backed tests cover the happy-path ordering and several fail-closed seams, and the CLI deliberately returns a typed blocker when no verifier-owned adapter exists. **Watch for:** **confirmed** the `issue_time_seed` contract can derive seed material before the runner verifies timing; **confirmed** local KMS clients and self-declared supervisor adapters can satisfy the success path; **confirmed** receipt validation trusts a caller-supplied chain digest; **confirmed** the final signed binding omits KMS authority/key-version metadata; **confirmed** no real Confidential Space, FreeTSA, native supervisor, durable input, or non-exportable KMS evidence exists.

**Verdict**: NEEDS_CHANGES

## High-level view

The orchestration has the intended broad shape and preserves the explicit one-case/one-control MVP, but **confirmed** its timing API permits pre-verification seed construction. The runner recomputes the seed after verification, yet `issue_time_seed()` has already been allowed to return seed material, so the ordering is not enforceable at the interface boundary.

The attestation binding and exact `KMSEd25519Signer` type are stronger than generic callbacks, but **confirmed** the KMS constructor accepts an arbitrary injected client and the supervisor accepts duck-typed `trusted`/`independent` booleans plus validators. The included success fixture therefore produces a signed-looking result from a process-local key and self-digested worker evidence.

**Confirmed** receipt checking covers task/control presence and a digest of the supplied records, not the append-only chain semantics or the relationship between `chain_digest` and those records. **Confirmed** the final binding carries the result seal but does not carry the signer authority/key version, while `TrackAResult.as_dict()` omits the timing/input/chain commitments needed to interpret the signed diagnostic output.

The CLI and adapter boundary correctly stop without external capabilities, so this is **confirmed** repository-only readiness rather than a Track A execution. Track B hardening and P5-E1/E2 remain separate; they cannot substitute for the missing signed Track A evidence.

<summary>Issues (7)</summary>

1. **Pre-verification seed construction** — `issue_time_seed()` can build and return seed material before timing verification. Split timing-record acquisition from post-verification seed derivation and build the input only after the verifier succeeds.
2. **Local KMS and supervisor promotion** — An injected process-local KMS client and duck-typed supervisor booleans/validators can produce a signed-looking result. Require opaque verifier-owned KMS/supervisor adapters with non-exportable key and authenticated evidence boundaries.
3. **Unverified receipt chain** — The runner checks only supplied record shape/digest and task/control presence, not chain links, sequencing, required closure events, or recomputed `chain_digest`. Apply a canonical append-only receipt validator before signing.
4. **Incomplete signer/result binding** — The signed final binding omits KMS authority/key-version metadata, and the returned result omits timing/input/chain commitments. Bind the authority and expose the permitted redacted commitments in the result schema.
5. **Task replay identity** — Task and control envelopes are not compared with the active run ID from `start()`. Require active-run equality through envelopes, outcomes, evidence, receipts, and the final binding.
6. **Failure-chain closure** — Post-start cleanup checks only a rollback status/digest and does not require a verified impasse/rollback/close chain or persisted impasse seal. Make failure receipts and sealing part of the rollback contract.
7. **Missing real execution prerequisites** — No verifier-owned Confidential Space, durable post-attestation rehydration, live FreeTSA, authenticated native supervisor, or non-exportable KMS execution evidence exists. Supply those exact boundaries before attempting Track A; do not substitute Track B or P5-E1/E2 work.

<summary>Details</summary>

### Timing-before-seed is not enforced by the execution contract

**Confirmed** `TrackARunner.run()` calls `capabilities.execution.issue_time_seed(...)` and only afterward calls `_validate_timing(...)`. The `TrackAExecution` protocol names that method as issuing a seed, and the test implementation actually calls `derive_time_seed()` inside it before returning the timing record. The runner later recomputes the seed after verification, but that does not undo the pre-verification input construction permitted by the API.

This violates the required order in which the V3 FreeTSA record is verified before any seed or time-derived input is built. Replace the method with a timing-record acquisition operation that returns no seed or input material; verify the record first; then call the input builder exactly once and bind only the resulting `timing_record_digest`, `input_seed_digest`, and `input_digest`.

### Local KMS and supervisor seams can promote caller evidence

**Confirmed** the runner requires `KMSEd25519Signer`, but `KMSEd25519Signer` accepts any caller-supplied `client` implementing `get_public_key` and `asymmetric_sign`. The Track A success test supplies `_KMSClient`, which holds an `Ed25519PrivateKey` locally, and the runner returns `signed_diagnostic`. This is not a non-exportable KMS boundary; a local client can satisfy the same type check and authority metadata checks.

**Confirmed** RS-050 authentication similarly relies on caller-visible `trusted=True`, `independent=True`, `validate_execution_evidence`, and `validate_bounded_compute_claim`. The success fixture supplies those flags and methods, while the worker supplies self-digested supervisor evidence. The protocol validator explicitly reports shape validity separately from authentication, but the Track A runner has no opaque/attestation-bound supervisor capability that prevents a local fake from reaching the promoted path. The action is to require verifier-owned opaque KMS and supervisor adapters whose identity, key/version, transport binding, and evidence authentication are established outside caller-controlled mappings; reject process-local clients, booleans, and self-digested observations.

### Receipt verification does not verify the receipt chain

**Confirmed** `_validate_receipts()` verifies the closed top-level shape, `records_digest`, allowed record kinds, and presence of one task and one control record. It does not recompute `chain_digest`, validate record sequencing or previous-digest links, require the applicable start/timing/result/rollback/close events, or establish that the records form an append-only chain. The success fixture sets `chain_digest` to an unrelated digest and still reaches signing.

The runner needs the canonical receipt-chain validator at this boundary, with run/sequence/event/previous-digest closure and final-chain recomputation. A caller-provided `status=verified` or digest of an arbitrary record list must remain non-promotable.

### Final KMS binding is incomplete and the public result drops evidence commitments

**Confirmed** the final binding includes `result_seal`, `result_seal_digest`, and `result_digest`, and signing occurs after persisted seal read-back and verification. However, the binding does not include the signer authority metadata or KMS key version; `_validate_authority()` validates those values and then discards its return value. The emitted `TrackAResult` also does not serialize the attestation binding digest, timing-record digest, input-seed digest, input digest, or receipt-chain digest, even though the internal `signed` mapping contains some of them. A consumer cannot reconstruct which KMS authority signed the result or inspect the required timing/input/chain commitments from the returned result object.

Bind the closed authority/key-version commitment into the signed final binding and expose the permitted redacted commitments in the public result schema. Keep raw tokens, private truth, and proof bytes out of that output.

### Task identity and failure closure need stronger binding

**Confirmed** `_validate_task()` checks that the envelope has a digest-shaped `run_id`, but it receives no expected run ID and never compares the task/control envelope to the run returned by `execution.start()`. `_validate_execution()` binds supervisor invocations to the envelope's value rather than the active run. A replayed or mismatched envelope can therefore satisfy the local checks if its accompanying evidence repeats that mismatched identity. Pass the active run ID into task validation and require both task and control envelopes, receipts, outcomes, and evidence to bind to it.

**Likely** failure cleanup only checks that `execution.rollback()` returns `status=exact` and a rollback digest. The failure path does not require the rollback to append a verified impasse/rollback/close chain, persist an impasse seal, or make those records available in the typed blocker result. Require a closed failure receipt/seal contract for post-start failures; otherwise return only a redacted blocker without implying that rollback evidence is complete.

### The external execution frontier is still blocked

**Confirmed** no concrete verifier-owned `TrackAAdapter` implementation or production CLI factory exists. The CLI intentionally returns `P5R0TrackAResultV1` with `status=blocked`, `stage=attestation`, and `reason_code=verifier_owned_adapter_required`. The repository tests use local fakes and do not establish the real evidence classes required by APPROVAL-015/REVIEW-065 or the P5 requirements.

The exact real prerequisites are: (1) a master-authorized immutable generated package and explicit MVP lock/selection, provisioned before launch to an approved durable path; (2) one real Confidential Space launch with Google-signed attestation bound to the exact image, project/zone, AMD SEV/Secure Boot/vTPM posture, WIP/IAM policy, lock, and generated-input commitments, with capabilities activated only after verification; (3) post-attestation durable input read, digest verification, and fresh-process private-store rehydration; (4) a live pinned FreeTSA RFC-3161 timing verifier and durable timing ledger, consumed before seed derivation; (5) the exact native image/crun/seccomp/argv/no-network/no-pull/resource closure and a separately authenticated supervisor producing lifecycle, OOM/deadline, exit, and cleanup evidence; (6) a non-exportable KMS Ed25519 authority through the approved signed boundary, with closed authority/key-version/public-key binding and a real final signature after persisted seal verification; and (7) durable canonical receipt and seal storage. No external task provider is needed: the project generator owns the selected task/control set. Track B, P5-E1/E2, and upstream P0-P4 gates are explicitly separate and remain neither executed nor waived by this change.
