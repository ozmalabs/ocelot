## High-level view

The approval and capability paths now distinguish verifier-issued runtime objects from caller-provided data. Exact request, parent approval, operation scope, expiry, provider/image/account/destination, and immutable issuance snapshots are checked before bootstrap can cross into adapter activation.

Credential bootstrap uses a capability-only adapter activation: launcher attestation, STS exchange, and short-lived service-account credential derivation can occur, but the returned `Capabilities` contains fail-closed placeholders and is never handed to the evaluator service factory. The adapter’s attestation binding remains the source of provenance, rather than a caller-supplied claims mapping or boolean.

This closes the repository-side REVIEW-060 defects but does not create external authority. **Confirmed:** the P5 runsheet still records `NO_GO`, with signed-environment remediation in progress and IAM/GCS/KMS/diagnostic gates blocked until fresh live observations and a new child approval are available.

### Child approval and capability evidence are no longer self-digested

`VerifiedCredentialChildApproval` in `services/p5_r0_evaluator/deploy/signed_environment_credentials.py` can only be constructed with the module-private seal, and validation additionally requires exact object identity in the verifier registry plus an immutable field snapshot. Its request digest, fixed operation scope, parent `APPROVAL-013`, verifier identity, issuance window, and closed approval digest are checked before activation. `VerifiedCapabilityBinding` uses the same pattern in `signed_environment_process.py`, retaining the canonical serialized snapshot and original binding digest; a caller mapping, copied lookalike, mutated object, or recomputed seal fails registration before the executor or adapter is reached. This is **confirmed** by the adversarial approval, mapping, mutation, reseal, and source-mismatch tests.

### Credential-only activation preserves the adapter contract without evaluator reachability

`CredentialOnlyCapabilityFactory.build()` accepts only an explicit STS bearer token, derives a source-bounded short-lived credential, records a redacted receipt, and returns the existing `Capabilities` dataclass. Its store, signer, and timing-attestor fields are fail-closed placeholders rather than GCS/KMS/evaluator clients. `ConfidentialSpaceAdapter.activate_attested_capabilities()` attaches the verifier-issued attestation binding and does not call `service_factory`; `bootstrap_credentials()` requires this exact factory type and invokes the capability-only path with `service=False`. The focused contract test confirms the service factory is not called and that credential expiry remains bounded.

### Adapter provenance remains verifier-owned

The adapter’s `AttestationGate` still owns nonce generation, launcher-token retrieval, JWT verification, issuer/audience/time checks, fixed Confidential Space claims, and STS exchange. The adapter creates the sealed `VerifiedAttestationBinding`; `validate_attested_activation()` accepts only that registered binding and the adapter’s closed startup evidence, including the current policy, claim-path, provider, image, project, zone, TEE, Secure Boot, debug, workload, and short-lived federation bindings. `bootstrap_credentials()` validates the exact request, KMS binding, registered capability snapshot, registered child approval, and current adapter activation before emitting a redacted receipt. No cloud, IAM, KMS, GCS, credential-export, or diagnostic operation is present in this module; **confirmed** the full service suite contains no production call site that bypasses the reviewed bootstrap path to invoke capability-only activation.
