# Canonical graph proposal binding at the evaluator boundary

P1 moves graph-action evaluation behind an evaluator-process endpoint: evaluated code submits only a proposal ID, while the endpoint resolves the canonical export record, projects `ActionRequestV2`, and seals the exact projected bytes into the broker binding. The P0-A empty manifest denies the valid native proposal before grant resolution, while the explicit local fixture accepts the exported `steps=1` proposal and records its canonical request. The public API and even a deliberately unwrapped client connection cannot carry a recomputed `steps=2` V2 request, and durable receipts reserve proposal identities across restart. **Watch for: confirmed — a self-consistent export is treated as native evidence without any signature, attestation, or independently held custody proof; confirmed — malformed raw messages sent to the evaluator pipe, and invalid export data rejected before broker construction, receive no receipt.**

**Verdict**: NEEDS_CHANGES

## High-level view

The evaluated side has a narrow protocol: only a string identity crosses the process pipe. The evaluator alone holds the export, projector, grant resolver, and broker, and the binding compares the entire canonical projected request. This correctly prevents the demonstrated `steps=1` evidence from being rebound to a caller-computed `steps=2` request.

The boundary authenticates the *internal consistency* of an export, not its origin. `export_digest` is an unkeyed object hash, so whoever supplies `native_graph_export` can construct a new, internally consistent candidate and have it projected and accepted in the enabled fixture. The current claim that acceptance requires a verified native proposal therefore depends entirely on out-of-code custody of the launcher argument.

Normal proposal-path denials, stale evidence, raw public V2 submission, and replay have broker receipts; legacy dispatch remains excluded. But malformed messages rejected by the process endpoint and malformed or duplicate exports rejected during startup bypass the broker’s receipt writer, so the requested all-failures receipt invariant does not hold at the full trust boundary.

## Native-export origin is assumed rather than verified

The custody gap is **confirmed**. `NativeGraphProvenanceVerifier` validates the export’s schema, bindings, duplicate IDs, and `object_hash(export, "export_digest")`, but no signature, key lookup, trusted capture handle, or attestation is present in the export or verified by `evaluation_mode` (`evaluation/p0a/provenance.py`, `evaluation/p0a/entrypoint.py`). A caller that controls `native_graph_export` can recompute both hashes.

A controlled enabled-fixture probe supplied a newly created, internally consistent export containing `steps=2`, with the normal fixture grant resolver. It returned `accepted`; the receipt’s normalized-argument hash matched `steps=2` and its graph proposal digest matched the supplied candidate. The canonical binding worked—the request was faithfully derived from that export—but native provenance was assumed rather than established.

For a trusted export, substitution protection is **confirmed**: only an ID crosses the public client, raw V2 bytes are rejected by the endpoint, and `GraphRequestBinding` compares the full canonical request. The enabled regression reaches acceptance only for exported `steps=1`; a recomputed `steps=2` request cannot reach broker dispatch.

## Boundary rejections escape the receipt chain

The raw-pipe gap is **confirmed**. `_projector_endpoint` answers malformed messages with `("invalid",)` without calling `GraphProposalProjector` or `ActionBroker` (`evaluation/p0a/entrypoint.py`). Sending `("submit", canonical_bytes({"schema": "ActionRequestV2"}))` returned exactly `("invalid",)` and left `ReceiptLog.last_receipt` as `None`. It did not dispatch to the simulator or a legacy handler, but it violates the requested receipt invariant.

The startup gap is also **confirmed**. `evaluation_mode` constructs `NativeGraphProvenanceVerifier` before `ActionBroker`; inconsistent/fabricated records and duplicate identities therefore raise during export validation, before a receipt writer exists (`evaluation/p0a/entrypoint.py`, `evaluation/p0a/provenance.py`). Stale evidence is receipted because the run starts and identity lookup returns `stale_graph_provenance` through the broker.

## Exercised protections and coverage boundary

`pytest -q tests/evaluation` passed all 28 tests. The suite demonstrates P0 denial, method/grant and request-argument substitution rejection, stale and duplicate provenance handling, replay across restart, broker V2 bypass rejection, and legacy-handler/direct-I/O exclusion. **Not tested:** a cryptographically authenticated or independently captured native export, nor receipt persistence for malformed process messages or rejected startup exports; both gaps are reproduced above.
