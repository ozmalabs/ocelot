# Native graph provenance binding for evaluation actions

The evaluation path accepts graph proposals only after matching them to evaluator-captured native evidence, projects those proposals to V2 broker requests, and leaves P0-A with no enabled handlers. Fabricated or absent evidence, stale or ambiguous exports, replayed proposals, and raw V2 calls through `submit_action` all deny with durable receipts; the evaluation tests also show that the daemon branch avoids legacy host handlers. A native proposal with a valid binding reaches the broker and is default-denied as `method_not_enabled`, with its graph provenance recorded in the receipt. Watch for: **confirmed** — the verifier can bind an arbitrary caller-created V2 request to otherwise valid native evidence, because it does not compare the request’s semantic fields with the canonical proposal; an evaluation client can reach that verifier and broker by unwrapping its stored bound method. **Verdict**: NEEDS_CHANGES

## High-level view

The launcher owns a native evidence export and supplies a verifier to the graph projector. That verifier correctly rejects self-asserted provenance when the evidence identity, source, causal parent, or logical time does not match the captured export, while the broker makes receipt issuance terminal on failure.

P0-A remains a genuine authorization boundary: a correctly bound native proposal reaches the broker but is denied before handler dispatch because the enabled-method set is empty. Raw V2 submission through the ordinary broker API likewise produces `verified_graph_proposal_required` and leaves the simulated host state unchanged.

The capability boundary is incomplete. A verifier-issued binding is meant to certify projector output, but its public binding operation accepts an arbitrary V2 request once the caller has a matching native proposal; the evaluation client’s retained bound method exposes the projector, verifier, and broker through normal Python introspection. This lets a raw caller obtain a receipt that treats altered request content as verified graph provenance, even though P0-A prevents the altered request from reaching a handler today.

## Adversarial provenance and P0-A checks

**Confirmed**: captured native evidence rejects fabricated, absent, stale, and ambiguous provenance with denial receipts, and V2 receipt recovery prevents replay after restart. A native proposal whose evidence matches reaches `submit_verified_graph_request` and records the proposal ID, digest, causal parent, request ID, nonce digest, and sequence. P0-A then returns `method_not_enabled` before grant resolution or handler dispatch.

**Confirmed**: a raw V2 call to `submit_action` returns `verified_graph_proposal_required` with a receipt and leaves the host simulator state at zero. The evaluation daemon test also asserts that neither the legacy host-handler factory nor dispatcher is constructed or called.

## Verified binding does not bind the proposal’s projected semantics

The provenance verifier’s `bind_request` checks V2 identity, run ID, request ID/hash, and the three provenance fields, but it does not derive or compare the method, arguments, requested budget, input snapshot, timestamps, nonce, or input references from the verified proposal. **Confirmed**: after calling `verify` on a native `steps: 1` proposal, I constructed a projected V2 request with `args: {"steps": 2}`, recomputed `request_hash`, called `bind_request`, and submitted it through `submit_verified_graph_request`. The broker accepted the binding and emitted a V2 receipt carrying the native proposal digest and altered request hash; P0-A subsequently denied it as `method_not_enabled`, so no handler ran.

The client’s double-underscore fields are only name-mangled, not a capability boundary: `object.__getattribute__(client, "_EvaluationActionClient__submit").__self__` yields the projector, which retains `_provenance_verifier` and `_broker`. **Confirmed**: that route lets evaluation code create the mismatched binding above. Although it invokes the verifier rather than bypassing its function entirely, it bypasses the projector’s canonical derivation and causes a raw request to be represented as verified native provenance. This becomes an effect-authority escalation if any evaluation manifest later enables a method.
