# FD-bound IAM transport and signed ledger-root reissuance for DISPATCH-086

DISPATCH-086 closes the two main DISPATCH-085 implementation gaps at the transport boundary: issuance hashes the actual bounded inherited-FD bytes, and the runner rechecks those bytes immediately before every gcloud call. It also adds signed transport-artifact rehydration and a signed IAM ledger-root envelope, with downstream ledger-path consumers requiring explicit packet, prestate, evidence, and trusted-verifier inputs. The repository-only tests cover FD tampering, unsigned roots, packet mismatch, and same-process stale-FD reuse. Watch for: **confirmed** — the ledger-root verifier can be constructed from the artifact’s public key, so the signature is cryptographically checked but not anchored to a pre-trusted authority; **confirmed** — the signed root is created before the terminal event and binds the poststate event rather than the final ledger head; **confirmed** — restart reissuance checks digest equality but has no signed freshness/generation proof for the credential source.

**Verdict**: NEEDS_CHANGES

## High-level view

The transport effect boundary checks the actual descriptor bytes and keeps credential material out of argv, environment, and the transport artifact; production still needs real verifier-issued inputs rather than repository fixtures.

The ledger reload path now has canonical-chain and signature checks with consumer packet/prestate/evidence bindings, but signer trust is caller-selected and the signed root omits the terminal event digest.

Rehydration rejects same-process descriptor reuse, but **confirmed** restart freshness is absent because a new process can reopen stale bytes with no signed issuance, generation, or one-time-use proof.

<summary>Details</summary>

### Actual FD bytes are checked at issuance and effect

**confirmed** — `issue_verifier_credential_transport` reads bounded bytes from the supplied descriptor, derives the digest from that read, and rejects a caller-supplied digest that differs. `SubprocessGcloudRunner.run` calls `_verify_live_transport` immediately before `subprocess.run`; that path re-reads the descriptor, compares the bytes to the signed digest, and checks descriptor identity before passing the same descriptor with `pass_fds`. The tamper test changes the file after issuance and confirms gcloud is not invoked.

**confirmed** — no credential bytes are placed in the reviewed subprocess argv or environment. The argv adds only `--access-token-file=/proc/self/fd/<fd>`, and the environment is the fixed `PATH`, `LANG`, and `LC_ALL` mapping. `build_signed_credential_transport_artifact` serializes signed metadata and digests rather than the payload bytes; the targeted artifact test asserts the token is absent. No logging call in this boundary emits the token. The remaining requirement is external: the injected descriptor, signed evidence, and verifier key must come from the approved signed environment rather than the module’s test signer.

### Ledger-root key trust is self-supplied

**confirmed** — `VerifiedIAMLedgerRootVerifier` is directly constructible from any base64 public key, and `_verify_ledger_root` accepts that object as the trust authority after checking only that the envelope key equals `trusted_verifier.public_key`. A caller can therefore read the embedded `public_key`, construct a verifier for it, and successfully reload a ledger signed by that same key; there is no sealed/registered capability or fixed authority binding comparable to the child-approval verifier.

The action is to make ledger-root verification consume a pre-established verifier capability or pinned authority/key digest, and reject an embedded key unless it exactly matches that external trust root. The signer used by `ReviewedFixedCommandExecutor` also needs to be the corresponding external verifier authority; the current fallback to `_TEST_VERIFIER_KEY` is a repository fixture, not production trust.

### The signed root does not cover the terminal ledger event

**confirmed** — the executor calls `issue_signed_iam_ledger_root` with `[started, verified_pre, verified, {}]` before appending `run_stopped`. `_ledger_root_payload` sets its `ledger_head_digest` to `poststate_verified.event_digest` and ignores the stopped record. Reload validates the four-event chain and terminal fields, but never requires the root’s claimed head to equal `run_stopped.event_digest`. Consequently, the trusted signature covers the prestate/poststate portion but not the final event that records terminal status, receipt repetition, and root placement.

The action is to construct the root over the complete finalized chain, or make the root explicitly bind the terminal event digest and verify that equality during reload. The root field must represent the actual persisted ledger head, not the poststate event used as an input to root construction.

### Restart reissuance proves bytes, not fresh credentials

**confirmed** — `load_signed_credential_transport_artifact` asks an arbitrary `signed_environment_source` for a descriptor and checks its bytes against the artifact’s already signed `transport_bytes_digest`. Its stale-FD defense compares descriptor numbers and identities only against the in-process transport registry. After restart that registry is empty; reopening an old credential file under a new descriptor, or returning stale credential bytes through the source, passes the same digest/signature checks until expiry. The existing test exercises same-process reuse of the registered descriptor, not this restart case.

The action is to bind the artifact to a verifier-issued one-time reissuance nonce/generation and an external issuance record, require the signed environment to attest that fresh issuance, and consume/invalidate that record before effectful use. Digest equality alone cannot distinguish a newly issued credential from a replayed credential with identical bytes.

### Repository validation and P5 gating remain local-only

The targeted independent run passed 41 tests across `test_dispatch086_hardening.py`, `test_reviewed_iam_backend.py`, and `test_iam_predecessor.py`. These tests establish the implemented positive paths and the listed same-process/adversarial cases, but do not establish pinned root authority, terminal-root binding, or post-restart stale-credential rejection. No cloud, IAM, KMS, GCS, VM, Confidential Space, task, credential issuance, retry, or external mutation was performed.

The P5 handoff and runsheet still require a master-authorized exact packet/attempt, fresh live IAM prestate, a real signed-environment credential/evidence chain, trusted authority and child approval, and a verified poststate before IAM can feed downstream work. P5 remains blocked beyond this repository review by real Confidential Space attestation, WIF/IAM/KMS bindings, durable input delivery and rehydration, timing-first evidence, authenticated native/supervisor evidence, canonical receipts, and a real KMS-signed final result; upstream P0–P4 trusted-release gates are also not passed.
