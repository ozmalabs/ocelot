# Fail-closed RS-069 operation-2 WIP provider handler

This change adds a dedicated operation-2 validation and execution boundary for replacing the WIP provider's incomplete claim mapping with the reviewed mapping and condition. It binds the candidate image, provider resource, claim values, desired-state digests, prestate etag, fixed absolute `gcloud` argv, poststate verification, rollback, and a hash-chained ledger while keeping later operations disabled. The new tests cover pure provider, claim, mapping, prestate, poststate, scope, and command-shape checks without invoking cloud tooling. Watch for: **confirmed** attestation evidence is not cryptographically bound to the claims, **confirmed** approval is accepted as caller-supplied booleans rather than a verified fresh approval record, and **likely** rollback verification cannot match the original state digest after an etag change.

**Verdict**: NEEDS_CHANGES

## High-level view

The handler has the intended narrow topology—an absolute provider describe, one fixed update, a second describe, and a same-runner rollback—but two trust-boundary inputs are still self-asserted. **Confirmed** the claim record checks only that `evidence_digest` has digest syntax, and **confirmed** the fresh-review gate accepts a matching in-memory dictionary plus the string `master_reviewed`; neither proves that an authorized reviewer attested the exact claims and scope.

**Confirmed** the prestate comparison checks only three fields from the externally supplied expected object, even though rollback later trusts that object's mapping and condition. **Likely** the rollback's full state digest includes the provider fingerprint, so a normal post-update etag change makes an otherwise correct restoration fail verification.

The command construction is absolute and shell-free, and downstream operations remain explicitly disabled. **Confirmed** the subprocess call does not set stdin to `DEVNULL`, and **confirmed** the tests stop at pure validators and command construction rather than exercising the update failure, rollback, ledger chain, or redaction behavior.

<summary>Details</summary>

### Attestation record is structurally exact but not evidentiary

`_validate_claim_record` requires a closed record, an expected schema/source, and exact normalized values for the candidate digest, project, zone, hardware, TEE, secure boot, workload, smoke flag, audience, issuer, and subject prefix. However, at line 162 it only applies `_is_digest` to `record["evidence_digest"]`; it never compares that digest with canonical evidence or verifies an authenticated attestation boundary. The test at `test_rs069r18_operation_2.py:89-107` deliberately uses `sha256:` followed by 64 ones and still passes, which demonstrates the gap rather than protecting it.

**Blocking, confirmed.** A caller can construct the exact-looking claim dictionary from public constants, choose any syntactically valid evidence digest, and obtain the returned `zone_digest`. That digest is then accepted into the approval binding and ledger. The handler needs a canonical evidence payload or independently verified record digest, with the trusted source/signature and candidate image bound before the normalized claims are accepted.

### Fresh review is represented by an untrusted call argument

The request validator keeps the checked-in R17 packet blocked and prevents reuse of the operation-1 scope. The new gate then requires `review_state` to equal a literal string and requires an approval mapping with the expected ID, booleans, scope, and computed bindings (`rs069r18_operation_2.py:220-250`). Those checks establish shape and equality but not provenance: a caller can supply the string and dictionary itself, including a matching digest computed locally.

**Blocking, confirmed.** The handler can cross its mutation gate without reading a canonical R18 approval artifact, checking an approval-record digest, or verifying that the reviewer approved the exact request version. The approval input should be closed and loaded from the reviewed source, with a record digest bound to the request scope and all immutable bindings; a signed or otherwise trusted master-review result should be required rather than a free-form `review_state` flag.

### Prestate data is not fully authenticated and rollback identity is unstable

`validate_prestate` (`rs069r18_operation_2.py:285-291`) compares only `provider_resource`, `fingerprint`, and `state_digest`. It does not require the expected object to have the canonical state schema, mapping, condition, project/pool/location fields, or digests that recompute to `state_digest`. Yet `build_rollback_command` later uses the expected object's mapping and condition as the rollback payload. An expected object can therefore pass the prestate gate with a matching observed digest while carrying different rollback content, or can omit rollback content and force a manual-review failure only after mutation.

**Blocking, confirmed.** Canonicalize and validate the expected prestate itself, recompute all component digests and the complete state digest, and compare the complete canonical object to the observed state before updating. The rollback payload must come only from that verified captured state, not from an independently supplied partially checked object.

The state digest produced by `_state_from_gcloud` includes `fingerprint` (`rs069r18_operation_2.py:274-281`). The rollback path updates with the current fingerprint and then requires `restored["state_digest"] == expected_prestate["state_digest"]` (`rs069r18_operation_2.py:462-464`). **Blocking, likely.** Provider etags/fingerprints normally change after a successful update, including an update that restores the same mapping and condition; the restored semantic configuration can therefore be correct while this check reports `rollback_failed_manual_review`. Split the stable configuration digest from the observed concurrency fingerprint, use the current fingerprint only as the rollback precondition, and verify provider identity, mapping, condition, and stable digest after rollback. Add a test where the rollback describe returns the original mapping/condition with a new fingerprint.

### The fixed runner still inherits stdin, and execution behavior is untested

`_run_json` documents that no stdin is accepted but calls `subprocess.run(..., input=None, ...)` (`rs069r18_operation_2.py:370-379`); `None` means no explicit input is supplied, not that the child receives `DEVNULL`. A parent process with open stdin remains observable by the child.

**High, confirmed.** Set `stdin=subprocess.DEVNULL` explicitly and assert it in a monkeypatched subprocess test. The current command-shape test only inspects `_describe_command`; it never verifies the execution boundary.

The ten new tests all target pure helpers. There is no test of `execute_operation_2`, the update failure path, a poststate mismatch followed by rollback, a rollback failure, the append-only chain, redaction of captured output, or the fact that later operations remain absent from every terminal event. **Medium, confirmed.** Add offline tests that monkeypatch `_run_json` with a deterministic describe/update sequence and use a temporary ledger. They should assert prestate drift prevents update, poststate drift invokes exactly one etag-guarded rollback, rollback verification handles a changed fingerprint, all event digests chain, no raw output/claim token is persisted, and no operation 3–7 command is generated.
