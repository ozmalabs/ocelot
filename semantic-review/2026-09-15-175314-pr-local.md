# Podman acceptance run stops before container creation

The provisioned P0 Podman command was run with both required environment switches and collected all three configured cases: hostile worker, forged authority frame, and external stop. Each case passed rootless/local-engine and pinned-base-image preflight, then failed closed while staging the image because the test interpreter’s `cryptography` distribution has no finite file manifest. No image was built and no worker container was created, so the run provides no actual hostile execution, live inspect/mapping, FD/mmap, filesystem/network/socket denial, evaluator receipt, forged-frame terminal, or descendant-stop evidence. **Watch for: confirmed — the required three-case acceptance contract is not met; provision a Python runtime whose `cryptography` metadata exposes a finite file manifest, then rerun and retain all three completed evidence files.**

**Verdict**: NEEDS_CHANGES

## High-level view

The evaluator correctly refused to copy an unenumerable third-party runtime into the isolated image. That fail-closed policy protects image provenance, but on this host it prevents the acceptance harness from reaching `podman build`, `podman run`, and every behavioral assertion downstream.

The retained evidence proves only the preflight posture: Podman 4.9.3 is rootless and non-remote, and the required base image is locally present. It contains no derived image ID, live `inspect` record, worker report, opaque proposal receipt hash, terminal runtime-record hash, process-table snapshot, or post-stop result, so the configured UID/GID mappings and all worker-level claims remain unverified rather than failed assertions.

## Finite runtime provenance blocks all three Podman cases

The acceptance command `P0_RUN_OS_ISOLATION_TESTS=1 P0_OS_ISOLATION_PROVISIONED=1 pytest -q -vv --basetemp=/tmp/p0a-podman-acceptance-review tests/evaluation/test_os_isolation_integration.py` collected and executed all three cases, and all failed in `PodmanAcceptanceLauncher._stage_worker_distributions()`. The launcher obtains the installed `cryptography` distribution and requires its `files` manifest before copying any third-party runtime inputs. Under pytest’s `/usr/bin/python3` 3.12.3, that field is absent, producing the confirmed `PodmanAcceptanceFailure: cryptography runtime distribution has no finite file manifest`; `evaluation_mode` then records a sandbox-start failure rather than launching a worker.

The evidence files retained at `/tmp/p0a-podman-acceptance-review/test_rootless_podman_{hostile_w0,forged_au0,stop_kill0}/podman-acceptance-evidence.json` each show preflight passed against a local rootless, non-remote Podman 4.9.3 engine and the exact base image. The acceptance fields `build`, `derived_image_id`, `inspect`, `worker_report`, receipt/runtime hashes, `live_descendants`, and `post_stop_inspect` are absent; the hostile and forged attempts retain only failed cleanup `podman stop` calls for containers that were never created. The hostile fixture therefore never attempted host checkout/home/control/receipt/terminal/result sentinels, TCP or Unix sockets, FD enumeration, or mmap; no evaluator-side opaque `method_not_enabled` receipt was produced. The forged fixture never sent the malformed authority frame, and the stop fixture never spawned a descendant or received evaluator stop.

The source profile requests `--user 65534:65534` with exact UID/GID mappings `0:1:65536`, and its live-inspect assertion would reject a mismatch. **Confirmed gap in this run:** no container was created, so no inspect artifact confirms those requested mappings, mount restrictions, network mode, capability state, or resource ceilings. They cannot be credited as execution evidence until the staging prerequisite is repaired and the three cases complete.
