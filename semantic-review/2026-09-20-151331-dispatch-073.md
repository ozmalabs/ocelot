# DISPATCH-073 packet-binding hardening for the Track A bootstrap runner

DISPATCH-073 carries the canonical APPROVAL-016 packet identity into the credential execution request, verifier-issued child approval, bootstrap receipt, and create-only attempt ledger. The runner now requires the canonical packet path, validates the packet digest before adapter construction, and rejects altered or rehashed packets before launcher activation when the reviewed approval is reused. The default adapter factory constructs the launcher, Google JWT verifier, STS client, and credential-only IAM path internally rather than accepting those components from its caller. **Watch for:** **confirmed** the canonical packet is still a blocked preparation artifact with unresolved authority, subject, WIP/IAM, and closure prerequisites; **confirmed** the effectful runner API still accepts a caller-supplied adapter factory and only type-checks its output, so verifier-owned trust construction depends on the production caller selecting the fixed factory.

**Decision**: BLOCKED — no launch or mutation occurred, but the real packet/evidence gates and the effectful trust-boundary constraint are not closed.

**Verdict**: NEEDS_CHANGES

## High-level view

The normal bootstrap path now has one packet identity threaded through all approval and receipt boundaries: the canonical packet digest and absolute path are included in the derived execution request, child approval, redacted receipt, and reservation/terminal ledger records. The runner validates those links before constructing an adapter or reserving the one-shot attempt.

The default loader validates the canonical packet against its reviewed source bindings, and the adversarial suite confirms that both an altered packet and a rehashed altered packet fail before launcher calls when the original approval is reused. This closes the REVIEW-073 mismatch between canonical packet identity and the derived credential request for the exercised path.

The **confirmed** fixed factory removes direct trust-component injection from its constructor, but `ReviewedBootstrapRunner` still takes an arbitrary `AdapterFactory` for effectful execution and accepts any exact `ConfidentialSpaceAdapter` whose capability factory has the required type. The production entry boundary must make that injection impossible or independently attest the factory before launch.

The **confirmed** canonical packet remains repository preparation only. Its authority binding is null, the attestation subject prefix and exact WIP/IAM state are unresolved, and the closure still requires reconciliation to the immutable registry reference; no local test result supplies the missing external evidence.

## Canonical packet identity across approval, receipt, ledger, and runner

`CredentialExecutionRequest` now contains both `packet_digest`/`packet_path` and its own `request_digest`. The child approval repeats the packet identity and the execution-request digest; approval validation requires all four values to match the prepared request. The receipt repeats the packet identity, approval digest, and execution-request digest, and the runner validates each against the prepared values before closing the ledger. Both memory and file ledgers carry the packet and path on reservation and terminal events, and reject terminal binding drift.

## Altered packets stop before launcher activation

The default request loader first requires the canonical absolute path and validates the file against the reviewed source-bound request builder. The runner then checks the packet’s self-digest and exact packet-derived bindings before it constructs the adapter or reserves the attempt. The tests cover a changed packet with the original digest and a changed packet with a recomputed digest; both fail before source calls and leave the ledger empty.

The **confirmed** remaining limitation is that `request_loader` is replaceable on `ReviewedBootstrapRunner`. A custom loader bypasses the source-bound `validate_request` call and supplies only the structural/digest checks in `_validate_request_shape`; an effectful caller could therefore pair a rehashed alternate mapping with a newly issued approval. Make canonical file loading non-overridable at the production boundary, or re-run `validate_request` against the canonical file inside `run` regardless of the loader used for tests.

## Fixed factory versus verifier-owned trust components

`ReviewedConfidentialSpaceAdapterFactory` now has no constructor parameters for launcher source, JWT verifier, STS client, or IAM impersonation. Its build path creates `LauncherTokenSource`, `GoogleJwtAttestationVerifier`, `GoogleSTSClient`, and a `CredentialOnlyCapabilityFactory` with the production IAM derivation default; this removes the constructor injection identified in REVIEW-073.

The **confirmed** residual gap is one level above that factory. Effectful `ReviewedBootstrapRunner` construction requires an `adapter_factory` supplied by its caller, and its checks accept an exact `ConfidentialSpaceAdapter` plus an exact credential-only factory without inspecting `adapter.gate.source`, `adapter.gate.verifier`, `adapter.sts`, or `capability_factory.impersonation_factory`. The focused success fixture demonstrates this shape with fake source, verifier, STS, and impersonation objects. That fixture is useful for ordering tests, but the same unchecked seam cannot be present in an effectful production entry point.

## Real evidence frontier remains blocked

The checked-in request is intentionally `blocked_pending_reviewed_effectful_bootstrap_runner`; it claims no attestation, credentials, timing, task, native execution, KMS result signature, GCS publication, or result evidence. The missing real prerequisites are a newly reviewed packet with materialized authority and closure/WIP/IAM bindings, a matching verifier-issued child approval, a real Google-signed Confidential Space attestation, and short-lived capability evidence bounded to that attestation. Only after those gates pass can a separately approved one-shot launch be considered; no timing, task, native, result, KMS, or GCS stage is authorized by this review.
