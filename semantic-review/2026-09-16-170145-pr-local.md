# V3 production activation and independently sealed evidence

This implementation adds a V3 repair lock and keeps the historical V2 lock/receipt format on a separate path. Production-mode execution validates the external authority and V3 lock before checking the rootless crun closure, and V3 runs prepend a signed preregistration receipt before worker evidence. The worker protocol and receipt chain are versioned, and the existing activation suite plus the requested P5 tests pass. Watch for: **confirmed** the V3 result seal can be re-sealed from a no-go into a go, **confirmed** the V3 worker validator accepts private data through `persistent_projection`, and **confirmed** repair preregistration does not cryptographically validate or protect the historical V2 parent.

**Verdict**: NEEDS_CHANGES

## High-level view

The lock boundary is weaker than the execution ordering: the V3 repair writer trusts a caller-supplied parent dictionary and can overwrite any output path, so “V2 is historical” is a convention rather than an enforced artifact boundary. **Confidence: confirmed.**

The V3 worker envelope has the right task/reply schema and fresh-episode fields, but the validator only protects control metadata. Its persistent projection is passed through without an allowlist, leaving a direct route for evaluator-private values to enter the worker contract. **Confidence: confirmed.**

The receipt chain is independently reloadable cryptographically, but the seal verifier checks mostly self-consistency. It does not recompute the gate decision or bind the first preregistration receipt’s workload commitments to the result, so a valid signed chain can be wrapped in a different semantic result. **Confidence: confirmed.**

## V3 seal can promote a no-go without native evidence

`run_readiness_gate` checks the authority and closure before native invocation, but the seal path loses that decision: `seal_result` only checks the V3 receipt-chain closure and exact rollback, while `verify_result_seal` repeats those checks plus the seal digest. Neither function checks `gate_reasons`, `closure.available`, `native_verified`, `external_authority_verified`, or the semantic evidence binding used by `evaluate_gate`.

This makes the no-go boundary mutable after the run. A result produced with `require_native=False` has a valid signed chain but a `native_closure` gate reason; changing `outcome` and `disposition` to `local_readiness_only/go`, clearing `gate_reasons`, and calling `seal_result` produces a seal that `verify_result_seal` accepts. The seal path must either invoke the complete V3 evidence/gate validator or carry a signed decision that cannot be upgraded by rewriting result fields. **Confidence: confirmed.**

## V3 worker projection is not actually private-field-closed

`validate_task` strictly checks the V3 top-level keys and filters forbidden names from `control`, but it never validates `persistent_projection`. `make_task_v3` copies the caller-provided projection into the task, and the validator accepts arbitrary keys and values. A task with `persistent_projection={"truth": "SECRET"}` passes validation, even though the V3 contract describes private fields as forbidden and the projection is intended to be the bounded public namespace view.

The validator should require the exact projection shape emitted by the evaluator—bounded `adoption_count` and a valid namespace digest, or an explicitly defined empty form—and reject unknown keys, private names, non-integer counts, and oversized/unverifiable values. Add a direct adversarial validator test; the current privacy test only checks fields at the task’s top level. **Confidence: confirmed.**

## Repair lock does not enforce an immutable, authenticated V2 parent

`preregister_repair` accepts a dictionary and proceeds when its `lock_digest` field equals the hard-coded `V3_PARENT_LOCK_DIGEST`; it does not validate the V2 lock schema, recompute its object hash, verify its signature, or read the historical artifact. The V3 lock therefore signs whatever `parent_manifest_digest`, truth, store, and split commitments the caller supplied under the expected digest label.

The writer also calls `write_bytes` directly on the requested output path. Because no parent path or nonexistence/distinctness check is part of the API, passing the historical V2 path would replace it rather than create a new repair artifact. Make the parent an immutable canonical file/artifact input, validate it against the external V2 authority, derive its digest from the bytes, and refuse existing or overlapping V3 output paths. **Confidence: confirmed.**

## First-receipt binding does not close the result semantics

V3 append ordering prevents a normal run from writing a terminal receipt before `preregistered`, and `_v3_chain` checks the first receipt’s authority, key, public-key digest, and internally computed order digest. That is not enough for independent seal reload: the verifier never checks that the receipt’s `content_digest`, order, parent commitments, lock digest, manifest digest, policy, worker contract, closure, and run ID agree with the result being sealed. It also does not compare the chain’s receipt run IDs with a result run ID.

Consequently, result-level manifest/lock/preregistration fields can be changed and re-sealed while the signed chain remains untouched. Bind the first receipt to the result’s canonical workload and lock commitments, require the result’s preregistration summary to equal that receipt, and validate a single run ID across the chain before accepting the seal. **Confidence: confirmed.**

## Coverage of the activation boundary

The focused suite passes (`14 passed` across the V3 activation/repair and P5 runner/repair tests), including V2 rejection without mutating the tested lock file, first-receipt ordering, key/receipt tamper rejection, and the missing-authority no-native assertion. It does not cover semantic seal tampering, private fields nested inside `persistent_projection`, fabricated parent commitments, or an output path collision with a V2 lock. Those cases should be added before treating the activation boundary as complete. **Confidence: confirmed.**
