# RS-069R1 candidate image binding with blocked base provenance

RS-069R1 records a locally rebuilt candidate image, a proposed immutable Artifact Registry reference, local closure inputs, and a review-only IaC commitment. The candidate binding explicitly states that the base image came from an unpinned `python:3.13-slim` tag and that remote base provenance is not established, so the base is blocked rather than presented as immutable production provenance. The approved consumer stops at the first unresolved RS-069 operation and the hash-chained ledger records no cloud operations, registry push, signing, or mutation. **Confirmed** the remaining release blocker is that the consumer accepts self-reported image and closure digests instead of independently recomputing and verifying them; **confirmed** the base blocked/pinned rule is documented but not enforced by that consumer.

Watch for: **confirmed** independent image/closure verification is absent and must be added before this binding can satisfy the consumer trust boundary; **confirmed** the base provenance block is explicit in the binding but is not machine-enforced; **confirmed** no registry, cloud, signed-environment, task, or supervisor execution occurred in the recorded attempt.

**Verdict**: NEEDS_CHANGES

## High-level view

Base provenance is explicitly unresolved because the source Containerfile uses a tag rather than a digest. The consumer must reject any future record that omits this explicit block or substitutes a mutable base tag for a digest-pinned base.

The consumer validates the binding’s canonical shape, target reference, registry/push flags, fixed closure digest, and IaC commitment, but does not independently inspect the image or recompute the closure from the supplied files, runtime, seccomp profile, resource limits, and argv. A binding can therefore remain internally consistent while its underlying image or closure inputs are stale or tampered.

The external boundary is preserved: the candidate build uses `--pull=never`, `--network=none`, and `crun`; the binding marks registry verification and push as false; and the RS-069 ledger records an approval preflight that stopped before `bind_candidate_image_digest`, with `cloud_operations=[]` and `mutations_performed=false` throughout.

### Base image provenance is explicitly blocked, not immutable

The candidate binding’s `build.base_image` records a local image ID, local manifest digest, repo digests, and the reference `docker.io/library/python:3.13-slim`. The source Containerfile uses the same tag without an `@sha256:` digest. The binding’s limitations explicitly say that the local base was selected by the unpinned tag under `pull=never` and that remote base provenance is not established. **Confirmed** this satisfies the requested alternative of explicitly blocking immutable-base provenance; it must not be promoted to a production provenance claim.

The gap is enforcement rather than wording. `_load_candidate_binding` checks the candidate image, target reference, registry flags, closure digest, and required-input commitment, but does not inspect `build.base_image`, `limitations`, or `provenance` to require either a digest-pinned base or a canonical blocked state. **Confirmed** a future malformed binding could omit or alter the base limitation while still passing the consumer’s current base-related checks. The consumer needs to independently derive the values it consumes. The existing two runner tests cover first-operation blocking and exact retry no-op, but **confirmed** they do not mutate a binding field or source input and assert rejection; add negative tests for stale image identity, changed closure file, changed argv/resource limits, and missing or contradictory base provenance.
