# GCS IAM capability boundary for operation 4

The proposed boundary defines a project-bound GCS destination, an exact digest-derived run namespace, and an 11-object bundle whose local semantic and file digests are closed. It also proposes a create/get-only custom role, an exact-run resource condition, removal of the observed bucket-level `roles/storage.objectAdmin`, and a Confidential Space STS → IAM Credentials path with no keys or ambient ADC. The repository artifacts remain explicitly review-only: the narrow IAM is not applied, the exact token-creator grant and short-lived token are absent, and no object or authenticated remote receipt exists. **Watch for:** **confirmed** `APPROVAL-011` is only broad sequential authorization while the canonical operation-4 child approval remains disabled with null destination and generation commitments; **confirmed** the current capability service account still has broad `roles/storage.objectAdmin` and also retains project-level KMS signer permission, so the proposed token is not GCS-only; **confirmed** the packet does not provide a reviewed IAM prestate/etag rollback path or a runner-generated receipt binding the authenticated principal to the exact project, bucket, generations, and private truth.

**Disposition**: `BLOCKED`

**Verdict**: NEEDS_CHANGES

The destination and bundle proposal is internally coherent. **Confirmed** the project number, bucket name, prefix, digest-derived run ID, private-truth suffix, 11-object order, local digests, and generation-zero observations agree across the packet, capability definition, and artifact index; these are read-only commitments, not current execution authority.

The IAM design is least privilege for the GCS permissions it declares, but only as desired state. **Confirmed** the broad object-admin grant remains live and no reviewed IaC apply, exact WIF/token-creator poststate, IAM etag/prestate, or rollback evidence is supplied. **Confirmed** the same target service account also has `roles/cloudkms.signerVerifier`, so a generated access token for that account carries a capability beyond GCS unless the reviewed boundary intentionally accepts a shared GCS/KMS identity or separates the accounts.

The runner’s explicit-store and generation checks prevent ambient credential discovery and enforce create-only/exact-generation object behavior. **Confirmed** the packet’s authenticated receipt contract is not implemented by that path: it does not bind the store’s authenticated identity and project to the packet or emit the required per-object project, bucket, checksum, and private-visibility evidence.
