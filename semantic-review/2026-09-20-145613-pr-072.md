# DISPATCH-072 bootstrap runner: credential-only boundary for APPROVAL-016

The change adds a repository-side runner for the single APPROVAL-016 bootstrap scope. It validates the canonical request and reviewed image, closure, WIP, authority, KMS, and IAM observations, then delegates the only effectful path to the existing Confidential Space adapter: launcher token, Google JWT policy verification, STS exchange, and short-lived IAM capability derivation. The credential-only factory exposes no evaluator, timing, KMS signer, or GCS client, and the runner records one create-only attempt with a redacted verifier-issued receipt. **Watch for:** **confirmed** — the child approval and receipt bind the derived credential-request digest rather than the canonical APPROVAL-016 packet digest, so packet metadata can change without invalidating approval; **confirmed** — the current packet still has unresolved authority, subject, and closure materialization and cannot reach launch.

**Review status**: NO_GO — the packet/approval binding must be fixed before the approved attempt can be used.

More importantly, a verifier approval is not directly tied to the canonical packet digest.

## Credential-only activation through the reviewed adapter

The default `ReviewedConfidentialSpaceAdapterFactory` selects the fixed launcher socket, `GoogleJwtAttestationVerifier`, and `GoogleSTSClient`. The adapter verifies nonce, JWT, issuer, time, and workload claims before STS exchange; `CredentialOnlyCapabilityFactory` derives only the short-lived IAM token and returns fail-closed placeholders for store, signer, and timing. `bootstrap_credentials` requires the sealed capability receipt and emits a redacted receipt without raw JWT, STS, or IAM material. This keeps APPROVAL-016 at capability activation rather than entering Track A execution.

The **likely** trust-boundary gap is that the public factory constructor also accepts caller-supplied source, verifier, STS, and impersonation implementations, while the runner checks only the resulting adapter and credential-only factory types. A production entry point must use the fixed Google implementations or require an independently verified adapter; the focused tests inject fakes and therefore prove ordering/redaction, not Google signature or IAM provenance.

## Canonical packet and derived-request binding

`build_execution_request()` creates a new digest from adapter configuration and reviewed capability/KMS bindings; it does not carry `request["request_digest"]`. `VerifiedCredentialChildApproval.request_digest` is checked against that derived request, and `_build_receipt()` stores the same derived digest. The outer `BootstrapRunResult` reports the canonical packet digest, leaving two public request identities with no equality check.

This is **confirmed** by code and a local preflight probe: changing only the packet claim-boundary text, recomputing its packet digest, and reusing the original child approval was accepted by `prepare_bootstrap`, because the credential execution request was unchanged. Packet metadata not represented in that request, including selection/source/inventory commitments, has the same reuse class. Bind both the canonical packet and derived-request digests through approval, receipt, and ledger completion.

## Current packet materialization is still a real launch blocker

## One-shot ledger and protected artifacts

`FileAttemptLedger` reserves with exclusive creation, rejects the canonical request and historical operation-ledger paths, writes no cloud-operation or credential-export claims, and appends one terminal event. A failed bootstrap is terminal, so later invocation cannot retry after launcher, STS, or IAM failure. The reviewed factory’s construction is local; downstream network work begins only after reservation.

The preservation result is **confirmed** for this review: no VM, launcher, STS, IAM, KMS, GCS, FreeTSA, timing, task, result, runsheet, canonical JSON, or protected-ledger mutation was performed. The focused tests cover reservation collision and terminal closure.

## Track A evidence frontier and missing real prerequisites

The runner deliberately stops at credential bootstrap. It does not provision/read generated inputs, derive a timing seed, issue a task, invoke native execution, create a result/seal, sign a result with KMS, or publish to GCS. This **confirmed** behavior satisfies the requested fail-before-timing/tasks/result boundary, but the receipt is not a Track A result.

The exact remaining real prerequisites are: repair direct packet/approval binding; materialize and independently verify candidate/closure, authority, WIP/IAM capability, packet digest, and child approval; provision exact public/private generated inputs to an approved durable boundary without reading them, then read and freshly rehydrate them only after attestation; perform one real Confidential Space launch with Google-signed image/project/zone/TEE/Secure Boot/WIP claims; obtain verified FreeTSA/RFC-3161 timing before seed/input/task; execute only the locked `cold_reset` case and `illegal_action` control through authenticated native supervision with OOM/deadline/cleanup and canonical receipts; then persist/read back the result seal and obtain the non-exportable KMS signature over the exact lock, all input, attestation, timing, supervisor, receipt, result, and seal commitments. Optional post-sign GCS publication and Track B hardening remain non-gates.
