# Integer-observable LogQuantum emitter — independent verification

The `LogQuantum` DSL Term emits an integer log-coordinate `q = round(log_a(x)/Δ)` from a continuous log-domain quantity, holding the base `a` and resolution `Δ` as intensional rational params on the Term (applied on read), so the only thing that lands in-frame is an `Int` and the frame/continuum invariant is satisfied by construction. It generalises `scale_pow2_once`'s fixed base-2 additive-`k` axis to an arbitrary base+Δ, and its output (integer log-quanta whose differences are integer log-ratios) feeds `RatioInduce` directly. I re-read the op, rebuilt the crate, re-ran the Rust suite (812 pass) and all three harnesses on the freshly built engine (`af09f38e0336`).

Watch for: (1) the H-L1 crux **holds on my own read** — `set_coord` writes `Value::Int` only, the transient `ln(x)/(ln a·Δ)` float is rounded to `i64` before it touches a slot, base/Δ are `i64` rational Term fields never stored as coordinates, and `coord_ints` is byte-untouched (confirmed). (2) The uncommitted tree bundles the **prior-stage `RatioInduce` alongside LogQuantum**, and RatioInduce's mid-enum insertion at discriminant 167 renumbers ~68 existing variants — the build report's "no existing renumbering (discriminant 236)" is true *for the LogQuantum addition only*, misleading about the tree as a whole; harmless because the JSON wire form is name-keyed, not discriminant-keyed (confirmed). (3) The H-L1 P4 skip-path is fail-*safe* not fail-loud: when the op is inapplicable it returns the population unchanged, leaving the original float in the slot — downstream `coord_ints` then refuses it (correct), but the emitter itself does not error.

**Verdict**: APPROVED

## High-level view

H-L1 is well-formed by construction and I confirmed it by reading the code, not just running the harness: the emitted quantum is the sole in-frame output and it is always `Int`; `a` and `Δ` ride as `base_num/base_den` and `delta_num/delta_den` rationals on the Term, applied inside the cross-frame render and never written to a slot; `coord_ints` is unchanged and still returns `None` on any non-`Int` slot. The price against the invariant is zero.

H-L2 composes with `RatioInduce` on my re-run: a fixed multiplicative factor `f` yields a constant integer quantum-difference `round(log_a f/Δ)` across five random per-frame scales (all `3` for `f=8`, scale cancels), 5/5 planted cross-axis log-extent ratios recover through emitter→RatioInduce, and the independent-axis negative control floors (`explained=false`). Recovery is planted-then-checked, not fitted-then-declared.

H-L3 runs on the real `domains/frame.py` machinery (`build_frame` storing `math.log`, `dimension_weight`, `relative_weight`, `frame_dims` imported directly), not a stand-in. The raw float-log-weight population is refused; after emission every in-frame coordinate is `Int`; RatioInduce recovers the non-degenerate 2:1 invariant with the per-frame importance scale factored; and the emitted quanta-diffs equal `round(relative_weight/ln2)` exactly (0,2,4,6).

Reuse discipline holds: the change is the five expected files (`term.rs`, `term_variants.rs`, `jsonio.rs`, `reflect.rs`, `shape_decode.rs`), `py.rs` is untouched (generic name-keyed handoff), the crate builds, and the full Rust lib suite (812 pass, dim_infer/ratio/shape_decode all green) plus the Python regression (25 pass / 1 skip) stay green.

### H-L1 — the price is zero, and it's structural

I traced the emitter (`shape_decode.rs::eval_log_quantum`, :3540) rather than trusting the harness. The whole risk is one line: what type reaches a coordinate slot. It reaches it through `set_coord` (:659), which builds the replacement slot as `Value::Int(val)` where `val: i64` — there is no float path into a slot. The quantum closure (:~3595) computes the one transient float `logx/delta` and immediately `.round() as i64`; that `i64` is what `set_coord` receives. The continuous base and step are the Term's `base_num/base_den/delta_num/delta_den` (`i64` fields on the `LogQuantum` variant, term.rs:3246), resolved to `f64` locally inside the map and never persisted — the exact "continuity is intensional, applied on read" posture the invariant demands.

`coord_ints` (:643) is byte-identical to its pre-change form: it returns `None` the moment any relation's target slot is not `Value::Int`. So the downstream integer-lattice gate is untouched, and the emitter is precisely the sanctioned bridge that turns a continuous reading into an admissible integer coordinate.

My re-run of `hl1_price.py` confirms all five price facts on the built engine: float inputs `[1.7,2.9,5.5,11.1,20]` emit `[1,1,2,2,3]` (all `int`, = `round(ln x)`); changing Δ changes the quanta and re-evaluating reproduces them (param applied on read, map is a rule); the emitter's integer output is RatioInduce-consumable while a raw-float population is refused (`explained=false, n_frames=0`); and a coarse Δ merges what a fine Δ separates (resolution pinned to observation, MDL). The one nuance worth stating: the "no float ever written" guarantee has two regimes — the *applicable* path provably writes only `Int`; the *inapplicable* path (Δ≤0, base≤1, slot out of range) is a graceful skip that returns the population unchanged, so the pre-existing float remains where it was. That is fail-closed (coord_ints then refuses the frame) but silent.

Resolution is pinned to Δ, not arbitrary precision: the identifiability guard `usable = delta > 0.0 && ln_a.is_finite() && ln_a != 0.0` gates the whole op, and the quantum is `(logx/delta).round()` — the stepped rendering, never sub-Δ precision.

### H-L2 — the difference is an integer log-ratio RatioInduce factors

`hl2_synthetic.py` on my re-run: for `f=8, base=2, Δ=1` the two-quantity difference is `3` across per-frame scales `{1.3,2.7,5.1,9.9,100}` — the multiplicative scale is a common additive log-offset that cancels in the difference. The population arm plants a cross-axis log-extent ratio `y_pow:x_pow` per trial, emits both axes to integer quanta, and checks the RatioInduce recovery against the *independently reduced* planted ratio: 5/5 (`3:1`, `1:1`, `4:1`, `2:1`, `3:2`), with the latent correctly `latent:scale2` for power-of-two ratios and `latent:ratio` otherwise. The recovery is genuinely planted — the op is handed only the integer quanta and is never told the ratio or the scales. The negative control (independent per-axis stretch, no single common scale) floors to `explained=false` after emission, so the honest MDL floor survives the emitter. This matches RATIO_INVARIANCE H-R1 in shape, now driven through the emitter instead of raw integer extents.

### H-L3 — real frame.py, no continuous weight in-frame

The harness imports `build_frame`, `dimension_weight`, `relative_weight`, `frame_dims` straight from `domains.frame`, and I confirmed those are the real functions: `build_frame` stores `math.log(wv)` per dimension (frame.py:86) and `relative_weight = log_weight(a) − log_weight(b)` (frame.py:171), the log-ratio the prereg targets. The harness builds four real Frame nodes differing by a per-frame importance scale, asserts frame.py's own scale-invariance as ground truth (relative_weight identical across frames — 1.3863 / 2.7726 / 4.1589 for the three pairs), then feeds the *stored float log-weights* to RatioInduce raw (refused) and after `LogQuantum` (`raw=false`, requantising the already-log value onto the base-2 integer axis).

On my re-run: the raw float population is refused; after emission every in-frame coordinate is `Int`; RatioInduce recovers the non-degenerate `2:1` invariant (`latent:scale2`, 4 frames) with the per-frame scale factored; and the emitted quanta-differences equal `round(relative_weight/ln2)` exactly for all four dims (topic 0, speaker 2, affect 4, time 6). The continuous log-weight lives only on the real Frame node and in the transient emitter read — never in a RatioInduce coordinate. This is the real headline site, unlocked without storing a continuous weight in-frame.

### Reuse discipline — the crate, the wheel, no fork

The uncommitted working set touches exactly the five files the prereg names: `shape_decode.rs` (+471, the op + doc), `term.rs` (+174: enum variant, `evaluate` arm, `copy_subtree`, `children`), `jsonio.rs` (+52: type-name + to_json + name-keyed from_json with sensible defaults base 2 / Δ 1 / raw false), `reflect.rs` (+88: encode/reconstruct), `term_variants.rs` (regenerated). `py.rs` carries no LogQuantum reference — the Python side is the generic `term_from_json` handoff, exactly as predicted. `scale_pow2_once`, `RatioInduce`, and `coord_ints` are reused unchanged. The engine was rebuilt via `scripts/engine_build.sh` (safe `--remove-destination` copy, not a fork), producing `af09f38e0336` — the build the harnesses actually loaded.
