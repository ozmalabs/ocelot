# R18R1 hardening for the fail-closed operation-2 boundary

The hardening moves operation 2 from caller-provided approval, claim, and prestate mappings to canonical file-backed artifacts, adds recursive unresolved-marker rejection, and contains terminal ledger-write failures with a redacted manual-review marker. The focused handler still defaults to disabled and is not dispatched by the legacy runner, so this review did not invoke operation 2 or any cloud command. The 14-test focused suite passes, including a mocked post-mutation terminal-ledger failure. **Watch for:** **confirmed** — the approval and attestation files are still caller-selected and self-authenticated by recomputed digests rather than authenticated by a trusted signer/verifier; the proposed state therefore remains blocked/manual-review.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** the direct caller-authentication bypass is closed: `execute_operation_2` rejects caller-supplied review state, approval, claim, and prestate mappings, and the binding validator requires canonical approval and claim artifact paths. The remaining **confirmed** gap is artifact provenance: the caller still supplies the paths and can construct a canonically encoded object whose SHA-256 matches its own `artifact_digest`.

The mutation gate now rejects unresolved markers recursively in desired state, canonical artifacts, expected prestate, observed provider state, and fixed update arguments before the update runner is reached. The handler remains narrow—describe, exact prestate comparison, one fixed update, describe, and verification—with later operations disabled; no operation or cloud state changed during this review.

**Confirmed:** post-mutation exceptions, including terminal ledger persistence failure, are converted into a terminal result and a redacted no-retry recovery marker rather than escaping as success or rollback completion. The mocked failure test verifies that behavior, although the approval and attestation provenance gap still blocks authorization.

<summary>Details</summary>

### Approval artifact provenance remains self-authorizing

`validate_operation_2_bindings` correctly rejects non-`None` caller approval and review-state arguments, loads the approval from canonical bytes, requires a closed schema, exact approval ID/status, exact request scope, and exact immutable bindings, and verifies `artifact_digest`. The trust boundary stops there: `approval_artifact_path` is an ordinary caller argument, there is no signature or trusted approval-store check, and `_artifact_digest` recomputes a plain SHA-256 over the supplied object. The focused test’s `_approval_artifact` helper constructs a passing approval object locally and writes it to a temporary path, demonstrating structural validity rather than independent authorization. **confirmed**

The apply gate should remain blocked until a trusted master/security review artifact is verified and its authenticated digest is bound to the exact operation-2 request and expected prestate. A canonical file format can be retained as the serialization layer, but it must not be treated as the authority.

### Attestation evidence remains caller-constructible

The claim validator improves shape and binding checks: it closes the artifact and nested evidence, checks the expected schema/source/verifier ID, binds candidate/provider/claim paths, recomputes evidence and claims digests, and checks the exact expected claim values. Those checks still accept a caller-created artifact because the source string and verifier ID are data fields, and no signature, token verification, certificate chain, freshness/nonce validation, or allowlisted verifier output is consulted. The focused test’s `_claim_artifact` helper constructs the entire evidence and claim record and the validator accepts it. **confirmed**

The production boundary needs an independently verified Confidential Space result, with authenticated verifier provenance and freshness, before the claims digest can authorize the update. That result should be cryptographically or otherwise trust-root bound to the candidate image, provider resource, exact claim paths, and approval artifact rather than merely copied into a canonical JSON file.

### Unresolved inputs and terminal ledger failures are contained

The pre-update path loads and validates the expected prestate and both artifacts before the first provider describe/update sequence. `_reject_unresolved` recurses through nested mutation-bound values; `_state_from_gcloud` applies it to observed mapping and condition; and the fixed update builder rechecks mapping, condition, and fingerprint. The focused tests cover unresolved desired mapping, provider mapping, provider condition, and missing provider/attestation boundaries, so unresolved markers cannot reach the update call through the reviewed paths. **confirmed**

After mutation begins, the normal verification and failure paths catch ledger append failures, attempt etag-guarded rollback where needed, and return `terminal_ledger_write_failed` with `manual_review_ledger_failure` plus a redacted recovery marker when the terminal event cannot be persisted. The test monkeypatches the terminal `run_stopped` append after a mocked update and verifies that the result reports mutation and manual review; all 14 focused tests pass. No real `_run_json` or cloud command was executed in this review. **confirmed**

The resulting proposed state is **blocked/manual-review**: no operation-2 authorization is established, the WIP provider and IAM/cloud state are unchanged, later operations remain disabled, and retry must wait for authenticated approval, verifier-produced attestation, and the expected-prestate artifacts.
