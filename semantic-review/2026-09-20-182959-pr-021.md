# APPROVAL-021 reviewed IAM and Confidential Space provisioning boundaries

The change adds repository-only, injected boundaries for the two APPROVAL-021 provisioning steps: a keyless GCS-only service account/custom role/WIF token-creator path and a digest-pinned Confidential Space VM bootstrap. The IAM path uses verifier-sealed short-lived credential and child-approval objects, REST-only mutations, optimistic versions, poststate checks, and reverse rollback; the Confidential Space path fixes the VM/image/closure values, redacts launcher evidence, and keeps timing, task, result, KMS, and GCS progression disabled. Local validators and the focused 30-test suite pass without cloud mutation, but the checkout has no verifier runtime, fresh live bindings, CS child approval, or new post-provisioning receipts. Watch for: **confirmed** — the CS child approval/live-binding fields are self-asserted JSON rather than verifier-sealed; **confirmed** — the CS poststate does not enforce the requested VM network; **confirmed** — the last checked-in live inventory still has the target account and role absent and legacy IAM bound to an older image.

**Verdict**: NEEDS_CHANGES

**Overall disposition**: `BLOCKED / NO_GO`. Do not invoke either effectful apply. The exact next reviewed execution operation is a single read-only signed-environment reconciliation for APPROVAL-021 that materializes fresh IAM account/role/bucket/WIF-provider observations and the VM/image/closure binding, then issues separately sealed child approvals. Only after that review should `provision_gcs_only_iam_boundary` run once; its verified IAM receipt must gate the one-shot `bootstrap_confidential_space_vm`. Track A timing, task, native, result-seal, KMS-result-signing, and GCS publication operations remain disabled.

## High-level view

The IAM design separates the existing KMS-capable account from the new GCS-only account and narrows the intended capability to `storage.objects.create/get` under the exact operation-4 prefix, with the candidate image principal allowed only to mint a token for that account. The verifier-owned credential and exact child approval are strong local gates, but no runtime factory or fresh signed-environment evidence is present, so this is not yet an executable approval boundary; the bucket validator also preserves unlisted bindings rather than enforcing a closed reviewed policy set.

The Confidential Space definition pins the candidate image digest, `n2d-standard-2`/`us-east1-b`/SEV/secure boot/vTPM/no external IP, and a restrictive container closure, then requires poststate and redacted launcher evidence before reporting success. Its structural values are precise, but the effectful path accepts a plain JSON `verifier_issued` flag and arbitrary digest fields, and its poststate check omits the VM-level `network=default` requirement, so the exact trust boundary is not proven.

Both implementations preserve the important downstream gate: neither can claim attestation, credentials, timing, task issuance, native execution, result sealing, KMS signing, or GCS publication from the current checkout. The last recorded inventory remains pre-provisioning—target GCS-only account and custom role absent, current WIF/IAM not least privilege, and no attestation or credential—so repository tests cannot advance Track A.

### GCS-only IAM capability and credential custody

The IAM definition correctly separates `p5-r0-gcs-only@ocelot-proof.iam.gserviceaccount.com` from the existing KMS-capable `p5-evaluator` account. Its intended role is exactly `storage.objects.create` and `storage.objects.get`, the bucket grant is conditional on the reviewed operation-4 prefix, and the WIF principal is the candidate image digest with `roles/iam.serviceAccountTokenCreator` on the target account and no direct bucket access. `GoogleIamRestBackend` stays on explicit injected REST transport with no subprocess, gcloud, ADC discovery, or key creation; the executor binds the fresh prestate, request digest, credential evidence, authority digest, and child approval before mutation.

**Confirmed concern — live readiness is still absent.** The checked-in Track A inventory records `target_service_account_exists=false`, `custom_role_exists=false`, `current_wif_mapping_is_exact=false`, `current_iam_is_least_privilege=false`, `current_attestation_verified=false`, and `current_credentials_injected=false` (`services/p5_r0_evaluator/deploy/p5-r0-track-a-bootstrap-request-approval-018-v1.json:104-109`). No `var/p5-r0-rs069/approval-021-confidential-space-approval.json` exists, and the advertised `signed_environment_runtime:build_approval021_iam_runtime` is not in this repository. The IAM CLI therefore correctly stops at its runtime-injection gate; that is a truthful blocked preparation state, not a successful provisioning receipt.

**Confirmed concern — the bucket policy is only partially exact.** The concrete REST update reads the current policy, removes only the two requested broad/stale entries, preserves all other entries, and appends the exact grant (`reviewed_iam_backend.py:355-371`). The shared poststate validator similarly checks for the exact grant and selected forbidden members, not equality with a closed approved binding set. If APPROVAL-021 requires the bucket to expose only the reviewed capability (or only an explicitly enumerated allowlist), an unrelated broad or conditional grant can survive and the receipt can still be marked verified. The next child approval must carry the allowed preserved set or the validator must reject any unbound grant.

### Confidential Space image, closure, and VM boundary

The CS definition binds the exact Artifact Registry reference and digest, `n2d-standard-2`, `us-east1-b`, SEV, Secure Boot, vTPM, no external address, the GCS-only account, and closure values for `crun`, pull-never, no mounts, non-privileged execution, read-only filesystem, dropped capabilities, default-deny seccomp, and bounded resources. `_validate_poststate` checks the image, shielded settings, service account, no external IP, and every declared closure field; launcher evidence is redacted to token/claims/nonce digests and is checked against the request. **Confirmed concern — the VM-level network request is not enforced.** The definition requires `network: "default"` (`confidential_space_bootstrap.py:162`) and the rendered future command contains `network=default,subnet=default,no-address`, but the poststate expected map omits `network` (`confidential_space_bootstrap.py:319-325`). The only `network` value checked by the closure loop is the container’s `network: "none"`. A reviewed backend could therefore create or report a VM attached to another network/subnet while satisfying the current validator. Add exact observed network-interface, subnet, route/no-egress, and external-address fields to the VM poststate contract; do not rely on the future command string as evidence.

**Confirmed concern — provider trust is reduced to caller-supplied digests.** `_validate_bindings` requires the observed object to echo the approval’s IAM/WIP digest and checks only provider URI, STS audience, claim-path names, account, role, and no direct bucket access (`confidential_space_bootstrap.py:308-313`). It does not verify the live provider’s condition terms, and the approval loader accepts any digest-shaped `live_bindings_digest` after recomputing a local JSON hash (`confidential_space_bootstrap.py:181-188`). The exact WIP conditions in the capability definition—issuer, subject prefix, image digest, project/zone, disabled debug, TEE/hardware, workload/smoke, and Secure Boot—must be captured from the live provider and verifier-sealed before VM creation.

**Confirmed concern — child approval provenance is not protected.** Unlike the IAM executor’s opaque registered `VerifiedIAMChildApproval`, the CS path reads a normal JSON object and treats `verifier_issued: true` as sufficient. A caller who can provide the approval file can construct the same fields and digest without a verifier authority. This permits an injected backend/evidence source to reach the effectful runner without a real child approval or launcher verification authority. Make the CS apply boundary consume a verifier-owned opaque approval/evidence handle or an independently verifiable signature with expiry and exact request/live-binding commitments.

### Receipts, rollback, and one-shot lifecycle

**Confirmed concern — failure closure is not receipt-complete.** On an IAM exception, the executor tries reverse restoration and then appends only `failed_phase`, exception type, `rollback_status`, and `mutations_performed`; on a CS exception, `ledger.close("failed_closed", ...)` records the same kind of terminal summary (`reviewed_iam_backend.py:473-489`; `confidential_space_bootstrap.py:383-384`). Neither failure event binds the original prestate digest, any observed poststate, the rollback observations/versions, or a canonical rollback receipt digest. A failed delete or ambiguous policy restoration can be marked manual review, but the durable artifact does not prove what state was left behind. Add a canonical failure/rollback receipt and require it before the ledger can close.

**Confirmed concern — IAM reservation is not atomic.** The executor performs a plain existence check before `prepare` (`reviewed_iam_backend.py:437-439`) and creates the ledger only when individual events are appended. Two processes can pass the check and both perform backend work, defeating the stated single-attempt/no-retry boundary. Use atomic exclusive reservation (and a durable lock identity bound to approval/request digests) before any prepare-time remote read or mutation.

### Track A progression remains disabled

The implementation does not advance Track A: neither boundary issues timing, tasks, native execution, result sealing, KMS result signing, or GCS publication. The existing request keeps `selection` unset and the execution/timing/result gates disabled, and the prior live inventory contains no attestation or credential evidence. The next allowed step is therefore not a VM launch or a Track A task; it is the read-only signed-environment reconciliation and verifier-approval issuance described above. After IAM is separately reviewed and verified, the only permitted next mutation is the single `bootstrap_confidential_space_vm` attempt, followed by fresh attestation/capability verification before any downstream gate is enabled.
