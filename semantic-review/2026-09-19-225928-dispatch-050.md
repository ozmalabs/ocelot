# DISPATCH-050 signed-environment validation and Confidential Space activation

This change adds a repository-only DISPATCH-050 validator that checks the frozen RS-065/RS-067/RS-068 artifacts, consumes a real `ConfidentialSpaceAdapter` activation receipt, validates external KMS/IAM observations, and verifies a future exact-lock response without creating signatures or credentials. The local contract path preserves the unsigned, non-promotable state and exact request/unsigned-lock digests. The intentional `confidential_space.py` changes add smoke/claim evidence, explicit federated capability construction, impersonation, and expiry handling, but the new validators are not wired into that activation path. **Watch for:** **confirmed, blocker** an activated service can outlive its source attestation; **confirmed, high** signed-result validation does not enforce the full V4 authority/KMS binding; **confirmed, high** activation crosses into KMS/IAM/GCS capability construction before the fresh binding validators run; **confirmed, high** default request/proposal inputs are ignored and absent from a clean checkout.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed.** The local-only process consumes already-produced objects: contract validation reads canonical files, signed-result validation never invokes a signer, and the summary reports no cloud operations or created credentials. The adapter receipt requires a real adapter instance rather than a caller-supplied `attested` mapping or boolean.

**Confirmed, blocker.** The Confidential Space gate checks nonce, issuer, time, image, project, zone, TEE, hardware, Secure Boot, debug, workload, and smoke claims before capability construction, but the resulting service lifetime is based on STS/capability expiry rather than attestation expiry. A long-lived or independently supplied federated token can keep the service active after its source attestation is stale.

**Confirmed, high.** KMS and IAM validators describe the intended external preconditions, but activation does not consume them. `CapabilityFactory.build()` can impersonate a service account and construct GCS/KMS capabilities, including a KMS public-key read, while the signed-result path checks only selected authority fields rather than the exact V4 authority object.

**Confirmed, high.** Local validation is pure and active adapter reuse is idempotent, but the default inputs are worktree-local ignored files. A clean checkout cannot reproduce `validate_local_contracts()` without separately restoring the ignored `var/` artifacts, and the configuration can authorize non-AMD or non-Secure-Boot claims instead of enforcing the required posture.

<details>
<summary>Issues (6)</summary>

1. **Source-attestation expiry is not enforced** — **confirmed, blocker**: activation sets `_expires_at` from the capability/STS token and never caps it at the verified attestation `exp`, so a capability can remain active after its source evidence expires. Bound every derived credential and service lifetime to the minimum attestation, STS, and impersonated expiries, and reject overlong injected STS results.
2. **Signed result accepts a non-exact authority binding** — **confirmed, high**: `validate_signed_lock_result()` delegates to a validator that permits `P5R0AuthorityV3`, then compares only key version and public-key fields against activation; different authority IDs, transport metadata, or a legacy schema can pass. Require the exact self-custodied `P5R0PublicAuthorityV4` object and invoke the full KMS binding validator before accepting the response.
3. **Activation bypasses the fresh KMS/IAM boundary** — **confirmed, high**: the new KMS/IAM/capability validators are not called by adapter activation, while activation can perform STS, IAM impersonation, KMS public-key retrieval, and GCS/KMS client construction. Keep the local process side-effect-free and require validated external binding receipts before any capability construction, or explicitly scope activation out of this task.
4. **Short-lived capability validation lacks provenance binding** — **confirmed, high**: `validate_short_lived_capability()` proves only that an arbitrary bearer token expires no later than an arbitrary source token and accepts any syntactically valid service-account argument; it does not prove derivation from the source or bind the token to the validated capability service account. Carry the source/token digest and exact service-account binding through the capability factory and receipt.
5. **Default review inputs are not reproducible** — **confirmed, high**: `DEFAULT_REQUEST` and `DEFAULT_RS068_PROPOSAL` point under ignored `var/`, so the validator passes only in a populated worktree and fails in a clean checkout. Track the canonical inputs or provide a deterministic tracked generator/fixture before treating the local process as rerunnable.
6. **AMD SEV and Secure Boot are configuration-selectable** — **confirmed, high**: `P5R0_EXPECTED_HARDWARE_MODEL` accepts arbitrary non-empty values and `P5R0_EXPECTED_SECURE_BOOT=false` is allowed, so a policy can authorize claims that do not meet the required AMD SEV/Secure Boot posture. Hard-bind the required hardware and boot values before accepting attestation.

<summary>Details</summary>

### Local-only process versus activation side effects

**Confirmed, high.** The `signed_environment_process.py` path reads canonical artifacts and consumes already-produced objects; it does not call `sign_digest`, create credentials, or invoke KMS, GCS, IAM, VM, or FreeTSA APIs. The boundary is different for `ConfidentialSpaceAdapter.activate_attested_service()`: after launcher verification and STS exchange it calls `CapabilityFactory.build()`. With production configuration, `_impersonate()` invokes IAM Credentials, `_kms_client()`/`KMSEd25519Signer` construct a KMS client and read the KMS public key, and a GCS client is constructed; timing bridge/FreeTSA access remains lazy until timing is recorded. The new `validate_kms_binding()` and `validate_capability_binding()` functions are not imported by any production path, so no fresh external KMS/IAM observation is required before activation.

### Source-bounded lifetime is weaker than the claim

**Confirmed, blocker.** `AttestationGate.verify_startup()` verifies the attestation `exp`, but `_build_verified_attestation_binding()` only checks that the federated token is not already expired. The adapter then stores the capability expiry, or the STS expiry, in `_expires_at`; it never includes the attestation expiry. The existing fake STS used by the tests returns an expiry far beyond the attestation window, and activation succeeds, demonstrating that the live adapter can outlast its source evidence. The separate `validate_attested_activation()` check for a maximum one-hour federation window does not repair this because activation does not call it.

**Confirmed, high.** `validate_short_lived_capability()` checks bearer shape and expiry ordering, but token contents have no lineage or audience field, and the returned receipt carries no source digest or validated capability-binding digest. An arbitrary bearer token with an earlier expiry and an arbitrary valid service-account string is accepted as source-bounded. The acceptance contract needs to bind the effective token to the exact source/capability observation, not only compare timestamps.

### Exact KMS authority and lock binding

**Confirmed, high.** `validate_kms_binding()` requires `P5R0PublicAuthorityV4`, self-custody labeling, the configured key version, matching public key, transport metadata, and the `P5R0KMSAuthorityBindingV1` structure through `validate_candidate_binding()`. The frozen RS-065 validator preserves the exact unsigned lock digest and verifies a future signature over that digest without creating one.

**Confirmed, high.** The signed-result consumer does not use that strict path. `validate_signed_response()` accepts both V3 and V4 authorities. `validate_signed_lock_result()` then checks only `response.kms.key_version` and the response authority public-key/digest pair against `adapter.config.authority`; it does not compare the full authority object, require V4/self-custody, or validate the returned KMS authority binding against the activation policy. A response can therefore be internally self-consistent and correctly sign the exact lock while carrying a different authority ID, key ID, transport binding, or legacy schema.

### Required hardware posture and validation coverage

**Confirmed, high.** The adapter gate requires nonce, issuer, temporal claims, image/project/zone, TEE, hardware model, Secure Boot, debug, workload, and smoke claim paths before capability creation, and the evidence schema is closed. However, `P5R0_EXPECTED_HARDWARE_MODEL` is accepted as any non-empty configured value and `P5R0_EXPECTED_SECURE_BOOT=false` is allowed, so configuration can authorize a non-AMD or non-Secure-Boot posture rather than enforcing the required AMD SEV/Secure Boot posture. The production policy should hard-bind those values if DISPATCH-050 requires AMD SEV with Secure Boot.

**Confirmed, high.** The targeted test run passes (`53 passed`), including local contract blocking, malformed capability/KMS observations, caller-boolean rejection, claim mismatch, and adapter evidence checks. It does not test activation with an STS expiry beyond attestation expiry, a V3 or mismatched full authority in `validate_signed_lock_result()`, capability-token provenance/service-account mismatch, or the no-network/no-cloud-call guarantee. Those cases should be covered before relying on the validators as the execution gate.

### Ignored review artifacts

**Confirmed, high.** `DEFAULT_REQUEST` resolves to `var/p5-r0-diagnostic-inputs/public/lock-signing-request.json`, and `DEFAULT_RS068_PROPOSAL` resolves to the corresponding ignored proposal. `.gitignore` ignores `var/`; the current worktree has the files, but a clean checkout does not. The local process therefore cannot be rerun from repository contents alone and should either use tracked canonical artifacts or a deterministic tracked generator.
