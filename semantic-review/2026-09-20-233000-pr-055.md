# Verifier-owned signed-environment readiness hardening

This change replaces the former caller-controlled readiness boolean and evidence mapping with a `VerifiedCredentialReadinessEvidence` object assembled from Confidential Space activation, a source-bounded capability receipt, and reviewed IAM credential validation. The transition API rejects the old keyword and plain dictionaries, while the checked-in packet remains unresolved with approval disabled, so no IAM mutation is reachable in the repository state. **confirmed** the implementation still has a provenance gap: Python callers can allocate the exact evidence type with `object.__new__`, recompute its public digest, and pass readiness; the public transition also accepts its packet-binding contract as a caller-supplied mapping. **Watch for:** **confirmed** a recomputed synthetic evidence object is accepted as `verified`; **confirmed** the focused tests do not exercise this bypass or make binding/expiry assertions reach their intended checks; **confirmed** real signed-environment and downstream P5 evidence is absent.

**Verdict**: NEEDS_CHANGES

## High-level view

The old `provenance_verified`/plain-mapping seam is removed. **confirmed**, the replacement is not an unforgeable verifier capability: a same-process caller can synthesize an exact-type object with a valid commitment and promote readiness.

The evidence factory composes Confidential Space activation, STS/capability lifetime checks, exact provider/image/audience/account/authority bindings, and the reviewed IAM adapter. **confirmed**, the standalone transition still receives `expected` as a caller-controlled mapping rather than deriving the packet contract internally.

The 99 focused tests cover the adapter-backed happy path, legacy-input rejection, binding drift, token lifetime, executor gating, rollback, and no-retry behavior. **confirmed**, evidence-specific negative cases leave the seal stale, so they prove seal-integrity rejection rather than semantic binding or expiry rejection.

The checked-in packet and approval remain blocked. **confirmed**, release still requires external signed-environment and downstream P5 evidence; repository fixtures cannot satisfy those gates.

### The evidence type is sealed only against ordinary construction

**confirmed** — `VerifiedCredentialReadinessEvidence.__init__` requires the module-private `_EVIDENCE_SEAL`, and the transition requires the exact class plus a commitment check. Passing `provenance_verified` raises `TypeError`, and a plain `dict` is rejected.

The commitment is a deterministic digest over public fields, and the dataclass is allocated with ordinary Python mechanics. A caller can copy a legitimate fixture into an `object.__new__` instance, recompute `seal_digest` with `_commitment`, and pass the exact checks:

```text
forged exact type: True
constructor seal recomputed: True
transition: verified
```

That object was not returned by `build_verified_credential_readiness_evidence`, did not come from verified Confidential Space activation, and did not come from `validate_short_lived_capability`. `CapabilityReceipt` has the same constructor-level weakness: `_CAPABILITY_RECEIPT_SEAL` is not an in-process provenance proof. The factory’s normal type checks therefore do not establish the claimed “only verified paths can produce it” property.

### The standalone transition does not own the current packet contract

**confirmed** — `transition_credential_readiness` receives `expected: Mapping[str, str]` and checks only that evidence fields equal it. `validate_iam_boundary` does derive `expected_credential` from the checked packet and fixed constants for the normal repository path, but the exported transition and evidence factory let a caller define the packet digest, evidence digest, provider, image, audience, principal, target resource, authority digest, service account, and capability binding. A sealed packet-bound contract or internal derivation would make the public promotion API independently enforce REVIEW-055’s current-environment binding.

### The test matrix validates rejection, but not the semantic gates it names

**confirmed** — the focused run is green at 99 tests and includes a helper-backed adapter/STS/capability fixture, old-argument and lookalike rejection, wrong provider/image/audience/authority/account cases, expiration cases, and the executor no-call gate. The parametrized evidence test uses `_tamper` without updating `seal_digest`; every case exits at `evidence seal digest drift`. It therefore does not prove that a correctly committed wrong binding or correctly committed expired attestation/source/capability is rejected by the intended checks. The recomputed-forgery case is absent.

### Repository boundary and remaining prerequisites

**confirmed** — the packet says `required_but_not_injected`, approval is disabled, `cloud_operations` is empty, and `execute_reviewed_iam` requires both a ready report and exact evidence before loading definitions or calling the executor. The protected runsheet, superseded packet, and R18R12 approval paths have no tracked diff in the current worktree; they appear as pre-existing untracked artifacts rather than implementation edits. Focused tests, compileall, and diff-check pass, but local results do not create external authority or credentials.

The exact outstanding prerequisites are: reviewed candidate image and Confidential Space deployment binding; canonical WIP provider, claim mapping/condition, and STS audience; a real launcher JWT with nonce, time, issuer, TEE, Secure Boot, AMD SEV, debug, workload, image, project, zone, and smoke claims plus signature verification; STS exchange and the exact GCS-only IAM-Credentials token-creator grant; a source-bounded short-lived credential with no key material or ADC; fresh least-privilege IAM prestate and exact poststate/receipt; existing evaluator KMS key-version/public-key observation and self-custodied authority binding; and a fresh child approval bound to unchanged packet and authority digests. The later sequence still needs an authenticated GCS receipt, exact KMS signature, independent timing evidence, supervisor/resource and append-only receipt-chain evidence, persisted verified result seal, and upstream P0-A/P0-E1/P0-E2/P1–P4 release gates.
