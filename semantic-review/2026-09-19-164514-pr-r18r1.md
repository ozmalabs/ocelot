# Fail-closed RS-069R18R1 operation-2 WIP mapping handler

R18R1 adds a separate operation-2 handler for replacing the WIP provider claim mapping, with an opt-in apply gate, exact pre/post-state checks, etag-guarded rollback, and a hash-chained redacted ledger. The handler is not imported or dispatched by the legacy RS-069 runner, and its command builders limit execution to provider describe/update/describe; operations 3–7 remain disabled. The focused adversarial suite passes 74 tests, but it exercises helpers rather than an actual mocked execution boundary. **Watch for:** **confirmed** — attestation and master approval are caller-supplied, not authenticated artifacts; **confirmed** — unresolved mapping/condition values can pass the remote-prestate validator; **confirmed** — terminal ledger-write failure can escape after a mutation/rollback attempt.

**Verdict**: NEEDS_CHANGES

## High-level view

The operation-2 topology is single-purpose: explicit enablement and one exact scope gate a full provider prestate capture, one internally constructed update, and desired poststate verification. No caller-provided shell command is accepted, and operations 3–7 are reported as skipped rather than dispatched.

**Confirmed:** the gate is structurally strict but not authoritative: `review_state`, approval flags, approval identity, attestation claims, and their digests arrive as ordinary function arguments. The checked-in R17 packet still has unresolved provider and attestation inputs, so no real R18R1 apply is authorized; a fresh master approval must bind independently supplied evidence before enablement.

**Confirmed:** prestate equality, poststate mapping/condition digests, etag-guarded rollback, and ledger chaining define the intended mutation boundary, but the unresolved-marker check does not cover all prestate values and failure logging itself is not failure-contained.

<summary>Details</summary>

### Single-operation WIP mutation boundary

`execute_operation_2` requires `apply_enabled is True`, repository-root execution, fresh review state, an exact operation-2 scope, and all binding checks before the first describe. The command path is assembled internally from the canonical provider/project/pool/location and reviewed mapping/condition; `_run_json` uses argv without a shell and closes stdin. The handler has no call to the legacy runner and returns the fixed later-operation list as skipped.

### Prestate, poststate, and rollback binding

The observed prestate is canonicalized into provider identity, project/pool/location, fingerprint, mapping, condition, component digests, and a configuration digest. `validate_prestate` validates both objects and requires complete equality before update; poststate validation binds mapping and condition to the reviewed desired-state digests. Rollback uses the same update builder with the current etag and then verifies restored configuration, allowing the provider fingerprint to change while requiring the original configuration.

**Confirmed:** the unresolved-value invariant is incomplete at this boundary. `_state_from_gcloud` requires a nonempty condition and string mapping values but only checks for the `REQUIRED_INPUT` substring in the condition; `_validate_state_integrity` repeats the permissive checks. A state containing `attributeMapping.google.subject = "UNRESOLVED"` and `attributeCondition = "UNRESOLVED"` is accepted and can become the expected prestate, so the handler can proceed from an unresolved remote observation. Apply the same strict unresolved-marker rejection to every mapping key/value and the condition in both canonicalization and integrity validation.

### Attestation and approval provenance

`_validate_claim_record` closes the record, binds its evidence payload and digest, and requires exact project, zone, image, issuer, TEE, security, workload, and audience values. **Confirmed:** those checks establish self-consistency, not provenance: the positive test constructs the entire record locally, and no signature, verifier identity, certificate chain, nonce/freshness check, or trusted Confidential Space output is required. The unresolved R17 packet can therefore be paired with a caller-created record unless an external gate prevents it.

**Confirmed:** the same issue applies to review authorization. The handler accepts the literal `review_state == "master_reviewed"`, four booleans, the fixed approval ID, and an approval-record digest calculated from the supplied record. It does not load or authenticate a master decision, and the repository contains no `APPROVAL-004-RS069R18R1` artifact. Before retry, independent master/security review must produce an authenticated approval bound to the exact request scope, candidate image, provider resource/digest, attestation evidence digest, claim paths, template, mapping/condition digests, and disabled later operations.

### Ledger terminal behavior and execution coverage

The normal path records start, prestate, verification or failure, and stop in the chained ledger, while the broad operation exception path attempts rollback for ordinary post-update failures. **Confirmed:** its subsequent failure/stop `_ledger_event` calls are not contained. A ledger I/O failure after mutation can therefore escape after rollback has been attempted without recording the terminal state, which requires explicit manual review and no retry.

**Confirmed:** the 74 tests cover binding drift, provider/audience separation, candidate/evidence equality, rollback command construction, disabled later operations, hash chaining, redaction, absolute gcloud argv, and closed stdin, but they do not call `execute_operation_2`; mocked execution coverage is still needed for approval rejection before describe, update failure, poststate mismatch, rollback verification/failure, and ledger persistence failure.
