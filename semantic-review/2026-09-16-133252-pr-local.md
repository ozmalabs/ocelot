# Fixture-derived P4 local container readiness

The repaired rootless Podman/crun path was exercised with fresh scratch images and the native ELF worker for both public records, `fx-0001` and `fx-0002`. Each run reached native completion, consumed the image-owned fixture bundle, emitted a signed release/replan/action chain, bound receipts to that case’s record digest, returned `no_go` as required, and restored the exact pre-run snapshot; only the two generated image digests were removed afterward. **Watch for: confirmed — `fx-0002` is not selectable through the production preregistration path and required a temporary in-memory selection override, so the two-case result is not yet evidence from the unmodified case-selection contract. confirmed — the declared mechanics arms are metadata only: there is no arm/control input or trace output, so causal/replan behavior has not been shown to differ under mechanics controls.**

**Verdict**: NEEDS_CHANGES

## High-level view

The native container boundary is working for the exercised records: the image embeds the worker, trust artifact, and fixture; the run is rootless, pull-free, networkless, read-only, capability-dropped, and private-PID under crun. Both cases produced complete native execution and then the mandated non-promotional `no_go` result, with exact rollback and narrowly scoped image cleanup.

For each case, the signed task release, replan, proposal, grant, action, outcome, terminal, result, and rollback records all carry the same fixture selection and record digest, and the proposal parent equals the replan receipt. This proves binding and lifecycle behavior for the two executed records, not trusted release readiness.

The experiment still lacks the requested control comparison. `ARMS` is declared in the lock, but `run_local`, the evaluator, and the native request have no arm/mechanics-control parameter or trace contract; moreover, the production lock helper always selects `fx-0001`, so `fx-0002` was reached only by an out-of-band test override. These gaps prevent approval of semantic fixture-derived local readiness as a reproducible two-case, controls-driven gate.

## Native worker consumed both image-owned fixture records

The clean temporary runs built digest-addressed scratch images from the local worker, trust artifact, fixture bundle, runtime closure, and repaired seccomp profile. Podman reported rootless operation and crun 1.14.1; the launch policy used `--pull=never`, `--network=none`, `--read-only`, dropped all capabilities, no-new-privileges, private PID, fixed UID, and the locked seccomp profile. Each native worker returned the complete reply rather than a containment impasse, which confirms that the worker read and validated the fixture bytes at the image path rather than relying on the host fixture path.

`fx-0001` materialized as selection `sel-3776ae79d2fea517` with record digest `sha256:f200a3181cd63fa810b45ec4946584422ba768f98f3268c0b3c4a042b09df655`. `fx-0002` materialized as selection `sel-f48582d4b9556554` with record digest `sha256:37ed2aba5c9ebbbeedb9244da2263303af76f26b319563f9f49547625c1946d7`; its actions and observations are currently identical to `fx-0001` apart from the fixture key, so these two records cannot by themselves establish a semantic mechanics difference.

## Signed receipts bind the record and causal parent

The receipt files were independently re-read through `P4ReceiptLog`, which verified canonical encoding, hash chaining, and signatures. Both runs produced the same semantic chain shape: `task_release`, `replan`, `proposal`, `grant`, `action`, `outcome`, `terminal`, `result`, and `rollback`. Every receipt payload carried its run’s exact record digest and selection ID; the proposal causal parent matched the replan receipt hash, and proposal/outcome payloads retained that record digest through the native handoff.

The result remains local-only: both runs intentionally report `classification: local_readiness_only`, `outcome: no_go`, `adopted: false`, and `promotion_authority: false`.

## Exact rollback and scoped cleanup

Each evaluator restored the canonical pre-run graph snapshot and reset simulator-call state to zero after native completion. The temporary validation removed only the two image digests it created; it did not prune unrelated images or alter repository files. The focused P4 suite also passed all 40 tests.

## Declared arms do not produce comparable mechanics traces **confirmed**

The lock declares `graph_planner`, `reactive_no_plan`, `no_causal_model`, `reset_memory`, and `search_budget_matched`, but they are not accepted as inputs by `run_local` and are not represented in the native request or receipt trace. The only observed differences between the two real runs are run/lock/fixture identities and receipt hashes; the causal/replan event shape is identical. A controls-driven claim therefore needs a new executable control contract and explicit trace evidence rather than the current arm list.
