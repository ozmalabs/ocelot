# DISPATCH-069 Track A final-gap hardening

DISPATCH-069 hardens the repository-only Track A runner around the main REVIEW-068 findings: receipt/result digest cross-binding, replay-resistant run identity, V3 receipt reload, failure closure, persisted seals, explicit diagnostic-only status, and activation commitments. The implementation now verifies the normal receipt chain and result seal before producing its signed-looking synthetic output, and its 19 adapter-backed tests exercise the new adversarial paths. The full evaluator suite passes 468 tests, but the repository still has no real signed-environment execution evidence. **Watch for:** **confirmed** capability activation is called before the runner validates the registered attestation and does not receive all provisioned input commitments; **confirmed** failure validation allows rollback/close without an `impasse` receipt required by Track A; **confirmed** real Confidential Space, FreeTSA, native supervisor, durable input, and non-exportable KMS evidence remain unavailable.

**Verdict**: NEEDS_CHANGES

## High-level view

The receipt and result path now has a meaningful cryptographic closure: V3 records are reloaded from durable storage, their links and signatures are recomputed, the receipt result digest is checked against the canonical result, and the persisted result seal is verified before final signing. Task/control envelopes also carry the active run identity, and synthetic results are explicitly non-promotable.

**Confirmed.** The activation boundary is not closed end to end. The adapter is asked to construct capabilities before the runner validates its registered attestation, while the activation commitment carries the lock, manifest, private store, selection, and provisioning digests but not the public-input and access-binding digests. The verifier-owned adapter contract must enforce attestation first and bind the complete generated-input set before capability construction.

**Confirmed.** Failure cleanup now has cross-linked rollback and close receipts plus a durable impasse seal read-back, but its acceptance predicate does not require an `impasse` event in the append-only failure chain. The implementation therefore blocks malformed links and seal drift while still permitting an incomplete failure lifecycle.

### Receipt/result closure and synthetic status

The prior result-digest gap is addressed: `_validate_receipts()` verifies the V3 schema, record hashes, signatures, previous links, preregistration link, required event coverage, recomputed chain digest, and the receipt’s `result_digest`; after the canonical result is created, the runner compares that receipt digest with `_canonical_result_digest(result)`. The result seal is persisted, read back, structurally revalidated against the canonical result and chain head, and verified before the final binding is signed. The public result exposes the timing, input, attestation, closure, supervisor, KMS, receipt, and seal commitments required by the Track A diagnostic schema.

The successful structural fixture returns `diagnostic_only` with `production_promotable=false`, and production promotion is rejected without a real KMS capability marker. The local Ed25519 client and test supervisor therefore remain test seams, not signed-environment evidence.

### Activation ordering and generated-input commitments

**Confirmed.** The runner obtains `capabilities` from `activate_attested_capabilities(activation_commitment)` at `track_a.py:816`, then calls `_validate_attestation()` at `track_a.py:822`. This leaves the ordering guarantee inside an unverified adapter method: a structurally valid adapter can construct execution, timing, worker, and signer capabilities before the runner has validated the registered binding and startup evidence. Track A requires verified attestation before capability activation, not merely before rehydration.

**Confirmed.** `_activation_commitment()` binds `lock_digest`, `manifest_digest`, `private_store_digest`, `selection_digest`, and `provisioning_digest`, but not the already validated `public_input_digest` or `access_binding_digest`. A capability can consequently be activated against a different public-input or access path while the later rehydration check still validates only the adapter’s returned rehydration object against the provisioned values. Add all generated-input/access commitments to the pre-activation contract and make the returned attested capability prove the same commitment.

### Failure-chain closure and durable impasse seal

The new failure path validates a closed receipt shape, run identity, rollback and close cross-links, reloads the V3 chain from its durable root, checks record signatures/sequence/previous hashes, and persists/reads/verifies the impasse seal.

**Confirmed.** The final kind check is `{"rollback", "close"}.issubset(failure_kinds)`. It does not require `impasse`, even though REQ-EVID-003 requires every impasse event in the signed chain and REQ-FAIL-003 requires rollback/impasse evidence before closure. A response containing only rollback and close records can pass `_validate_failure_closure()` and receive a verified impasse seal.

### External execution frontier and protected artifacts

**Confirmed.** Repository tests establish protocol behavior only. The CLI has no adapter factory and returns a typed blocker, so no external operation or fabricated production result is hidden by this implementation. The remaining real prerequisites are: a verifier-owned Confidential Space launch with Google-signed claims bound to the exact image, lock, policy, and generated inputs; post-attestation durable input read and fresh-process private-store rehydration; a live pinned FreeTSA RFC-3161 timing record and durable timing ledger; native worker execution through the locked crun/seccomp/resource closure with independently authenticated supervisor/OOM/deadline evidence; durable canonical receipts and result/impasse seals; and a non-exportable KMS authority producing the final signature over the exact verified binding. No cloud, FreeTSA, KMS, GCS, credential, or protected-artifact mutation was performed during this review.

The implementation files are the newly untracked `services/p5_r0_evaluator/track_a.py` and `services/p5_r0_evaluator/tests/test_track_a.py`.
