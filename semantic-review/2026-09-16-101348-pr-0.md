# Evaluator-signed outcomes remain disconnected from P4 runtime

The candidate adds a concrete Rust verifier for canonical evaluator-signed P4 outcomes and keeps the completion capability opaque. In the isolated Rust path, canonical parsing, installed authority/key/lock matching, Ed25519 verification, and native reservation binding all happen before the capability is minted; the focused suite confirms valid completion and rejection of forged, malformed, altered-binding, and replayed transports. **Watch for: [confirmed] no non-test runtime component calls this entry point, and the Python evaluator, local lock, and Rust fixture use incompatible key identities, so a real evaluator outcome cannot currently reach native P4.** The local runner also deliberately terminates before native stdio exchange, retaining no-go-only status. **Verdict**: NEEDS_CHANGES

## High-level view

The verifier is a well-contained trust boundary: untrusted serialized JSON is canonicalized and authenticated against an authority installed outside the payload, then checked against persisted native action state before it can advance P4. The opaque completion object is not public-convertible or serializable, preserving the intended authority boundary within Rust.

The boundary is not connected to an executable runtime topology. The only call sites are Rust unit tests, while `run_local` validates containment and then unconditionally reports `native stdio protocol not yet attested`; it never obtains or passes a signed transport to Rust.

The three identity sources also diverge: the Python evaluator signs as `p4-r0-receipt-log`, local locks identify an ephemeral `p4-r0-ephemeral-local-test-key`, and the Rust positive fixture trusts `p4-r0-local-test-key`. A production bridge must establish one installed trust record from the same signer used to emit the transport.

## Signature verification precedes opaque completion capability

`seal_serialized_evaluator_outcome` accepts only byte-for-byte canonical JSON, removes the signature from the canonical object to form the signed payload, and compares the signed authority ID, key ID, public key, and lock digest with `P4TrustedEvaluatorAuthority`. It then verifies the Ed25519 signature over the SHA-256 prehash before deriving persisted native expectations. The crate-private adapter is the sole minting site for `VerifiedActionOutcome`; it additionally requires matching run, proposal, receipt-chain, sequence, snapshot, reservation, and outcome bindings before `advance_p4_r0` can complete.

With the local Python embed-link settings, the focused Rust suite passes: a valid transport returns `Complete`; tampered signature, missing field, noncanonical encoding, validly signed altered reservation digest, and replay all fail. Authority-boundary integration tests also show downstream callers cannot construct, deserialize, or convert the capability.

## P4 verifier has no runtime caller

**[confirmed]** The public `advance_signed_evaluator_outcome` is compiled in the normal library, but the only repository invocation is `p4_evaluator_adapter_tests`, which is itself included only under `cfg(test)`. The Python-side runtime does not bridge to it: after containment checks, `run_local` deliberately raises `native stdio protocol not yet attested`, records an impasse and a non-promotional no-go result, and restores the pre-run snapshot. This leaves the positive Rust test as a test seam rather than evidence that a signed evaluator transport completes native P4 in a deployed local flow.

Add a real, non-test worker protocol that installs the trusted evaluator authority, forwards the canonical signed transport and matching observation to `advance_signed_evaluator_outcome`, and emits the resulting native decision. Test that path end to end from `P4R0Evaluator.serialized_verified_native_outcome` rather than from a separately hard-coded Rust fixture.

## Evaluator and verifier trust identities do not align

**[confirmed]** `P4R0Evaluator.serialized_verified_native_outcome` labels its signing key `p4-r0-receipt-log` and embeds the receipt-log public key. `preregister_local` instead generates a fresh lock key under `p4-r0-ephemeral-local-test-key`, while the Rust successful test constructs `P4TrustedEvaluatorAuthority` with `p4-r0-local-test-key` and an unrelated fixed public key. Since Rust requires exact authority ID, key ID, public-key, and lock-digest equality before verifying a signature, there is no demonstrated configuration by which the Python evaluator output can pass the Rust verifier.

The bridge must define a single authority record—key ID, public key, and lock digest—from the evaluator signing authority and install that record at native launch. An end-to-end test should prove that a transport emitted by Python verifies in Rust, then separately prove rejection after changing each binding.

## Containment remains local no-go only

**[confirmed]** Podman 4.9.3 is available and rootless on this machine, and its policy requests a pinned local image with `--pull=never`, no network, a read-only filesystem, dropped capabilities, and a signed closure. That does not provide trusted release evidence: the runner cannot reach the native protocol and is intentionally hard-coded to return `classification: local_readiness_only`, `outcome: no_go`, `adopted: false`, and `promotion_authority: false`. Bounded local P4 readiness is therefore not approved until the runtime bridge and unified trust binding exist; nothing here authorizes adoption, promotion, or trusted-release execution.
