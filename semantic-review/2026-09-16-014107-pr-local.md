# P3-R0 local readiness gate

P3-R0 adds a signed release-lock format, a proposal schema intended to confine changes to `mutable-agent/`, finite-study/statistical helpers, signed receipts, and byte-level rejection rollback. It is documented as local-only scaffolding that should fail closed until an external P2-go and P0/P1 evidence package are available. **Watch for:** **confirmed** the coordinator bypasses both proposal validation and the sequential evaluator/study path, accepts unsigned and unbound P0/P1 evidence, and immediately rolls back; **confirmed** the required adversarial cases do not exercise their named attacks or any Podman boundary. **Verdict**: NEEDS_CHANGES

## High-level view

The signed lock and isolated proposal validator are not on the path that receives a learning proposal. Once preflight succeeds, `P3R0Runner` treats the proposal as receipt metadata and copies the pre-snapshot over the candidate without validating or staging it. **Confirmed concern:** immutable control-plane confinement is not enforced by the live coordinator.

The study implementation can construct 12 × 30 signed envelopes and calculate per-distribution statistics, but it is disconnected from the runner. No component supplies only the next task, preserves evaluator-private material across a worker boundary, collects the four R0 arms, or produces the sealed evidence the preregistration describes. **Confirmed concern:** this is helper code, not real sequential evaluator-owned evidence.

The documented P3-E1 decision requires a hierarchical aggregate bootstrap, eight improving distributions, no harms, and retention, transfer, safety, resource, custody, and rollback conditions. The implementation only classifies individual distributions and has no adoption-decision function; R0 itself always rejects. **Confirmed concern:** the stated adoption/rollback rule cannot be evaluated or enforced.

P3 accepts any mapping carrying the expected P0/P1 schema and `passed` status, without a signature, digest, or lock binding. The focused tests pass, including a parameterized mutation test, but that test causes a generic proposal-schema rejection before the named attack is examined and no test launches or inspects a Podman workload. **Confirmed concern:** containment evidence and adversarial boundary coverage are not real gate evidence.

## Control-plane lock is not enforced by the coordinator

`validate_learning_proposal` and `validate_staged_proposal` can reject forbidden names and locked digests, but that boundary never reaches `P3R0Runner.run`: after `verify_preflight`, the runner sends the caller-provided proposal digest directly into `reject_and_rollback` (`evaluation/p3/runner.py:14-19`). It neither calls `validate_staged_proposal` nor `stage_isolated_candidate`, and `verify_preflight` compares the caller-supplied `candidate_digest` string with the lock but never hashes `request.candidate` (`evaluation/p3/admission.py:19-30`). **Confirmed concern:** a request carrying a control-plane-referencing proposal or a candidate whose bytes differ from the declared locked digest reaches the live success-preflight branch rather than being denied before staging, contrary to the frozen boundary in `evaluation/p3/PREREGISTRATION.md:9-11`.

Make validated proposal confinement, candidate-byte binding, isolated staging, and lock-preserving verification prerequisites of every runnable path, rather than independently callable helpers.

## Evaluator-owned release remains a disconnected in-memory package

`materialize_study` returns all 360 envelopes grouped in a `public` dictionary, with private commitments in another caller-visible return value (`evaluation/p3/study.py:16-30`). `release_next` only advances a caller-owned `set` over one caller-selected distribution (`evaluation/p3/study.py:32-37`). There is no evaluator service, worker interface, authenticated release state, or runner invocation of either function. **Confirmed concern:** the code does not enforce next-only release, evaluator-private task order, or non-enumerability in an execution; any holder of the return values can enumerate the entire package, including the private map.

This conflicts with the preregistration’s claim that the worker receives only the next envelope and cannot enumerate, replay, reorder, or reread releases (`evaluation/p3/PREREGISTRATION.md:7`), and with its statement that R0 runs four matched arms, seals their records, and computes a report (`evaluation/p3/PREREGISTRATION.md:23-25`). **Confirmed concern:** the local-only disclaimer is scope-correct, but the operational R0 description overstates what this diff delivers. Either implement the release authority, arm execution, and sealed 30-pair record, or revise those passages to describe a planned P3-E1/R0 execution rather than a current gate.

## P3-E1 adoption rule is specified but cannot be decided

The per-distribution functions compute a 30-pair bootstrap, sign-permutation values, Holm adjustments, and a local classification (`evaluation/p3/study.py:41-79`). `seal_results` produces records for all 12 distributions, but it never calculates the preregistered aggregate or evaluates the required eight-improve/no-harm, retention/interference, transfer, safety, resource, custody, or rollback predicates (`evaluation/p3/PREREGISTRATION.md:19-21`). **Confirmed concern:** a seal can be emitted without an implementation of the stated P3-E1 pass/no-go rule, so no later adoption authority can rely on it as proof the rule passed.

Implement the complete locked P3-E1 predicate behind the separately authorized evaluator path and test both pass and each mandatory no-go condition; R0 must remain no-adoption.

## Podman evidence is a status field, not verified containment evidence

P3 preflight accepts `provisioned_evidence` solely when it is a mapping with `schema == "P0P1ProvisionedEvidenceV1"` and `status == "passed"` (`evaluation/p3/admission.py:24-25`). It neither verifies a signer nor binds an evidence digest, container/image profile, inspected restrictions, or acceptance result to the release lock. **Confirmed concern:** an arbitrary caller can manufacture the two fields and reach the branch intended for provisioned containment evidence.

The focused P3 suite does not run the gated Podman acceptance case, and no P3 code consumes its actual evidence. Bind a trusted, signed profile-specific P0/P1 artifact into the release lock and verify it at preflight; add a provisioned integration case that proves the P3 task worker preserves no-network, read-only, no-mount, rootless, and resource restrictions.

## Adversarial fixtures only prove an extra field is rejected

Every parameter of `test_adversarial_control_plane_mutations_deny` adds the same unexpected `nested` top-level field to an otherwise valid proposal (`tests/evaluation/test_p3_control_plane.py:8-11`). The schema validator requires an exact top-level key set, so each test fails before the attack string is semantically assessed (`evaluation/p3/protocol.py:44-45`). **Confirmed concern:** the passing parameterization does not validate writable remounts, score/result reads, key substitution, receipt disruption, broker compromise, protected-constraint violations, unchanged control digests, zero effects, or rollback.

Tests exercise helpers and a missing-P2 denial, but none executes four matched arms, a release sequence, receipt ordering/tamper, or the Podman profile. Replace the schema-only fixture with attack-specific mutations at the relevant boundary and assert the complete required outcome for each.
