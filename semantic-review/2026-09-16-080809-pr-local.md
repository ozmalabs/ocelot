# Sealed P4 effect boundary with local-only containment

This change introduces a signed evaluator-side proposal → grant → broker-action → outcome chain, lock-bound resource reservations, and a Podman-only containment preflight for P4-R0. The Python boundary correctly validates the chain before exposing native outcome fields, debits each signed reservation cumulatively, and rejects changed, extra, or symlinked staging inputs. The local runner cannot execute without a rootless Podman preflight against a locally present digest-pinned image, and on every containment failure it emits an impasse/no-go result and rolls the graph back. **Watch for: confirmed — the Rust state machine accepts a publicly constructible `VerifiedActionOutcome` containing only caller-supplied digest strings, so it can complete without the evaluator having verified the signed receipt chain.**

**Verdict**: NEEDS_CHANGES

## High-level view

The evaluator is the substantive enforcement point for the Python path. It requires a signed local lock and receipt log before granting, binds proposal, proposal-receipt, grant-receipt, broker-receipt, sequence, snapshot, and reservation into the sealed outcome, and enforces exact cumulative actions, risk, and transaction limits.

Containment is lock-bound rather than path-bound: worker, agent tree, input tree, seccomp profile, and Containerfile are recursively digested from a non-symlink staging root and rechecked before Podman preflight and argv construction. The available rootless Podman installation does not contain the test digest, so the runner takes the prescribed local-only impasse path rather than pulling, building, or falling back to host execution.

The native API does not preserve the Python boundary’s authority model. Its exported input includes a public `VerifiedActionOutcome` with public string fields, and the native transition checks only shape and consistency of those strings; it cannot distinguish an evaluator-verified record from one fabricated by its caller.

## Evaluator receipt chain and reservation accounting

`P4R0Evaluator.grant` requires both the signed local lock and evaluator receipt log, rejects action kinds outside the lock allowlist, requires a causal replan receipt with the same run, lock, fixture, and graph snapshot, and reserves the requested actions, risk, and transactions against the three signed ceilings. The reservation counters are cumulative and the action token is removed before an action can be repeated. `act` carries the proposal, proposal-receipt, grant-receipt, broker-receipt, sequence, snapshot, and reservation into an evaluator-signed outcome receipt; `verify_sealed_action_outcome` reconstructs and compares every expected binding before `verified_native_outcome` returns native fields.

The adversarial tests cover expiry and grant replay before simulator entry, unallowlisted kinds, forged causal parents, over-reservation, cumulative reservation exhaustion, receipt binding tampering, and Python-side receipt exposure.

## Forgeable native verified outcome

**Confirmed:** `runners/dsl/src/p4_readiness.rs` exports both `VerifiedActionOutcome` and the `verified_action_outcome` field on `SealedObservation` with public fields. `advance_p4_r0` treats an outcome as verified if the caller supplies digest-formatted values that are mutually consistent with native state; it has no signature, receipt-log, evaluator-key, or opaque capability check. No production adapter found in the changed sources constructs this type from `P4R0Evaluator.verified_native_outcome`; the only usage is the test, which directly builds `valid_outcome()` and reaches `P4Decision::Complete`.

That leaves the claimed effect boundary dependent on a comment and caller discipline. A caller with access to the public Rust API can first supply a chosen action-proposal digest at phase 2, then construct a matching `VerifiedActionOutcome` with arbitrary digest-shaped receipt values and complete phase 3. Receipt binding must remain enforced at the exact transition that authorizes native completion: make the verified type opaque and constructible only by a trusted adapter that verifies the signed Python receipt chain, or serialize the sealed outcome and verify the receipt signatures and bindings in Rust before state advancement. Add a test that attempts direct construction or an unverified adapter input and proves it cannot complete. 

## Lock-bound staging and fail-closed local execution

The lock signs recursive digests for worker, agent, input, seccomp, and Containerfile inputs. Staging rejects symlink roots and entries, enforces containment under the staging root, includes every tree entry in the digest, and preflight/argv repeat closure validation. Podman is constrained to the fixed entrypoint, rootless mode, digest-pinned locally available image, no pulls, no network, read-only filesystem, dropped capabilities, fixed unprivileged UID/GID, and locked worker mount; there is no host-execution fallback.

The actual local Podman probe reported `true` for rootless mode and exit 125 for inspection of the test’s pinned digest because the image is absent. The Python test suite therefore exercises a real local preflight failure and confirms a `local_readiness_only` no-go result with exact rollback. No fixture execution was attempted or claimed; the unavailable image correctly prevents it. The runner’s output and its preregistration explicitly remain non-adopted, non-promotional, local custody evidence, so the failed run cannot be misrepresented as P3/P4 evidence.
