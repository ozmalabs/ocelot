# Attested Podman graph-proposal mediation

The P1 gate replaces worker-selected opaque proposal IDs with complete bounded `GraphActionProposalV1` candidates. Before the worker launches, the evaluator verifies a signed native-export attestation bound to the run, build, control-plane, and input digests; it accepts a candidate only when it exactly equals a still-valid record in that export, then binds the derived V2 request before the broker can act. Verified candidates produce signed `ActionReceiptV3` records carrying the export and attestation digests, while forged, mismatched, and replayed candidates are chained denials with no effect. The rootless-Podman fixture enforces and inspects a constrained, fresh-container profile and scoped cleanup, but it deliberately copies a precomputed candidate from its probe contract rather than running native graph or rule code. Watch for: **confirmed** the gate demonstrates pre-attested native-proposal mediation—not dynamic native-substrate execution or general autonomous planning—and **confirmed** two security documents still instruct readers to use the removed opaque-ID protocol.  
**Verdict**: NEEDS_CHANGES

## High-level view

The evaluator is the authority boundary for this scope. It verifies the export attestation before any sandbox launch, compares the worker’s full candidate to evaluator-held evidence, derives the only V2 action request, and seals that exact request with an evaluator-held in-process binding checked by the broker. The P0 manifest’s empty enablement set remains the first authorization boundary, so the demonstrated route ends in a signed default-deny receipt rather than an effect.

The Podman profile is concrete test evidence for the supplied local engine/image and for its cleanup behavior: local rootless non-remote preflight, a fresh no-network/read-only container, exact ID mappings and resource limits, live inspect checks, and exact-name/tag removal. This is not custody against the same OS user and is not proof that the worker executed a native graph substrate; the fixture’s proposal is supplied in the contract before launch.

The protocol documentation is inconsistent with the enforced interface. `agent_protocol.py` accepts only a `submit_native_graph_proposal` frame containing the complete candidate, whereas two security documents still call for bounded opaque proposal IDs. That mismatch can lead an integrator to build a worker that the evaluator necessarily rejects.

## Complete candidate matching and broker sealing

`EvaluationAgentProtocolV1` allows the worker to send only a run/session-bound `submit_native_graph_proposal` frame containing a dictionary candidate; authority-bearing request, grant, callback, path, and descriptor fields are rejected. `GraphProposalProjector` canonicalizes and structurally validates that candidate, then asks `NativeGraphProvenanceVerifier` to compare it exactly with one record in the evaluator’s export. A differing `args` value or source digest does not get projected from worker bytes: it receives `forged_graph_provenance` and an effect-free signed denial.

For a match, projection uses the evaluator-owned export record, constrains the catalog to `GraphCounterAdvanceV1`, derives identity/nonce/sequence from the verified proposal, and calls `bind_request`. The broker accepts V2 only when `validates_binding` confirms the exact canonical request bytes, run, request identity, sequence, nonce digest, causal predecessor, and proposal digest. Raw V2 submission consequently receives `verified_graph_proposal_required`; worker data cannot select a host callable or smuggle a grant.

The export attestation is verified before launch against an authority key and binds the run ID, agent build digest, control-plane digest, input snapshot digest, and export digest. A verified graph receipt is V3 and includes both `native_export_digest` and the canonical digest of that attestation. Receipt-chain validation verifies hashes and signatures, and V3 records require those provenance fields. The forged/mismatched cases intentionally remain V2 denials, avoiding a false claim that unverified data was attested.

## Replay denial consumes the proposal without producing effects

A proposal is marked used only after a receipt carrying its graph proposal ID has been durably appended. The projector restores this reservation set from V2/V3 history, so the reservation survives reconstruction of a broker/projector. A first valid P0 candidate reaches the existing `method_not_enabled` default-deny result and becomes consumed; a second submission yields `replay`. The focused routing test checks that forged, valid/default-denied, and replayed submissions form a valid receipt chain while the counter remains zero. The provisioned Podman adversary test exercises the same forged, mismatched, and replay paths from separate fresh containers and asserts every receipt is denied with zero accepted effects.

## Podman constraints and evaluator-scoped cleanup

The acceptance launcher requires a local non-remote rootless engine, the exact cached base-image ID, and an explicit seccomp policy. It builds from a finite staged import closure with pulls and build networking disabled, runs under a derived local image with no network, read-only root, a sole constrained tmpfs workspace, private namespaces, fixed rootless mappings, unprivileged user, dropped capabilities, no-new-privileges, seccomp, and explicit PID/memory/CPU/file/process limits. Live `podman inspect` rejects any absent or changed field, host bind/volume mount, or unexpected writable mount; the hostile probe additionally checks descriptors, sentinels, loopback/external networking, and Podman socket reachability.

Cleanup inventories only the exact randomized container name and derived image tag, records that evidence, then stops/removes only those artifacts and verifies that the scoped inventory is empty. The stop test captures a live descendant snapshot and rejects a still-running container or exposed descendant after evaluator-driven stop. The unit suite confirms the command/profile and cleanup scoping; the six real-container acceptance cases were not runnable in this review environment because `P0_RUN_OS_ISOLATION_TESTS=1` and `P0_OS_ISOLATION_PROVISIONED=1` were not supplied. **Not tested:** independent execution of the provisioned Podman profile on this host.

## Native-execution and autonomy boundary

The limitation is explicit in `docs/security/P0A_PODMAN_ACCEPTANCE.md` and `docs/security/P0A_ROADMAP_EVIDENCE.md`: same-user rootless Podman is not evaluator custody, the local attestation signer is a protocol fixture, and the evidence does not prove arbitrary worker code executed a native graph substrate. This is borne out by the staged runtime manifest and `hostile_entrypoint.py`: the image excludes native graph/rule modules, and the entrypoint reads `native_proposal` from `/agent/probe_contract.json` before submitting a copy. **Confirmed:** no worker-side native graph/rule execution produces the candidate in the demonstrated test.

That absence is correctly fail-closed in the intended claim: a dynamically produced native proposal requires evaluator-owned post-launch capture/replay or separately attested substrate evidence, not an opaque ID or precomputed result substituted as proof. The implementation can be approved only as mediation of a complete candidate against a pre-verified export; it does not demonstrate general autonomous planning, dynamic native execution, or evaluator custody.

## Superseded opaque-ID wording

**Confirmed:** `docs/security/P0A_LOCAL_HARNESS_DESIGN.md` says the intended worker protocol carries opaque proposal IDs, and the final “Delivered code policy” paragraph of `docs/security/P0A_ROADMAP_EVIDENCE.md` repeats “opaque-ID protocol.” These statements contradict the P1 protocol validator and the immediately preceding P1 roadmap paragraph, which prohibit that route. Because this documentation defines the expected deployment contract, it should be corrected before the gate is represented as ready for integration.
