# Persistent IAM evidence and verifier-bound credential transport for DISPATCH-085

DISPATCH-085 adds signed inherited-FD credential transport, reloadable IAM predecessor validation, and mandatory predecessor checks before Confidential Space, credential bootstrap, and Track A work. The IAM loader verifies a canonical four-event JSONL chain and binds its terminal receipt to the operation, attempt, prestate, least-privilege condition, and no-export/no-key boundary. Unknown mutation outcomes are conservatively marked as attempted and enter re-observation/rollback, with manual review when state cannot be established. Watch for: **confirmed** — the subprocess path authenticates only a signed digest and never verifies that the bytes in the inherited FD equal that digest; **confirmed** — the persisted predecessor ledger is self-hashed but not verifier-signed, so a forged complete ledger can survive restart; **confirmed** — no transport artifact loader preserves credential provenance across process restart.

**Verdict**: NEEDS_CHANGES

**Disposition**: NO_GO

## High-level view

The credential path avoids token bytes in Python objects and passes an inherited FD to the fixed absolute `gcloud` path with ambient ADC and exports disabled. The byte-integrity check is exposed as `verify_transport_bytes`, but the actual runner does not invoke it, and the public transport factory can sign a caller-supplied digest without binding the FD contents.

The predecessor gates are present at all three reviewed downstream entrypoints and reload a four-event ledger before effectful work. The ledger’s internal hash chain and receipt checks catch ordinary tampering, but there is no trusted external signature or immutable verifier root; downstream reloads also accept the ledger’s packet/evidence commitments when no expected values are supplied.

Mutation uncertainty is handled conservatively: effectful attempts are marked before dispatch, remote failures trigger re-observation and rollback, and an unobservable state becomes manual review. The implementation and local tests do not alter the master runsheet or perform cloud operations, but effectful provisioning remains ineligible until transport byte binding and restart-safe verifier provenance are fixed and the external live artifacts exist.

<summary>Details</summary>

### Inherited-FD transport does not prove the bytes consumed by gcloud

`VerifierOwnedCredentialTransport` retains only `token_fd` and a signed `transport_bytes_digest`; it intentionally does not retain token bytes. `verify_transport_bytes` rejects a different byte string, but it is only a helper used by the test and is not called by `SubprocessGcloudRunner.run`. The runner checks that the FD exists, then passes `/proc/self/fd/<fd>` and `pass_fds` to `gcloud`; the code never reads, duplicates, or otherwise proves the bytes presented on that FD match the signed digest.

This leaves a concrete substitution path: a caller can issue a transport with a caller-selected `transport_bytes_digest` (the factory also has a compatibility path when no bytes are supplied), attach an FD containing different bytes, and satisfy the runner’s signature and metadata checks. The subprocess may therefore consume credentials different from those the verifier committed to. This is **confirmed** by the transport factory and runner implementation. A production verifier must own both the signed digest and the FD payload, or expose a trusted one-shot transport primitive whose byte comparison is part of issuance/consumption rather than an optional caller-side helper.

### Self-hashed IAM ledger is not restart-safe verifier evidence

`_load_lines` checks canonical JSON, event digests, ordering, and the previous-event chain. `_verify_persisted_records` checks the terminal receipt, poststate, exact role condition, and closed credential boundary. The predecessor gates reject missing, failed, or manual-review ledgers before downstream work.

They do not authenticate who produced the ledger. Every digest is recomputed from the file itself, and the ledger schema has no signature, trusted public key, or verifier-issued artifact commitment. An attacker who can replace the ledger can rewrite all four records, recompute the chain and receipt digests, retain the fixed operation/attempt identifiers, and pass `load_verified_iam_predecessor`. The downstream `iam_ledger_path` callers also do not provide packet or evidence expectations, so those bindings are accepted from the ledger rather than checked against the current consumer. This is **confirmed**; a process restart cannot restore verifier provenance from this artifact alone.

### Mutation uncertainty and gates

The backend increments its mutation marker before each remote effect boundary, and the executor sets its phase marker before invoking each effectful backend method. If a call raises after a remote write or its follow-up observation fails, the failure path re-observes and attempts the reviewed rollback. An unavailable observation or failed rollback produces `rollback_failed_manual_review` and keeps `later_operations_enabled` false.

`execute_bootstrap`, `prepare_bootstrap`, and `TrackAConfig.validate` all reject a missing or invalid predecessor before their effectful paths. The gates are mandatory structurally, but their restart-era trust depends on the unsigned self-hashed ledger described above. The signed child-approval and redacted credential-evidence loaders use a caller-supplied trusted public key, but neither closes the transport-handle gap for the actual IAM subprocess nor is the persisted evidence automatically wired into predecessor reload validation.

### Test boundary and protected artifacts

The independent local run passed 95 tests across `test_dispatch085_hardening.py`, `test_iam_predecessor.py`, `test_reviewed_iam_backend.py`, `test_confidential_space_bootstrap.py`, `test_track_a_bootstrap_runner.py`, and `test_track_a.py`. Coverage includes valid and substituted byte strings through the standalone helper, chain/receipt tampering, failed/manual-review terminal rejection, child-approval signature reload, mandatory predecessor rejection, and unobservable mutation manual review. Not tested are a mismatched FD payload reaching the actual subprocess runner, a recomputed forged four-event ledger, or process restart/reload of the transport credential itself.

No cloud, IAM, GCS, VM, credential creation, export, or retry operation was run. The reviewed implementation writes only its caller-selected attempt ledgers; it contains no write path for `P5_MASTER_RUNSHEET.md`. The protected runsheet and checked-in packet were observed without source edits in this review, but both are untracked in this checkout, so Git cannot independently prove their unchanged state against a committed baseline.

### Remaining prerequisites before any effectful provisioning

Before re-review, the repository needs a verifier-rooted exact-byte transport contract, a trusted signed/immutable persisted IAM receipt and ledger with consumer-side packet/evidence binding, and a restart-safe way to rehydrate or reissue the credential transport. Separately, the external execution prerequisites remain: fresh authorized IAM prestate; one approved exact packet/attempt producing the canonical persisted receipt; verifier-signed Confidential Space evidence over real transport bytes and its trusted public key; signed-environment attestation/STS short-lived credentials; exact WIF, authority, KMS, and least-privilege bindings; and fresh IAM/GCS observations. Until those are present and the two provenance gaps are closed, the result is NO_GO.
