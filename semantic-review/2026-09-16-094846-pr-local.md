# Verified evaluator outcome transport bound to native reservation

This change adds a canonical `reservation_digest` to evaluator-verified native exports and persists the matching digest with the native action reservation before an action can complete. The Rust state machine now accepts completion through an opaque `VerifiedActionOutcome`, and its crate-private adapter compares the serialized transport with run, proposal, sequence, snapshot, receipt, and reservation bindings. Python tests exercise canonical export plus missing and altered reservation fields; Rust unit tests exercise a synthetic successful transport and several malformed variants. **Watch for: confirmed — no production receipt verifier or production caller invokes `seal_serialized_evaluator_outcome`; the only `EvaluatorReceiptVerifier` implementation and bridge invocation are test-only, so the evaluator-to-Rust handoff requested here is not actually wired into a runtime path.**

**Verdict**: NEEDS_CHANGES

## High-level view

The evaluator makes the reservation commitment canonical by hashing its run, proposal, proposal sequence, snapshot, and resource quantities, then includes that digest in the verified export. Native phase 2 stores the supplied digest on its `ActionReservation`, and phase 3 requires the minted outcome to match both that persisted value and the expected state binding.

The completion capability is no longer publicly mintable, which closes the previously exposed direct-construction path. Its adapter has the intended shape—decode the evaluator transport, derive local reservation expectations, verify a receipt chain, then mint—but the repository contains neither a real receipt-verifier implementation nor a runtime integration that calls it.

## Test-only evaluator adapter leaves the native handoff absent

**Confirmed:** `EvaluatorReceiptVerifier` and `seal_serialized_evaluator_outcome` are crate-private in `runners/dsl/src/p4_readiness.rs`, but no non-test implementation of the trait or caller of the bridge exists. The repository-wide reference search finds `SignedEvaluator` and all calls to `seal_serialized_evaluator_outcome` only in `runners/dsl/src/p4_evaluator_adapter_tests.rs`, which is compiled under `#[cfg(test)]`. The Python-side `serialized_verified_native_outcome` method likewise has no consumer outside its own tests.

As a result, the bridge never receives an evaluator export during a P4 run, and no production component validates receipt signatures or binds a verified export to persisted native state. The opaque capability prevents external callers from bypassing the check, but it also means there is currently no runtime path that can mint it from a real evaluator outcome. Add the concrete trusted verifier and a production boundary that passes Python’s canonical bytes into the bridge; the end-to-end test should exercise those components rather than the in-crate synthetic verifier alone.

The Python tests cover canonical reservation export plus missing and altered reservation fields. The Rust tests cover a missing serialized digest, a digest altered after export, and a forged synthetic export rejected by their stub verifier. **Not tested (confirmed):** a real evaluator-signed serialized outcome entering a non-test Rust/Python runtime boundary, including verification against the evaluator’s public key and receipt log; that coverage cannot exist until the production verifier and caller are added.
