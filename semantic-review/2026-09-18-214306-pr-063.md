# Canonical signed-environment request for self-custodied diagnostic execution

RS-063 adds a canonical, deterministic request and fail-closed local validator for a future signed Confidential Space run of the generated diagnostic bundle. It binds the current RS-062 artifact index and unsigned KMS lock request to the RS-040 closure, RS-060 bundle contract, and deployment renderer while keeping all production values unresolved. The implementation separates local generation from future KMS signing, durable ingestion, Confidential Space activation, supervisor evidence, and task execution; its commands only validate or write a local audit. The focused suite passes 21 tests, and the checked-in request reports no cloud operations or mutations.

Watch for: **confirmed** the request is not rerunnable from a clean checkout because every bound RS-062 input is under ignored `var/` and the validator requires those files to already exist; **confirmed** the request binds dependency paths but not their contents, so later renderer/definition changes can alter a rerun; **confirmed** the inherited RS-060 policy requires `external_authority_required: true` without an explicit RS-063 self-custody contract. These should be resolved before treating the request as a portable review artifact.

**Verdict**: NEEDS_CHANGES

## High-level view

The artifact boundary is strong for the current workspace: canonical parsing, exact artifact-map equality, file digests, unsigned-lock checks, null production fields, and a disabled run order keep this as a request rather than execution evidence. The audit reports `ready: false`, an empty cloud-operation list, and no mutations, so no KMS signature, upload, activation, supervisor observation, task run, or result claim is being smuggled in.

The request is a future control-plane sequence rather than an apply script. It names the renderer and the immutable Confidential Space posture, but leaves image, closure, IAM/WIP, GCS, authority, and supervisor inputs absent and forbids the future mutating stages. That preserves the required no-go, but the contract's portability and authority semantics are not yet complete.

The main reproducibility risk is that the request's hashes protect the current generated files, not their availability in a new checkout or the source code that will render the future deployment. The authority risk is separate: the generated RS-060 policy still says an external authority is required, while RS-063 is intended to be self-custodied and does not explicitly assert or validate that distinction.

### Current artifact binding and execution boundary

The validator requires canonical JSON, compares the embedded artifact map with the current RS-062 index, recomputes the index digest, checks every artifact's raw file digest, and verifies that the lock request remains unsigned, non-release, and cloud-operation-free. It also requires the KMS operation to remain request-only, leaves production identity and closure values null, and disables every run-order step. **confirmed** the current artifact cannot be mistaken for signed execution evidence: the status is `blocked_pending_approval`, the audit is `ready: false`, signature and authority fields are null, `cloud_operations` is empty, and the claim boundary excludes KMS signing, durable ingestion, activation, supervisor evidence, task execution, and result claims.

The local-only split is concrete: `execution_request.py` has no cloud SDK, subprocess, KMS, GCS, Confidential Space, FreeTSA, supervisor, or task-runner call; the apply plan has no commands and explicitly forbids mutation operations. The seven focused RS-063 tests cover canonical serialization, blocked strict validation, audit output, artifact drift, signature/cloud-bound values, and disabled mutation stages; the RS-040/RS-060 regression tests bring the reported total to 21 passed.

### Generated inputs are not portable enough for a rerunnable request

**confirmed** the request's `input_locations` and every artifact binding point into `var/p5-r0-diagnostic-inputs`. The repository ignores `var/`, and neither `artifact-index.json` nor `lock-signing-request.json` is tracked. On a clean checkout, `_resolve()` rejects the missing files before the request can validate. The deterministic RS-062 generator can recreate the files, but RS-063 neither invokes it nor records a generator/version/seed precondition in its own validator; the request therefore proves exactness only for the current workspace, not rerunnability from the repository artifact.

The action is to choose one explicit custody model: carry a reviewed, non-sensitive canonical index and lock request with the request, or make RS-062 regeneration a declared prerequisite that records and verifies the generator version, seeds, output digests, private-truth custody, and all 11 artifact files before RS-063 validation. Without that, `PASS_REVIEW` means local workspace validation only, not a portable rerunnable request.

### Source paths do not freeze the future deployment semantics

**confirmed** `_validate_sources()` resolves four repository-relative paths, checks the exact RS-040/RS-060 definition path names, confirms that `render_deployment` is callable, and confirms that the upstream definitions remain blocked. It does not hash the contents of `deployments.py`, either definition, or the validator itself. The target closure likewise names the RS-040 file and renderer but contains no source digest commitments.

A later renderer edit can change metadata, CEL, VM, or container output while leaving this request's canonical bytes and artifact bindings unchanged; a later blocked-definition edit can likewise change what a future strict run accepts. **confirmed** this is a reproducibility and trust-boundary gap, not a claim that the current renderer performs a cloud operation. Add exact SHA-256 commitments for the source files that affect rendering and validation, make the source map closed, and verify those commitments before any future render or activation.

### The inherited authority policy is not reconciled with self-custody

**confirmed** the generated `public/policy.json` contains `external_authority_required: true`, and RS-060's complete policy validator requires that value. The RS-063 validator only checks that RS-060 is currently blocked; because its reviewed inputs are null, it does not evaluate this policy boundary. The request leaves authority fields null and says no production authority or signed evidence exists, but never explicitly declares that the evaluator authority is self-custodied or explains why `external_authority_required` does not mean an independent evaluator.

This is not evidence that an external authority was used—none was—but it is an unresolved contract ambiguity at the boundary this request is meant to preserve. Define a diagnostic self-custody mode and validate it end to end, or clarify the field's meaning and add a test proving that no independent evaluator authority is required while KMS/Confidential Space attestation remain separate future gates.

### Test coverage and claim boundaries

The tests establish the intended current no-go and reject several direct mutations of the request, but they do not test the clean-checkout failure, source-content drift, or authority-policy ambiguity. **likely** these omissions would let a future refactor preserve the happy-path assertions while weakening portability or introducing an independent-authority requirement. Add those adversarial cases and assert that any resulting audit still has `ready: false`, `cloud_operations: []`, `mutations_performed: false`, and a claim boundary that excludes signed execution evidence.

The evidence packet's repository-only review state and separate overall `NO_GO` should remain distinct. No current artifact, audit, unsigned lock, or local validator result should be promoted to KMS signature, Confidential Space attestation, supervisor evidence, task execution, or a P5 result.
