# Provisioned Podman P0 probe remains blocked at namespace creation

The acceptance harness invokes the real local Podman CLI, builds a fresh derived image from the cached digest-pinned base, and retains its command profile as evaluator-side evidence. The retained probe reached that build successfully on a rootless, non-remote Podman 4.9.3 engine, but the hardened `podman run` was rejected before a container was created because the host cannot supply a UID/GID mapping for `--userns=private`. Consequently, no live container inspection or worker behavior was executed. **Watch for: confirmed — this provisioned host is not eligible for acceptance until subordinate UID/GID mapping (or the equivalent rootless Podman mapping prerequisite) is configured and every gated probe is rerun to completion.**

**Verdict**: NEEDS_CHANGES

## High-level view

The proposed boundary is a genuine out-of-process Podman boundary rather than an in-process mock: the evaluator builds with `podman build` and starts a named container through `podman run`. The recorded preflight and build establish local engine use and image provenance for this attempt, including a matching cached base image ID and a derived image ID.

The launcher requests a restrictive profile with no host mounts or control sockets, disabled networking, read-only root, private namespaces, dropped capabilities, seccomp, and resource ceilings. **Confirmed gap:** Podman exited 125 while applying the private user namespace, so none of those requested restrictions were live-inspected and neither the hostile worker nor evaluator-controlled termination ran. The acceptance result must remain fail-closed.

## Local Podman boundary and image provenance

The acceptance launcher uses `subprocess.Popen` to execute an exact `podman run` command, rather than replacing the worker with an in-process test double. Its preflight evidence records `rootless: true` and `serviceIsRemote: false`, and local inspection resolved the required base image to `a6f700b96627c9d19a0147d664febb16fa0039b631cf2351b4c51365048ca962`. The subsequent local-only build completed with `--pull=never --network=none --http-proxy=false --layers=false`, producing derived image `8a6961d852141365d3da217100081b11ea2a0d5a6435447a451a9bb5ee62a9ef`; the recorded run targets that image ID, not an ambient tag.

**Confirmed:** this demonstrates the engine boundary and provenance only through image construction. The only `podman run` record has return code 125 and no corresponding container inspect result, so it does not demonstrate a running worker boundary.

## Hardened worker profile never became active

The retained command requests no network, read-only root, only a private `/workspace` tmpfs, private user/PID/IPC/UTS/cgroup namespaces, UID/GID `65534:65534`, all capabilities dropped, no-new-privileges, an explicit seccomp policy, and PID, memory, CPU, and ulimit ceilings. It contains no volume or mount flags, devices, group additions, privileged mode, host namespace, or Podman socket. The intended hostile worker also attempts the current-user and system Podman sockets, loopback/external TCP, and evaluator-created filesystem sentinels; its expected report would be retained only after the evaluator validates it.

**Confirmed blocker:** the host rejected `--userns=private` with `Error: must provide at least one UID or GID mapping to configure a user namespace`. The launcher recorded the failed command and stderr, then its cleanup `podman stop` found no named container. No `inspect` data, worker FD/path/network report, sentinel comparison, receipt/runtime evidence, or post-stop state is present. Therefore the absence of mounts/sockets, authority access, network reachability, capability/resource enforcement, and worker access to evaluator data remains specified and statically asserted, not demonstrated by the executed probe.

## Hostile routing and external termination remain unexercised

The integration suite has separate gated cases for a hostile opaque-proposal route, a forged authority frame, and evaluator `podman stop --time 2` after a descendant is observed with `podman top`. Those cases would provide the required runtime evidence only after the container starts. The retained artifact is from the hostile-route case and stops before its handshake; there is no hostile report or receipt, no forged-frame terminal record, and no descendant or post-stop inspection.

The exact fail-closed remedy is to provision valid subordinate UID/GID mappings for this rootless Podman user (or otherwise meet Podman’s required mapping configuration without weakening `--userns=private`), then rerun `P0_RUN_OS_ISOLATION_TESTS=1 P0_OS_ISOLATION_PROVISIONED=1 pytest -q tests/evaluation/test_os_isolation_integration.py`. Approval requires retained evidence from completed runs showing the live inspected profile, failed hostile access attempts, evaluator-only authority behavior, and confirmed descendant termination.
