# Attested complete-candidate mediation for the Podman probe

P1’s Podman documentation now says that the worker submits a bounded complete `GraphActionProposalV1`, which is admitted only after signed native-export attestation and equality with the matching canonical export record. The source follows this path, and a verified candidate’s default-deny result is recorded with export and attestation digests in `ActionReceiptV3`; forged, mismatched, and replayed candidates remain effect-free denials. **Watch for:** `NativeGraphProvenanceVerifier` still says a public client may name an opaque proposal ID without a body, contradicting this contract. **[confirmed]**

**Verdict**: NEEDS_CHANGES

## High-level view

The worker protocol accepts only a complete candidate, not an ID-only request. Launch verifies the signed export attestation, then admission matches the candidate to its canonical export record before trusted V2 projection; V3 is reserved for that verified provenance, while failed provenance remains V2 denial evidence.

The documents state the correct narrow boundary: test-only same-user rootless Podman mediation, not independent evaluator custody, dynamic native-substrate execution, autonomous or general planning, or external evaluator custody. The pre-launch fixture export and fixture signer in the implementation support that limitation.

## The obsolete opaque-ID contract survives in a provenance docstring

`agent_protocol.py` accepts `submit_native_graph_proposal` only with a `proposal` object, and the worker sends that object to `GraphProposalProjector.submit_native_proposal`. `test_agent_protocol.py` rejects the old-looking `submit_graph_proposal` frame carrying `proposal_id="opaque-id"`.

Yet `evaluation/p0a/provenance.py` says, “The public evaluation client may name a proposal ID, but it never submits a proposal body.” **[confirmed]** `proposal_for_identity` is an internal lookup helper, but it is not a worker-facing path. This wording conflicts with both the actual public worker protocol and all three P1 documents, so it must be removed or changed to describe evaluator-private lookup.

## Attested equality is the gate for V3 provenance

`evaluation_mode` rejects launch without a valid `NativeGraphExportAttestationV1` and passes its digest to `NativeGraphProvenanceVerifier`. Candidate verification resolves one evidence record by ID and requires equality with that record’s complete `proposal`; because the objects are canonical protocol values, the admitted candidate is the canonical export candidate. Trusted code alone then projects and binds `ActionRequestV2`.

`GraphRequestBinding` transfers the export and attestation digests to the receipt, and `ReceiptLog` selects and validates `ActionReceiptV3` only when that provenance is present. The routing and provisioned Podman tests distinguish this from unverified input: an attested default-deny candidate is V3, forged or mismatched candidates are signed V2 denials, and a replay is denied with zero effects. This matches the P1 documentation’s claim that an unverified candidate is not represented as an attested V3 receipt.

## Podman remains a mediation probe, not a native-execution authority

The documents explicitly limit the rootless same-user Podman gate to its hardened test profile and deny that it establishes evaluator custody. **[confirmed]** The integration setup supplies a precomputed export and fixture signature before the worker starts; it has neither an evaluator-owned capture/replay service nor distinct external authority. The documentation therefore accurately avoids claims of dynamic native graph execution, autonomous or general planning, and external evaluator custody.
