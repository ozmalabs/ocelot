# RS-069R15 provenance and immutability hardening

The R15 correction keeps local build provenance separate from the historical R14 Artifact Registry digest observation and leaves remote provenance and remote immutability as `null`. The candidate binding and ledger-adjacent interpretation are review-only, the historical ledger is not modified in the working tree, and this review executed only local pytest/compile/git inspection commands. **Watch for:** **confirmed** — positive remote provenance and immutability claims can still be promoted by a caller-authored self-digesting record; **confirmed** — registry publication flags accept integer `0`/`1` and candidate/remote digest fields are not uniformly strict; **confirmed** — no direct no-cloud subprocess/network guard protects the local-only R15 boundary.

**Proposed state**: `RS-069R15 = NEEDS_CHANGES`. The truthful null projection and preserved historical boundary are suitable for review, but the positive-claim validator and local-only regression boundary are not hardened enough to accept this item.

**Verdict**: NEEDS_CHANGES

## High-level view

The corrected projection has the right claim separation: local provenance is verified, the remote image digest remains an observed R14 fact, and remote provenance/immutability remain unknown. The candidate is explicitly non-production, and the correction artifact says no additional push or downstream operation was performed.

The positive evidence path remains a trust-boundary gap. It recomputes canonical record and evidence digests and binds the request, operation, image, source, and command, but all of those values arrive from the candidate input; there is no authenticated runner-owned or independently fetched remote evidence source.

The candidate boundary is not fully closed: exact boolean checks are used for the remote claim fields but equality-based set membership remains for registry verification and push state, while the image digest check accepts any `sha256:` prefix. The focused suite passes, but it demonstrates acceptance of locally constructed positive evidence and contains no direct assertion that cloud-capable commands or network access are unreachable during R15.

<summary>Issues (4)</summary>

1. **Caller-authored positive remote evidence** — **confirmed**: self-consistent record and evidence digests do not establish that a remote provenance lookup or immutability observation occurred. Reject all positive claims until evidence comes from an authenticated runner-owned/remote boundary, or verify such an independently fetched artifact.
2. **Non-boolean publication flags** — **confirmed**: `registry_digest_verified=0/1` and `push_performed=0/1` pass membership checks because Python treats integers equal to booleans. Require `type(value) is bool` and add regression coverage for both fields.
3. **Loose candidate and remote digest validation** — **confirmed**: the candidate image digest is only checked for a `sha256:` prefix, and related remote/observed digest fields are not uniformly checked with the full 64-lowercase-hex predicate. Apply one strict digest validator to every digest accepted as a positive binding.
4. **Missing direct no-cloud guard** — **confirmed**: the focused tests avoid operation 1 through stale approval/binding state but do not fail if `subprocess.run`, `gcloud`, `podman push`, or network access is invoked. Add a monkeypatched subprocess/network guard around the local R15 path.

### Corrected projection preserves the historical boundary

`candidate-image-binding.json` retains the R14 image digest and remote digest observation while setting `remote_provenance_verified` and `immutable_verified` to `null`; the correction artifact likewise records no provenance lookup and no independent immutability observation. The binding remains `review_only_registry_bound_non_production`, and the master runsheet still leaves R15 `IN_PROGRESS`, so the artifact’s proposed `PASS_REVIEW` is not master acceptance.

**confirmed** — the historical `operation-ledger.jsonl` has no working-tree modification, and the correction points to the historical R14 verified/stop event digests rather than appending a new R15 operation. The repository records a historical R14 push and digest describe; “no remote operation” is accurate only for the R15 correction/review, not for the entire R14/R15 history. The commands run for this review were local only; no gcloud, push, signing, upload, deployment, VM, task, or supervisor operation was invoked.

### Self-digesting evidence can still self-promote remote claims

`_validate_canonical_remote_evidence()` checks canonical field closure, recomputed `record_digest`, recomputed `evidence_digest`, timestamps, and exact request/operation/image/resource/command bindings. **confirmed** — these checks prove internal integrity, not provenance: the test helper constructs the complete “valid” evidence object locally, and `test_valid_digest_bound_remote_provenance_evidence_is_accepted` accepts it without a signature, attestation verification, authenticated fetch, or trusted evidence-store reference. The immutability positive path has the same property.

The loader rejects incomplete fabricated evidence but still accepts a fabricated complete evidence object. Positive remote provenance and immutability must remain rejected until the approved remote boundary supplies independently authenticated evidence; a caller-authored self-digest must not be sufficient.

### Publication flags and digest fields are not closed consistently

The loader uses `target["registry_digest_verified"] not in {False, True}` and the equivalent check for `push_performed`. **confirmed** — integer `0` and `1` satisfy those equality-based membership tests, so a caller can supply non-boolean publication state. The remote claim fields use `type(value) is bool`, showing the stricter boundary needed for the adjacent fields.

`candidate["image_digest"]` is guarded only by `startswith("sha256:")`. **confirmed** — a self-consistent candidate could carry malformed digest text after that prefix, and the interpretation’s remote/observed digest fields are compared for equality without a uniform full digest predicate. Require `^sha256:[0-9a-f]{64}$` for candidate, image-manifest, remote, observed, and evidence-bound digest values.

### Local-only coverage does not directly guard the cloud boundary

The focused suite passes all 24 tests and both R15 Python files compile. Its approval tests stop before `_operation_1`, which is useful fail-closed coverage, but **confirmed** — no test in the R15 module monkeypatches the runner’s subprocess/network boundary and asserts that local correction cannot invoke `gcloud`, `podman push`, or a network client. Add a direct guard so a future refactor cannot turn the local-only correction into a remote operation while the existing tests remain green.
