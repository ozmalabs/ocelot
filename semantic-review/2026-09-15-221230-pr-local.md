# Native P2 envelope binding without a provisioned release lane

The new native worker and evaluator recompute a SHA-256 digest over the received canonical envelope before they plan or reconstruct, rather than copying the frame-supplied digest. The release runner separately loads the locked canonical sealed-input artifact, requires the caller envelope to be byte-identical after canonicalization, and records caller-submitted evidence separately on the normal alternate-envelope denial path. **Watch for:** **confirmed** — this is not a releasable P2 lane: there is no staged signed `P2ReleaseLockV2`, no P2 image, and the only checked-in lock is an intentionally invalid placeholder; **confirmed** — denial before lock validation still writes the caller hash into the receipt's authoritative `input_digest` field.  
**Verdict**: NEEDS_CHANGES

## High-level view

The trust boundary is substantially stronger at execution time. Both native processes derive the digest locally and reject a mismatched envelope before graph work; the evaluator independently reconstructs the expected plan, so a worker reply cannot establish its own truth.

The runner gives the sealed input authority over a caller submission after preflight succeeds: staged-artifact closure, lock keys, image digests, and the canonical sealed file must all agree before the worker is launched. That protects normal scoring and normal alternate-envelope denials, but it does not establish a deployable lane because the required release closure exists only as a local, opt-in test scaffold.

The preregistration explicitly labels P2 as pre-release scaffolding, which matches the observable state: the repository has an unconfigured V1 lock, no signed V2 release lock or P2 Podman tags, and no completed local closure result. The earlier closure attempt also cannot be retried on this host without provisioning storage, since the filesystem is at 100% use with about 1.2 GiB available.

## Digest ownership at the native process boundary

`worker_reply` and `evaluator_reply` each call `locked_envelope_digest` before `graph` or evaluator reconstruction. That helper canonicalizes the received JSON value, hashes it with the local SHA-256 implementation, and compares it with `verified_input_digest`; a mismatch returns an error before planning or scoring. The process-level regressions launch both binaries, demonstrate rejection with an alternate digest, and complete one measured worker-to-evaluator round trip. This is a meaningful correction to the previous digest-copying trust gap.

The Python release entrypoint reinforces the same identity from the other side. It parses the staged sealed-input file only as canonical JSON, requires the caller envelope's canonical bytes to equal those artifact bytes, validates the envelope signature, and checks the raw file hash against the lock. Its worker and evaluator requests carry that artifact digest, which the native processes recompute rather than trust.

## Locked-input receipt authority on denial paths

After successful preflight, a separately signed but different envelope is denied before worker launch. The terminal receipt keeps `input_digest` equal to `lock["artifacts"]["sealed_input"]` and adds `submitted_input_evidence_hash` for the rejected submission. The replay regression verifies the two values differ, so submitted evidence cannot be presented as the sealed artifact identity in this normal denial case.

**Confirmed concern:** before `_release_preflight()` has validated a lock, `P2Runner.score` initializes `input_digest` from `_safe_digest(envelope)`. If lock validation then fails while receipt storage is healthy, the exception path still calls `_finish`, which appends a normal receipt with that caller-derived value in `input_digest` and no separately labeled submission field. The run still fails closed and receives no success credit, but the persisted field has the semantics reserved elsewhere for the immutable lock artifact. A malformed or untrusted lock therefore produces an audit record that cannot truthfully establish which sealed input, if any, was authoritative.

## Scratch-image policy is designed but not staged

The intended container posture is bounded and restrictive: the scratch Containerfile contains the worker plus dynamic loader/library closure; the launcher requires rootless Podman, `--pull=never`, no network, read-only filesystem, non-root UID/GID, dropped capabilities, no-new-privileges, seccomp hashing, bounded resources, and read-only input/agent mounts. The local-only test constructs the closure from `ldd`, requires the loader in `lib64`, builds without pull or network access, pins both images, and then exercises the runner and a raw-frame bypass denial.

**Confirmed release blocker:** this exists only in `test_local_only_p2_release_and_bypass_controls`, guarded by `P2_RUN_LOCAL_OFFLINE_RELEASE=1`. Its lock is created from deterministic test keys and temporary artifacts, not staged release material. The checked-in `evaluation/p2/p2.lock.json` instead declares `P2EvaluationLockV1`, zero hashes, and `UNCONFIGURED-INVALID-LOCK`; `validate_lock` rejects it as a P2 lock schema. The preregistration explicitly says no score is published or claimed until independently produced non-placeholder lock, image, binary, policy, and evaluation evidence are available.

The current machine has no Podman image tag matching P2, and the required opt-in test was skipped in validation. A prior attempt recorded in the supplied context stopped with `ENOSPC`; the final check still shows the root filesystem at 100% capacity with roughly 1.2 GiB free. That is a provisioning blocker, not evidence that a bounded release image ran. Do not approve or claim the release lane until the artifacts are provisioned and the complete offline exercise passes in a retained staging environment.

## Validation boundary

The native executable suite passed all three tests, and the focused replay/receipt/offline suite passed ten tests with the one image-building test skipped. These establish the repaired process boundary and the receipt behavior reachable with synthetic fixture locks. They do not supply the missing production signature, measured artifact manifest, image digests, or a successful rootless Podman transcript; the preregistration's held-out clone and controls gate also has no result evidence in this change.
