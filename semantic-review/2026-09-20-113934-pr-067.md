# Track A evidence hardening remains blocked

DISPATCH-067 adds a typed Track A orchestration boundary around attestation, timing, native execution, receipts, result sealing, and KMS signing. However, the boundary still permits the execution seam to derive timing input before the runner verifies timing, accepts self-described supervisor ownership, and treats a caller-provided receipt summary as a verified chain. The final public result and signing binding also omit commitments required by the P5 contract, and post-start failures have no verified impasse seal.

**Watch for:** **confirmed** timing can be consumed before `_validate_timing`; **confirmed** supervisor/KMS ownership is still supplied through injectable objects and flags; **confirmed** receipt, active-run, result-commitment, failure-seal, and key-version gaps remain. Local tests pass but **confirmed** their fake supervisor, worker, and in-memory KMS client can produce `signed_diagnostic`, so they do not evidence external execution.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** the runner does not own the full timing dependency boundary. It asks an execution object for a time seed and only then verifies the returned record, so the API permits pre-verification derivation.

**Confirmed:** native evidence is structurally validated, but trust and independence are represented by mutable attributes and callbacks on injected objects. The same problem exists for the KMS capability’s client and authority metadata: the code verifies a returned public key, not that the capability was issued by the locked authority or that its key version is bound to the final artifact.

**Confirmed:** task/control outcomes and a digest of a records list are carried into a final binding, but the runner does not independently verify an append-only signed chain or require all required lifecycle events. Task envelopes are not compared with the active run identity, leaving stale cross-run data admissible.

**Confirmed:** success performs persist/read-back/seal verification before final signing, but failure only checks an exact rollback response. The public result drops timing/input/chain fields that the internal signed mapping temporarily contains, and the local happy-path test labels entirely synthetic evidence as signed diagnostic output.

<summary>Issues (8)</summary>

1. **Timing derivation seam** — **confirmed:** `issue_time_seed` is called before `_validate_timing`, and the test execution implementation derives the seed inside that call. Split record acquisition from seed derivation and make verification precede any builder invocation.
2. **Self-asserted supervisor ownership** — **confirmed:** `trusted`/`independent` flags and validator methods are accepted from an injected supervisor, while worker-supplied evidence remains the input to those methods. Require an opaque verifier-issued supervisor capability and externally anchored observation, with adversarial rejection tests.
3. **Receipt chain verification** — **confirmed:** `_validate_receipts` checks only a caller-provided list digest, event kinds, and task/control references; it does not verify signed records, sequence/previous links, run binding, or closure events. Reload and verify the canonical append-only chain and require applicable timing, result, rollback/impasse, and close receipts.
4. **Active-run task binding** — **confirmed:** `_validate_task` checks only that `run_id` is shaped like a digest, not that it equals the runner’s active `run_id`; invocation validation repeats the envelope’s value. Pass the active run into task validation and reject stale or cross-run envelopes before the worker call.
5. **Failure impasse sealing** — **confirmed:** `_cleanup_after_failure` accepts an exact rollback digest and returns a typed impasse without appending/verifying a failure receipt or persisting a result/impasse seal. Add a verifier-owned failure closure that records impasse, rollback, chain closure, and a durable verified seal before returning.
6. **Public result commitments** — **confirmed:** the internal `signed` mapping has timing/input/chain fields, but the returned `TrackAResult.as_dict()` omits them, and the canonical result is only checked for run ID and claim boundary. Make the canonical/public result require and expose the exact `timing_record_digest`, `input_seed_digest`, `input_digest`, and receipt-chain digest.
7. **KMS authority and key-version binding** — **confirmed:** `KMSEd25519Signer` verifies the client’s public key but does not bind `key_version`, `authority.key_id`, or the signer authority into `final_binding`; an explicitly injected client can therefore be locally backed while passing shape checks. Bind the immutable KMS key version and closed authority/transport commitment into the final digest and require a verifier-issued KMS capability.
8. **Synthetic tests overclaim execution** — **confirmed:** `_Supervisor` self-asserts both trust flags, `_KMSClient` signs with an in-memory Ed25519 key, and the happy-path test asserts `signed_diagnostic`. Keep these as structural fixtures that can only produce diagnostic/non-promotable status, and add negative tests proving self-asserted evidence cannot reach signed status.

## Timing-first seam still permits pre-verification seed consumption

**Confirmed.** `TrackARunner.run` calls `capabilities.execution.issue_time_seed(...)` at `services/p5_r0_evaluator/track_a.py:551`, then invokes `_validate_timing` at line 555 and only derives again at line 559. The test execution object implements `issue_time_seed` by calling `derive_time_seed` before returning, so the accepted interface has already built a seeded input before the runner has verified the timing record. `derive_time_seed` validates record shape and RFC-3161 fields, but it assumes the record was already verified; that assumption is not enforced at the execution seam.

The execution contract needs a record-only method whose return cannot contain a derived input or seed commitments produced by the builder. The runner should verify the record and only then call the builder; a test should assert that the builder is untouched until the verifier returns success.

## Supervisor and KMS capabilities remain caller-shaped

**Confirmed.** `_validate_execution` accepts any object with `trusted is True`, `independent is True`, and two callable validators (`track_a.py:394-422`). `validate_authenticated_rs050_evidence` repeats this attribute check and delegates authentication to those injected methods. The worker supplies the identity and observation mapping that is then validated, so a structurally valid, self-digested observation can become promotable when paired with a lookalike supervisor. The protocol documents a separate supervisor boundary but does not enforce one.

The KMS path has the same ownership boundary in a different form. `KMSEd25519Signer` checks that the injected client’s public key matches the supplied authority public key, but the caller still chooses the client, key-version string, and authority mapping. This proves equality of supplied values, not issuance from the locked authority. The final binding has no signer authority or key-version member, so the signed digest cannot reconstruct which immutable KMS identity was authorized.

## Receipt summary is not an append-only receipt chain

**Confirmed.** `_validate_receipts` accepts exactly the fields `chain_digest`, `records`, and `records_digest` plus task/control references (`track_a.py:462-481`). It recomputes the digest of the supplied list and checks that two records have the expected kinds and task digests, but does not verify record signatures, sequence numbers, previous-record hashes, run IDs, timing events, result/close events, or the relationship between `chain_digest` and the records. A caller can therefore manufacture a self-consistent summary and pass the receipt gate.

The repository’s `ReceiptChain.verify_chain` already establishes the stronger canonical V3 mechanics, including canonical parsing, sequence/previous links, signatures, and first-record authority binding. Track A should consume that verifier’s result, not a reduced mapping that merely says `status: verified`.

## Task envelopes are not bound to the active run

**Confirmed.** `_validate_task` requires `run_id` to have digest syntax but receives no expected run (`track_a.py:364-389`). `_validate_execution` compares invocation evidence to `task["run_id"]`, and the runner passes the active run separately to `issue_task`/`submit_task`; neither comparison requires the two run IDs to be equal. A task envelope from another run can therefore be internally consistent and still reach native validation. The fix is to pass `run_id` into `_validate_task` and require it in both task and invocation evidence for task and control paths.

## Rollback does not close a verifiable failure artifact

**Confirmed.** After a post-start exception, `_cleanup_after_failure` calls `execution.rollback` and accepts only `status == "exact"` plus a digest (`track_a.py:506-516`). `_blocked` then returns an in-memory typed impasse (`track_a.py:518-520`); no receipt-chain verification, impasse record, chain close, durable result seal, or seal read-back occurs. This violates the P5 requirement that failures leave a typed, redacted, verifiable impasse closure rather than only a rollback claim. Cleanup uncertainty must remain a no-go and itself be sealed as an impasse.

## Final result and public output lose required commitments

**Confirmed.** The runner places timing/input commitments and `receipt_chain_digest` in the local `signed` mapping, but the returned `TrackAResult` contains only status, disposition, stage, reason, run, result, seal, final-binding, and signature fields (`track_a.py:46-72` and the return path). A caller consuming `as_dict()` cannot see the required `timing_record_digest`, `input_seed_digest`, `input_digest`, or chain digest. More importantly, the runner only checks the canonical result’s run ID and claim boundary (`track_a.py:581`); it does not require the result itself to contain those commitments before sealing.

The canonical result schema and redacted public result must carry the exact three-digest timing/input chain and receipt-chain digest, with the same values validated against the verified seed and receipt chain before sealing and signing.

## Local happy-path tests are not external execution evidence

**Confirmed.** The Track A happy-path test uses `_Supervisor` with literal `trusted = True` and `independent = True` (`test_track_a.py:67-75`), a worker that fabricates supervisor/resource evidence, and `_KMSClient` backed by an in-memory Ed25519 private key (`test_track_a.py:35-43`). It then asserts `result.status == "signed_diagnostic"` and a final signature (`test_track_a.py:290-298`). The test verifies ordering and shape behavior only; it cannot establish Confidential Space attestation, FreeTSA, authenticated supervision, durable receipts, or real KMS execution. Its current assertion overstates what this fixture proves and leaves no adversarial test for a self-asserted supervisor/KMS object.

The tests should distinguish structural diagnostic simulation from a real signed-environment result and must explicitly assert that local callbacks, self-digested observations, and local keys cannot reach a promotable signed status.
