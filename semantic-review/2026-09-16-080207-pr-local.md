# P4-R0 sealed execution and staging closure

P4-R0 adds a local-only signed lock, receipt chain, evaluator grant path, native readiness state machine, and an offline rootless Podman policy. It deliberately fails closed when containment or native stdio attestation is unavailable, preserving non-adoption and non-promotion. The closure verifier rejects substitution, added inputs, and symlinks at the runner boundary, while the native state machine rejects stale and malformed observations. **Watch for:** **confirmed** — the evaluator and native handoff do not yet fully prove that a sealed outcome is bound to the registered proposal and reservations, and the hardened command does not execute the locked worker closure. **Verdict**: NEEDS_CHANGES

## High-level view

The evaluator records a proposal, grant, broker action, and outcome in an append-only signed log, while the native state machine only accepts a host-provided `VerifiedActionOutcome`. **Confirmed:** no reviewed adapter derives that native record from `verify_sealed_action_outcome`, leaving an unaudited construction boundary.

The signed lock fixes numeric budgets, yet action reservations are counted as one per grant rather than as the proposal's requested action amount. **Confirmed:** allowed action kinds are a process constant rather than an allow-list committed by the signed lock, so the evaluator cannot demonstrate that both dimensions came from the preregistered policy.

The runner validates the five staged artifacts against their lock digests before containment preflight and fails closed on the unavailable placeholder image. **Confirmed:** the Podman command starts an image binary without mounting or invoking the staged worker, and it does not consume the staged Containerfile, so successful preflight would not execute the closure it attested.

## Sealed outcome stops at an unchecked host boundary

**Concern (confirmed):** `P4R0Evaluator.verify_sealed_action_outcome` verifies the outcome receipt's immediate hash chain, but it never checks the broker receipt payload against the proposal and grant, the grant payload against its proposal receipt, or the referenced proposal receipt itself. Its return value also is not consumed anywhere in the reviewed P4 path: `advance_p4_r0` receives an already-populated `VerifiedActionOutcome` and only compares its copied strings. A host can therefore provide a structurally valid native outcome record that is not demonstrably derived from the evaluator verifier; and a signed-but-misbound receipt chain would pass evaluator verification because the payload bindings below the outcome receipt are not checked.

The chain must be verified as data, not merely as adjacent receipt hashes:

```text
proposal receipt --binds--> proposal digest, replan parent, run/snapshot
       |
grant receipt    --binds--> proposal + proposal receipt + reservation + limits
       |
broker receipt   --binds--> grant + proposal + sequence
       |
outcome receipt  --binds--> all prior receipt digests + outcome digest
       |
verified native record --> same values, produced only by this verifier
```

The Rust tests exercise a manually constructed `VerifiedActionOutcome`, and the Python test changes an outcome sequence after successful verification. They do not prove that a mismatched broker payload, mismatched grant proposal receipt, cross-run receipt mix, or manually constructed native record is rejected. Add adversarial cases for each mismatch and an integration test that feeds the verifier's output through the actual adapter before `advance_p4_r0` can complete.

## Reservations diverge from the signed action request

**Concern (confirmed):** `_reserve` rejects zero values but compares the action budget using `self.reserved["actions"] + 1`; `grant` then increments the action ledger by one as well. The returned grant retains the proposal's unmodified `reservation`, so a request for two actions is acknowledged as two while only one action is reserved. Eight proposals requesting two actions each remain admissible under the signed `action_grants: 8` limit, even though their grants claim sixteen actions.

Risk and transaction reservations use the requested values. The evaluator should either require exactly one action per grant and normalize the contract to that fact, or debit `reservation["actions"]` and enforce its cumulative total against the signed action limit. The permitted `SUPPORTED_ACTION_KINDS` set remains outside the signed lock; changing program code changes the evaluator's authorization surface without changing the lock reviewers signed. Put the allow-list in the lock, validate it as signature-covered content, and test a lock whose kind policy differs from the module default.

## Podman validates inputs it does not run

**Concern (confirmed):** `run_local` validates the digest closure before calling `launcher.preflight`, preventing the tested input substitution from reaching the launcher. `P4PodmanLauncher.argv`, however, only mounts `/agent` and `/input`, then executes the fixed absolute `/runtime/p4_native_readiness_worker` from the pinned image. The staged `worker_binary` is neither mounted at `/runtime` nor used as the entrypoint, and `container_spec` is never passed to Podman. Their digests are present in the lock but do not constrain the process that would execute.

`preflight` receives only a `P4PodmanSpec`, not the lock's expected closure, so it cannot independently revalidate immediately before launch. Bind the expected closure to the execution spec or provide it explicitly to preflight, validate there immediately before `podman run`, and launch the locked staged worker from the read-only agent mount. If the Containerfile is intended only as build provenance, it should not be presented as a runtime closure input; if it defines the image, build or verify the local image from it without pulls and record that relationship. `run_local` always raises `native stdio protocol not yet attested` after preflight, so even a present image cannot produce the requested fixture run.

## Missing adversarial and fixture-run coverage

**Not tested (confirmed):** no end-to-end verifier-to-native adapter exists to test; no available-image Podman fixture run can prove that the lock closure is what executes; and no test requests `actions > 1` or attempts a valid signed receipt chain with mismatched grant/broker payload bindings. The focused checks passed: `python3 -m pytest evaluation/p4/tests -q` reported 14 passed, and `cargo test --test p4_readiness` reported 7 passed. Podman reported rootless mode, but inspecting the required placeholder digest exited 125; no image was pulled or built.
