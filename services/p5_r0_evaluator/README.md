# P5-R0 V3 evaluator service

This is an isolated, authenticated control-plane wrapper for the existing `evaluation.p5_r0` evaluator. It is not deployed by this change.

The Confidential Space workload is deliberately separate from the Cloud Run entrypoint: `Dockerfile`/`app.py` remain the Cloud Run path, while `Dockerfile.confidential-space`, `deploy/Containerfile`, and `confidential_space_app.py` form the dedicated attested image path. The latter starts with policy-only locked state and exposes `/healthz` plus non-secret `/startup-attestation` evidence before activation.

## Guarantees

- HTTP bodies, GCS objects, task envelopes, receipts, and seals use strict canonical JSON. Duplicate keys, floats, non-NFC strings, unknown fields, and non-canonical bytes fail closed.
- The service reads lock/public manifest/private store commitments from private GCS through `ObjectStore`; truth is never returned to the runner. GCS writes use create-only or generation preconditions.
- `KMSEd25519Signer` obtains and validates the configured KMS `EC_SIGN_ED25519` public key, sends the protocol's SHA-256 digest as raw signing data, and verifies every returned signature locally. No private key is exported or accepted by the service.
- Google-signed OIDC identity tokens are required and the runner principal is bound to run state. Start, task, and result operations enforce idempotency, one outstanding task, sequence, task digest, and immutable receipt replay checks.
- Task envelopes and V3 receipts are signed by the configured authority. The service always reports no-go/impasse for this minimal wrapper because Cloud Run cannot independently prove local crun containment, controls, mechanics contrasts, or rollback closure.

## Timing and third-party seeds

The service records task issuance and result receipt timestamps with its trusted process clock. These timestamps are never accepted from the runner. The task envelope and response expose the service-issued `issued_at_ms` and `expires_at_ms`; terminal records, receipts, and result responses bind the service-observed `received_at_ms` and the exact canonical `result_digest` (the digest of the complete result request). The compute-class observation derives its coarse wall bucket from those two server timestamps.

`services/p5_r0_evaluator/rfc3161.py` provides a separate, digest-only RFC 3161 evidence adapter. It supports the explicitly allowlisted DigiCert endpoint and FreeTSA endpoint (`https://freetsa.org/tsr`, policy OID `1.2.3.4.1`); the currently reviewed FreeTSA artifacts are `cacert.pem` PEM digest `sha256:2151b61137ffa86bf664691ba67e7da0b19f98c758e3d228d5d8ebf27e044438` and `tsa.crt` signer DER digest `sha256:32e841a95cc1164101ffde41298ef2fc75c1c4372ef095e88a6bbd47dfb191fc`. Provider selection still requires the matching CA PEM and TSA certificate pins. It posts only the existing SHA-256 payload digest as the RFC 3161 MessageImprint, rejects redirects and oversized/malformed responses, verifies the CMS token with OpenSSL, and records only token/response digests plus TSA policy and `gen_time`. Its `P5R0RFC3161TimingEvidenceV1` record owns a local sequence/previous-digest chain but deliberately sets `bridge_required` and `bridge_target`; it is not `P5R0IndependentTimingAttestationV2`, and cannot make `timing_certified` true. A separately operated remote Ed25519 timing bridge remains required before the existing service can certify timing. The adapter never uses a caller timestamp or self-authored local clock as evidence; its injected clock is only a bounded freshness rejection check.

A `TimingAttestor` may additionally record signed `task_issued` and `result_received` events. Existing `P5R0IndependentTimingAttestationV2` records remain valid; the additive `P5R0IndependentTimingAttestationV3` record carries the digest of independently verified RFC3161 evidence and is signed by the bridge authority. `timing_bridge.py` now requires a pinned `RFC3161Config` and accepts only a canonical `P5R0RFC3161TimingBridgeEnvelopeV1`: its signed V3 record is accompanied by bounded base64 RFC response proof. The evaluator reconstructs and verifies that proof with the pinned FreeTSA policy, CA, signer certificate, imprint, and freshness bounds, recomputes the exact V1 evidence digest, and only then accepts the V3 record. The proof is internal to the authenticated bridge/evaluator boundary; evaluator result/startup responses and persisted public timing evidence remain digest-only. Bare V3 bridge responses and record-only bridge adapters are rejected because they would recreate the verification gap. The client has no default endpoint, does not provision cloud resources/IAM, and sends only public IDs plus the payload digest in its request. Until a real independently operated bridge endpoint is deployed and configured, RFC3161 evidence remains bridge-required and production timing certification is unavailable. `timing_bridge_service.py` is only the injected server-side seam: it validates the canonical request, re-verifies the returned proof/evidence pair, signs V3, and requires an explicitly durable ledger in production-ready mode; its in-memory ledger is test-only and explicitly non-production. Key custody, the FreeTSA CA PEM and signer pin configuration, durable ledger implementation, HTTPS/TLS policy, endpoint authentication, and production deployment remain external requirements. Such an attestor certifies freshness/order and its provider-observed interval, not the worker's exact CPU start/end or process containment. A runner-submitted timestamp, duration, timeout flag, or seed is never treated as an observation. Timing remains uncertified for GO purposes when no independent attestor is configured.

### Production bridge adapters

`timing_bridge_production.py` is the production-only bridge assembly. `create_production_bridge(...)` requires an explicit `credentials` object (for example credentials loaded from the reviewed service account/ADC context) unless both cloud clients are injected for a controlled test. It constructs `GCSDurableTimingBridgeLedger`, `BridgeKMSEd25519Signer`, the pinned FreeTSA adapter, `TimingBridgeService(production_ready=True)`, and the authenticated WSGI app. It never provisions resources and never exports a private key. The ledger uses only the exact object name `P5R0_BRIDGE_PREFIX/runs/{run_id}/timing-bridge/ledger.json`; appends use GCS generation preconditions, including generation `0` for first creation.

The bridge app factory requires these environment values: `P5R0_BRIDGE_AUTHORITY_JSON` (canonical closed public authority metadata), `P5R0_BRIDGE_LEDGER_ID`, `P5R0_BRIDGE_KMS_KEY_VERSION`, `P5R0_BRIDGE_BUCKET`, `P5R0_BRIDGE_PREFIX`, `P5R0_BRIDGE_FREETSA_CA_PEM_PATH`, `P5R0_BRIDGE_FREETSA_CA_PEM_SHA256`, and `P5R0_BRIDGE_FREETSA_CERTIFICATE_SHA256`. The KMS version must be a bridge-owned `EC_SIGN_ED25519` version and, when `P5R0_KMS_KEY_VERSION` is present in the environment, must differ from the evaluator receipt key. The authority public key is read from KMS and must match the authority metadata. FreeTSA endpoint and policy are fixed to `https://freetsa.org/tsr` and `1.2.3.4.1`; the CA PEM and signer certificate pins remain required. A callable authenticator is also required; Cloud Run IAM/ingress and candidate-bound IAM are deployment responsibilities, not provisioned here. Missing or invalid values leave construction unavailable rather than creating an unauthenticated/default app.

`timing_bridge_auth.py` provides separate IAM Credentials factories: `IAMCredentialsAccessTokenFactory` performs the post-STS `generateAccessToken` exchange for the committed `P5R0_CAPABILITY_SERVICE_ACCOUNT` used by GCS/KMS, while `IAMCredentialsIDTokenFactory` continues to mint the bridge-bound ID token from the original federated token. Both use fixed endpoints, bounded canonical requests/responses, no redirects, and never accept ADC or key material. The evaluator relocks at the effective impersonated-token expiry.

These adapters do not create service accounts, IAM bindings, Cloud Run services, buckets, KMS keys, TLS certificates, FreeTSA CA files, or network policies. Deployment must separately grant the evaluator only the candidate-bound IAM Credentials permission for the bridge service account, grant the bridge service account only its private GCS/KMS/egress permissions, deliver the reviewed CA PEM, and configure HTTPS ingress. The evaluator process must relock when its federated token expires; the bridge service must run with a durable GCS ledger and a separately reviewed bridge key.

## Protocol adaptations still required

The checked-in V3 lock currently uses `P5R0AuthorityV2`, local filesystem receipt roots, and closure fields for local crun/Podman. This service introduces `P5R0AuthorityV3`, `P5R0TaskEnvelopeV1`, HTTP request/response schemas, GCS URI object names, and `P5R0ResultSealV3HTTP`; an adapter is needed before the existing local `verify_result_seal` can verify a GCS-backed seal. The wrapper currently schedules only the 144 primary records and intentionally does not synthesize the locked controls/contrast matrix. It therefore emits an explicit impasse rather than claiming GO.

## Local checks

From the repository root: `PYTHONPATH=. pytest services/p5_r0_evaluator/tests -q` and `python -m py_compile services/p5_r0_evaluator/*.py`. Docker/Cloud Run deployment is deliberately not invoked.


## Compute-class protocol

The compute-class endpoints are application-authenticated with the same Google OIDC verifier as the run control plane. Cloud Run ingress must remain internal; `Authorization` is reserved for platform IAM when applicable and `X-P5-Authorization` carries the application token. No endpoint is intended for public ingress.

1. `POST /v1/runs/{run_id}/tasks/{task_id}/seed` issues one deterministic challenge derived by the configured Cloud KMS Ed25519 key. The response may contain the challenge, but durable state stores only its `seed_digest`, binding, and expiry; private truth and challenge material are never written to GCS. Reusing the same idempotency key returns the same KMS-derived challenge; a different key cannot issue a second seed.
2. `POST /v1/runs/{run_id}/compute-class/observation` requires the committed result, exact server-issued task digest, exact service-computed result digest, seed, and immutable runtime commitments. It emits a signed `P5ComputeClassObservationV2` containing service-observed issuance/receipt timestamps and a coarse wall bucket derived only from their difference. Replays are idempotent and conflicting reuse fails with 409. There is deliberately no runner timing endpoint.

The signed compute-class record states `wall_vs_cpu: provider_wall_transport_interval_not_worker_cpu` and `cpu_time_bucket: not_observed`. A service-observed interval includes request transport and does not prove worker CPU start/end, process containment, or scheduler behavior. The observation is consequently an auditable coarse timing commitment, not a CPU-time or isolation claim. Production startup requires `P5R0_IMAGE_DIGEST`, `P5R0_RUNTIME_DIGEST`, and `P5R0_RESOURCE_PROFILE_DIGEST`; these are non-secret immutable commitments supplied through deployment configuration.

The service still uses generation-checked private GCS objects and never serializes the private case store into run state or responses. It fails closed on expired tasks, missing seed bindings, mismatched runtime commitments, missing timing events, replay conflicts, stale state generations, and unavailable engine state. The Cloud KMS signer only sends SHA-256 digests to `asymmetric_sign`; private key material is neither accepted nor exportable by this service.
